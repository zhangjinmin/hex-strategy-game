## 0. 结论先行

### 0.1 一句话结论

旧案战术层是一份**"结构完整、数值不可用"**的设计：**4 类武器 / 6 舰种 / 12 阵型 / 10 种地形 / 16 项改装 / 30 项特技的战术效果**，其价值在**字段划分与相互关系**，不在数字本身（2012 年草稿，与现项目数值量级差 1~2 个数量级）。整合的正确姿势是**"借结构、不借数值"**。

### 0.2 三条建议（按性价比排序）

| # | 动作 | 为什么值得做 | 代价 | 定级 |
|---|---|---|---|---|
| **1** | **修掉阵型互克的"双表不一致"** | 这是**现存缺陷**，不是新功能：战略层结算与战术层伤害用了**两套不同的互克环**，玩家看到的信息与实战结算对不上 | 改 1 处 import + 2 张内联表 | **P0** |
| **2** | **阵型从"3 个标量"升级为"列位 × 距离带"** | 旧案给了完整的「前列/中列/后列 × 近/中/远/舰载」矩阵，而现项目的阵型**只给整队 3 个乘数**——与该舰站在哪、离敌人多远无关。这是"阵型没手感"的根本原因，且**落地不需要改任何几何** | 新增 1 个纯函数模块 + 1 处伤害结算挂点 | **P0** |
| **3** | **伤害方向从"仅背击"扩展为"前/侧/后三档 + 舰种装甲比"** | 现项目**只有 >135° 的背击 ×1.5**，没有侧击档，且装甲是单值——导致**舰种编成在战术层没有形状差异**。旧案的三向装甲（如高速战舰 前 125 / 侧 30 / 后 15）正好补这个洞 | 改 1 处（约 6 行） | **P0** |

### 0.3 明确不建议照做的四条

1. **不要照搬旧案数值**（舰种 hp 1500 / 装甲 120 与现项目 hp 1200 / def 15 不同量纲；射程用"光秒"而现项目用像素）。
2. **不要把「崩溃」做成可选阵型**——旧案把它列在阵型表里，是因为那张表按"当前状态"视角列条目；**它在语义上是状态**（火力/回避/机动 -50%），应实现为 `fleet._formationCollapsed` 布尔态，而不是玩家能选的阵型。
3. **不要为新增阵型写新几何**——`formationLayout.ts`（429 行）承载了大量已调优的不变量（格距/足迹上限/掉头跳过旋转），另写一套几何会直接撞上 v31-D 的教训。正确做法见 §3.2。
4. **不要做"真弹道拦截"**——现项目没有弹道实体（伤害在 `BattleScene.ts:5418` 一次乘算后直接扣 hp），为拦截新增实体层的收益远低于成本；用"伤害减免"替代（见 §4.2）。

### 1.1 必须记入的两条硬约束（来自本项目既有教训）

1. **`formationLayout.ts` 的几何是调优过的复合体**：格距 26px 与舰长绑定（`FORMATION_SPACING`）；足迹上限 `FORMATION_FOOTPRINT_LIMIT = 6` 由"压缩后格距 ≥ 舰宽"推出；`formationLayerOffsets` 的 R2 低差异序列 + 单调修复是**规格的一部分，不是实现自由度**（换哪一对元素会改变侧向剪影）。**任何阵型改动必须先证明不动这些不变量。**
2. **v31-D 铁律**：阵位旋转真源是 `fleet.formFacing`，且**对称阵型掉头跳过旋转**依赖"旋转下格位集合与自身重合"。**给阵型引入前后不对称的几何改动，会直接让"整体画圆"复发**（该缺陷被用户反馈过 3 次）。

## 2. 整合总原则

### 原则 A：**只加"读取层"，不加"几何层"**

旧案的阵型字段里，**「配置（前 3 后 1）」「旗舰（前/后）」「射角（近/中/远）」全都是对既有几何的"读法"**，不是新的几何需求。

> 现 `formationOffsets()` 已经返回 `[gx, gy]`，`gx` 就是前进轴。**"前列/中列/后列"= 对 gx 做三分**。旧案想表达的东西，现项目的数据结构里**已经全都有了，只是从没被算出来过**。

⇒ **P0 阶段对 `formationLayout.ts` 零改动**。这是把风险压到最低的关键决策。

### 原则 B：新增阵型 = **新增参数，复用几何**

现项目 `formation → geometry` 是 1:1 硬编码（`formationLayout.ts:257-264` 的 switch）。旧案的 12 行阵型显然不可能都配一套独立几何。

⇒ 改为 **"一份几何 + 多份 doctrine 参数"**：`凹型` 复用 `line` 的几何、`包围` 复用 `circle` 的几何，只在参数表里给不同的射角分布/列位模式/效果值。**阵型数可以从 5 扩到 8~10，几何零风险。**

### 原则 C：借结构，不借数值

旧案数值一律**只作"字段存在性"与"相对大小关系"的参考**，实际数值必须按现项目量级重标定，并写进 `config/balance.ts`。

## 3. P0：三项立刻可做（高收益 / 低风险）

### P0-1 · 修掉「阵型互克」的双表不一致 ⚠ 现存缺陷

**现象**：同一个"楔形阵对纺锤阵"，战略层与战术层给出**相反**的结论。

| 调用点 | 数据源 | 楔 vs 横 | 楔 vs 纺 |
|---|---|---|---|
| 战略层自动结算 `gameStore.ts:2940-2941` → `getFormationCounterBonus` | `formations.ts:30-86` 的 `counters` | **楔克横**（楔→横） | 互不克制 |
| 战术层伤害 `BattleScene.ts:5131` | 内联 `beats` | 互不克制 | **楔克纺** |
| 战术层参谋提示 `BattleScene.ts:2943` | 同一张内联 `beats` | 互不克制 | **楔克纺** |

**根因**：`config/formations.ts` 里那张表（附注释"完整五边形闭环：楔→横→纺→圆→方→楔"）与 `BattleScene` 内联的两张表（"楔→纺→圆→方→横→楔"）是**两个不同的 5-环**——同样的 5 个节点，不同的邻接关系。另有一处不对称：战术层用 `1.3 / 0.7`，战略层用 `1.30 / 1.0`。

**修法（推荐）**：

1. **以 `config/formations.ts` 的环为准**（理由：① 它在 config 层且有文档注释；② 被战略层引用；③ 军事直觉更顺——楔形突破薄正面故克横阵、横阵火力密度故克细长纺锤；④ 5 个关系里有 4 个与内联表一致，只差 2 组对）。
2. `BattleScene.ts:2943` 与 `:5131` 两处内联 `beats` **删除**，改为 `import { getFormationCounterBonus }`（或导出 `FORMATION_COUNTERS` 常量）。
3. 顺带统一倍率语义：把 `0.7`（被克惩罚）也收进 config，命名 `FORMATION_COUNTERED_PENALTY`（**该常量已存在但从未被消费**，见 `formations.ts:136`——这也是一处死代码，正好一并收口）。

**影响面**：战术层 `wedge↔spindle`、`line↔wedge` 两组关系会翻转 → **属于行为变更**，必须：① 写台架固定 5×5 互克矩阵；② 真机确认手感；③ 在批次报告中显式标注"生效关系变更"。

**成本**：约 20 行改动，1 个台架。**风险：低**（不涉及几何、不涉及数值标定）。

### P0-2 · 阵型从「3 标量」升级为「列位 × 距离带矩阵」

**目标**：让"阵型"第一次真正作用于**单舰**——同一支舰队里，冲在前面的舰和落在后面的舰打出不同的伤害。

**旧案给的矩阵**（`01_..._整理.md §6.5`）：

| 列 \ 距离 | 近火 | 中火 | 远火 | 舰载 |
|---|---|---|---|---|
| 前列 | **150%** | 80% | 100% | 120% |
| 中列 | 100% | **150%** | 80% | 80% |
| 后列 | 80% | 120% | **150%** | 50% |

**实施方案（三步，全部为新增纯函数，不改几何）**：

**① 新增 `frontend/src/config/formationColumns.ts`**

```ts
/** 列位：由既有阵型几何（gx 轴）派生的"读法"，不改变任何格位 */
export type FormationColumn = 'front' | 'mid' | 'rear';

/**
 * @param offsets formationOffsets(formation, n) 的返回值
 * @returns 长度 = offsets.length 的列位数组
 *
 * ⚠ 中心对称阵型（circle / square）恒返回 'mid'：
 *   它们的格位在 gx 上对称分布，"三分"会把半个环判成"前列"
 *   ⇒ 会出现"圆形阵一半舰队吃 150% 近火"的荒谬结果。
 *   这一取舍同时与 v31-D「对称阵型没有前后之分、掉头只需原地转身」的既有认识一致。
 */
export function formationColumns(offsets: FormationCell[], geometry: string): FormationColumn[]
```

判定：`ratio = (gx − gxMin) / (gxMax − gxMin + ε)`；`ratio < 1/3 → rear`、`> 2/3 → front`、其余 `mid`。
（`gx` 为前进轴且"+"朝敌，故 `gx` 最大者是前列——**用实际极值归一化，不能假设 gx=0 就是最前**，因为 `circle/square` 会出现正 gx。）

**② 新增距离带判定（复用既有 `getIdealEngageDist`）**

```ts
/** 距离带：以该舰队既有"理想交战距"为尺度归一，天然随舰种/地图自适应 */
function rangeBand(d: number, ideal: number): 'near' | 'mid' | 'far' {
  if (d <= ideal * 0.75) return 'near';
  if (d <= ideal * 1.25) return 'mid';
  return 'far';
}
```

> **为什么必须用相对比例而不是绝对格数**：现项目射程已与地图尺寸耦合（`BattleScene.ts:464` 的 `maxRange` 随地图缩放；`getIdealEngageDist` 返回 560~880px），而 `hexRadius` 会在 26~50 之间动态变化（`:2629-2633`）。**若用绝对格数分档，地图缩小时全部交战都会落进"近距"档。** 以 `ideal`（既有量，代表"本舰队最舒服的距离"）为分母，则三档在任意地图尺寸下都成立，且**驱逐（ideal 560）与战列（ideal 800）各自的口径自动区分**。

**③ 挂点**：`BattleScene.ts:5418` 的乘算链**追加一个乘区**（不改动既有 9 个乘区）：

```ts
// 每单位独立计算（注意：Unit 已有自身坐标 u.sprite.x/y 与 slot 序号）
const col = columns[slotIdxOf(u)];              // 列位（阵型几何）
const band = rangeBand(distToNearestEnemy(u), idealEngageDist);  // 距离带（自身位置）
const columnMul = FORMATION_COLUMN_MATRIX[col][band];             // 旧案矩阵查表
finalDmg *= columnMul;
```

**关键性质（必须写进注释并在台架上验证）**：

- **前列的舰天然离敌更近 → 落"近距"档 → 吃 150%**；后列的舰被拉开距离 → 落"远距"档 → 吃 150%。**矩阵的"列位 × 距离"两维在实战中自动相关性成立**，不需要额外强制 —— 这正是该矩阵设计得妙的地方。
- 因此"把主炮舰放在后列"会**掉进远距 150% 档**（对主炮远程舰是增益），而"把驱逐放前列"则吃近距 150%——**列位不再是装饰**。
- **`circle / square` 恒 `mid`** ⇒ 二者得到的是 100/100/100 的均匀档，与它们既有的高 `defenseMod`（1.35 / 1.25）、低 `attackMod`（0.70 / 0.80）语义一致（防御阵不给火力专精）。

**成本**：约 120 行（含矩阵与注释）+ 1 个台架。**风险：中低**（新增乘区会改变平衡，但可用一个全局系数 `COLUMN_ENABLED` 一键回退）。

**验证要求（本项目无自动化测试，必须自建）**：
- 台架 1：`formationColumns()` 对 5 种几何 × n ∈ {1, 7, 30, 120} 的输出分布，断言 ① 长度 = n；② `circle/square` 全 `mid`；③ `wedge/line` 的 `front` 集合 = `gx = max` 那些格。
- 台架 2：矩阵单调性——对任一列，`MAX(该列三档)` 出现在旧案标注的档位上（前列→near、中列→mid、后列→far）。
- 台架 3：单场战斗的伤害分布——同一舰队内各单位 `columnMul` 的标准差 > 0（证明"阵位真的生效了"）。

### P0-3 · 伤害方向：从「仅背击」扩展到「前 / 侧 / 后 × 舰种装甲比」

**现状**（`BattleScene.ts:5385-5394`）：只有一档背击。

```ts
const angleDiff = | 目标舰队位置→本单位 的方位角 − 目标舰队 facingAngle |;
if (angleDiff > Math.PI * 0.75) { backstabMulti = 1.5; /* CRIT! */ }
```

**缺口**：
1. **没有侧击档**（45°~135° 全按正面算）；
2. **装甲是单值**（`baseStats[cls].def`）—— 导致**编成选择在战术层没有"形状"**：高速战舰与盾战舰除了 hp/def 的标量差，挨打方式完全一样。

**旧案给的结构**（`01_..._整理.md §6.3`）：

| 舰种 | 前装甲 | 侧装甲 | 后装甲 | 前/侧 | 前/后 |
|---|---|---|---|---|---|
| 盾战舰 | 120 | 80 | 30 | 1.50 | 4.00 |
| 标准战舰 | 100 | 50 | 20 | 2.00 | 5.00 |
| 高速战舰 | 125 | 30 | 15 | **4.17** | **8.33** |
| 巡航舰 | 50 | 20 | 10 | 2.50 | 5.00 |
| 驱逐舰 | 30 | 15 | 5 | 2.00 | 6.00 |
| 标准空母 | 80 | 60 | 30 | 1.33 | 2.67 |

**读出**：**盾战舰三向最均衡（1.5× / 4×），高速战舰最怕侧后（4.17× / 8.33×）**，空母次之。这正是"突击舰要正对敌人"的机制来源。

**落地方案（锚定现状，连续迁移）**：

```ts
// 方向档（以"目标舰队朝向"为参考系）
//   ≤45°   → front  ×1.00
//   (45,135]→ side   ×clamp((前装甲/侧装甲)^0.5, 1.00, 1.60)
//   (135,180]→ rear  ×clamp((前装甲/后装甲)^0.5, 1.20, 2.00)
```

- **取平方根压缩**：直接线性用装甲比会得到 8.33× 这种破坏平衡的倍率；开方后 高速战舰侧 2.04× / 后 2.89×、盾战舰侧 1.22× / 后 2.00×，**相对关系保留、绝对量级可控**。
- **clamp 下限锚定现状**：背面下界 1.20 高于正面，上界 2.00 容得下现状的 1.5 —— **现有平衡不会突变**（盾战舰后击仍≈1.5，与现状一致）。
- **舰队级倍率 = 按目标舰队编制加权平均**该舰种的装甲比（而非取旗舰舰种），这样"高速战舰多的部队侧后被爆很痛"成为编成决策。
- **挂点**：`BattleScene.ts:5389-5394`（原地替换约 6 行）。**不要新增乘区**，直接替换 `backstabMulti` 的赋值逻辑，`CRIT!` 提示条件改为 `backstabMulti > 1.2`（`isCrit` 已在 `:5557` 按此判定，正好复用）。

**成本**：约 40 行（含舰种装甲表）+ 1 个台架。**风险：低**（单点改动、上限受 clamp 保护）。

**必须避开的坑**：
- **参考系必须是"目标舰队的实际运动方向"，不是舰首平滑值**。现项目 `formFacing` 是低通滤波值（`rateLimitAngle`），在急转/撤退时会短暂与新航向背离，若用舰首算会出现"背向敌人却在挨正面的伤"的观感矛盾。**建议优先取 `atan2(vy, vx)`（实际速度方向），速度过低（`|v|² < FORM_FACING_MIN_SPD2`，该阈值已存在于 `:5112`）时回退到 `formFacing`。**
- 旧案的**三向装甲值不可直接用**，只用于确定"哪一档更痛"的偏序；实际值写入 `config/balance.ts`。

## 4. P1：值得做，但需要新机制或新标定

### 4.1 地形表的「索敌」列（**性价比最高的那一列**）

- **现状**：4 种地形 ×（移速 / 射程 / 闪避）。
- **旧案**：10 种地形 × 5 列，其中**移动/索敌/损伤**三列是"等级化"的（无/小/中/大/极大/特殊）。
- **为什么选索敌列先做**：现项目**已有插槽**——`getVisionRange()`（`:2870`）返回视野半径，`:4295` 已按 `d > visionRange*0.5` 判 `partial`（只识别舰队类型）。给地形加一个 `visionMul` 并乘进 `getVisionRange`，**零新机制、零新状态**。
- 旧案等级映射建议（借"相对关系"）：`无 → 1.0`、`小 → 0.9`、`中 → 0.75`、`大 → 0.5`、`极大 → 0.3`、`特殊 → 需专门实现`。
- 对应到现 4 种地形：`nebula`（旧案最接近"杰夫粒子云/星云"）→ 0.5；`asteroid` → 0.75；`debris`（残骸 = 旧案"陨石带"）→ 0.5；`gravity` → 0.75。
- **副作用需注意**：视野降低会让 AI 目标选择抖动（`closestEnemyFleet` 可能频繁切换）→ **必须在同一批次验证 AI 行为稳定性**（参考 `docs/qa/v20_*` 的对战运动学判据：Δrel 沿航向投影的符号翻转率）。

**新增地形（机雷 / 杰夫粒子云）**：`tilesDict` + `renderTerrainMarkers`（`:2687`）都是数据驱动，**新增一种地形 = 加一个 switch 分支 + 一个配色**，成本极低。但是：
- **机雷**需要"清除"动作（旧案"清除=可"）→ 需要新指令；
- **杰夫粒子云**需要"爆炸链式反应"→ 需要新机制。
⇒ **建议只加地形本体（移动/索敌/损伤三列），不做"清除 / 冒险使用"两列**，把这两列留到 P2。

### 4.2 「迎击导弹」= 拦截机制（**用伤害减免替代弹道实体**）

- **现状**：无拦截概念；空母/电子舰没有功能性差异。
- **旧案**：迎击导弹（360° 球形、射程 1~3 光秒）专门用于拦截；阵型表中「凹型」给**拦截 150%**；舰种表中**巡航舰防空 150 为全表最高**。
- **推荐方案（20% 复杂度 / 80% 效果）**：**不做弹道实体**，在 `finalDmg` 链上加一个减伤乘区：

```ts
const intercept = fleetInterceptRate(targetFleet);   // 由编制加权（防空值归一化）
finalDmg *= 1 / (1 + intercept);                     // intercept ∈ [0, 0.6]
```

  - `fleetInterceptRate` = Σ(舰种防空值 × 数量) 归一化到 [0, 0.6]，**巡航舰权重最高**（旧案防空 150）→ 让巡航舰从"中庸舰"变成"防空核心"。
  - 视觉侧可挂既有 `battleFx.ts` 的护盾涟漪/弹幕（**注意 `battleFx.ts` 是唯一真源，战场与巡览共用，不要在 BattleScene 新写特效**）。
- **明确不做**：真弹道拦截（需要弹道实体 + 穿透判定 + 与 `backstabMulti` 的方向交互），收益/成本比不成立。

### 4.3 「阵型崩溃」状态（补齐士气链的中间档）

- **现状链路**：士气下降 → `retreatDoctrine` 三档撤退（disengage / withdraw / rout）。
- **旧案**：崩溃 = 火力 / 回避 / 机动 **-50%**，是**比撤退更前的中间态**；触发源包括「旗舰被击破」「士气低落」（多个特技可以施加或防止它：冷静 / 幽雅 施加，棋手 防止）。
- **建议**：新增 `fleet._formationCollapsed: boolean`，触发条件（建议，需标定）：
  1. 旗舰（`formationOffsets` index 0 所在单位）被击毁；
  2. 舰队士气 < 阈值（与 `moraleDrainPerTick` 同源）；
  3. 被敌方特技"阵型崩溃"命中。
  效果：`attack / defense / mobility` 各 ×0.5，并允许「棋手」类特技免疫。
- **与 v31-D 的耦合点**：旗舰位暴露度 = `formationOffsets[0]` 的 `gx` 相对位置（前列更易被击毁）——**这是"读"几何，不是改几何**，符合原则 A。
- **注意**：不要把它做成玩家可选的阵型项（见 §0.3 第 2 条）。

### 4.4 特技战术效果扩维（3 个候选维度）

`utils/skillEffects.ts` 现 7 维。旧案战术效果里现项目**确实没有**的：

| 候选新维度 | 对应旧案特技 | 前提 |
|---|---|---|
| `formationCollapseResist`（阵型崩溃防止/施加） | 棋手、冷静、幽雅 | 依赖 §4.3 先落地 |
| `intercept`（拦截/防空加成） | 凹型阵的 150% + 未来"拦截强化"改装 | 依赖 §4.2 |
| `weaponFire`（射击武器专精，只作用于光线炮/轨道炮类） | 真·神射手（+20%/+30%） | 需要 §4.5 的武器分类 |
| （`fatigue` 疲劳度） | 烈风、巧妇、义肢 | **现项目零疲劳概念**，属新增状态，非扩维 |

> ⚠ `computeCombatModifiers` 有 `MAX_MODIFIER = 1.5` 上限（`skillEffects.ts:10`）。**扩维前后都要检查该上限是否会把新维度吃掉**——上限是按维独立生效的，但多个特技叠同一维时会撞顶（旧案单特技就有 +30% 量级，3 项特技叠满即触顶）。

### 4.5 舰种参数升维（武器三槽 + 转向）

- **武器三槽**（主炮 / 轨道炮 / 导弹）：现项目每舰只有单一 `atk / range / interval`。旧案给了三槽数量——**"怎么打"取决于舰种类别**（驱逐主炮 0、轨道炮 6；空母主炮 8、轨道炮 0）。
  - **推荐简化**：不改数据结构，改**语义**——把现 `range / interval` 视为"该舰主武器的距离与节奏"，再新增一个 `preferredBand`（near/mid/far）与 §3.2 的距离带矩阵对接。**这样舰种与距离带第一次产生联系，而零结构改动。**
- **转向值**（旧案 40/50/30/40/100/40）：现项目已有角速度 + 制动/吸附逻辑（**v29 曾因只测建立时间不测过冲而出现 −13.5° 过冲 / 7 次符号翻转的"波浪舞"**）。
  - ⚠ **若要用旧案转向值重标定舰种转向，必须同时验「建立时间」+「过冲/振荡（角速度符号翻转次数）」，不得只验其一。** 诊断脚本范式见 `_v29_osc_diag.cjs`。
  - 建议直接**延用现项目的制动口径**（目标速率上限 `sqrt(2·a·|d|)` + `|d| ≤ 步长` 时吸附清零），只改转向速率常量。

## 6. 反方审查：这套整合最可能失败在哪里

按"如果失败，先死在哪"排序：

1. **【最高】撞 v31-D 的旋转铁律**。
   只要有人"顺手"把阵型的旗舰位从 `[0,0]` 改到后列、或让 `circle/square` 的格位变成前后不对称（例如为了让"后列"更明显），**对称阵型掉头跳过旋转的条件（`BattleScene.ts:5122` 的 `_sym` 判定）就会失效 → "整体画圆"复发**。该缺陷被用户反馈过 3 次。
   **对策**：§3.2 的方案**只读不写几何**；若一定要新增几何，必须把 `FORMATION_FOOTPRINT_LIMIT` / `FORMATION_SPACING` / `FORM_SKIP_SPIN_RAD` 三条不变量写成台架断言，改几何前先跑。

2. **【高】平衡被乘区叠加击穿**。
   现 `finalDmg` 已有 **9 个乘区**（`:5418`）。再加"列位 × 距离带"（最高 1.5）与"侧/后装甲"（最高 2.0），**理论叠加上限会到 3.0×**。
   **对策**：① 两个新乘区都设**独立的总开关常量**（`COLUMN_MUL_ENABLED` / `DIRECTION_ARMOR_ENABLED`），可一键回退；② 新乘区**只对 AI 与玩家同时生效**（避免出现"玩家靠机制碾压 AI"的不对称）；③ 在 `balance.ts` 里给"单次命中最大倍率"设硬上限。

3. **【高】"距离带"在混战中抖动**。
   单位到最近敌舰的距离逐帧变化，若 band 跨越阈值，伤害会**逐帧跳变**（100% ↔ 150%），观感是"伤害数字忽大忽小"。
   **对策**：① 加**滞回**（进入 near 用 0.75×ideal，退出用 0.85×ideal）；② 或按"每秒采样一次"更新 band，而非逐帧。**不处理这一条会直接被用户当成 bug 报回来。**

4. **【中】以 `ideal` 为分母的地图耦合**。
   `getIdealEngageDist` 的 560~880 是**凭舰种硬编码**的，而实际交战距离受地图尺寸、双方接近速度影响。在小地图上可能出现"所有单位都在 far 档"或都在 near 档，**列位矩阵退化成全局常数**。
   **对策**：台架上统计"单场战斗中三档各自占比"，若某一档占比 > 70% 则说明尺度选错，需把分母改为 `min/max` 混合（如取 `0.6×ideal + 0.4×全场中位交战距`）。

5. **【中】零自动化测试 ⇒ 回归面全靠自建台架**。
   仓库**没有任何 `*.spec.ts`**（已核实）。上述每项改动都必须配一个 `_vXX_*_sim.cjs` 台架，且**验收顺序必须是：改 → 冻结哈希 → 独立验证（打在终态上）→ 真机**。跳过任何一步，等于把"是否真的生效"交给运气。

6. **【低但真实】旧案数值的语言陷阱**。
   旧案的"射程 1~2 光秒""装甲 120""瓦普 2"与现项目量纲全不同；若有人图省事直接抄表，会出现"战列舰射程 2px"这类荒谬值。
   **对策**：把旧案数值**只写进 01 文档作为参考**，任何进入 `balance.ts` 的值都必须重新标定并注明来源为"结构参考、数值重标"。
