## 0. 一句话结论

用户「从正面看阵型是一条斜线、不是从全局三维角度布阵」的指控，由两个**独立**缺陷叠加而成——**排内层号单调**（`formationLayout.ts:295-296` 的 `rank % Leff`，实测 73.3% 的多格排单调）与**恒定 16 层对小足迹舰队的过度加高**（`fleetTierLayout.ts:65`）。定案采用 **R2 低差异序列分层**（`li = floor(frac(k·α + r·β)·L)`，α=1/φ、β=1/φ²）**并由平面足迹推导层数 L**（候选 F）：30 组对比下，排内单调占比 **73.3% → 6.9%**，最差 PCA 各向异性中位 **0.9884 → 0.8335**，被判「读作一条线」的档位 **14/30 → 2/30**（剩下 2 档是 `line n=6/8`，物理上就是单排，见 §5）。

## 1. 问题定义：把指控翻译成可检验的几何命题

### 1.1 命题

> **俯视轮廓与正视轮廓，都必须是二维有面积的形体；不允许在任一视角下退化成一条线。**

用户的原始描述（转述）包含两个互相独立的观察，必须分开处理，否则会误诊：

| 用户观察 | 几何含义 | 归属 |
|---|---|---|
| 「俯视看还行，是长方形的」 | 平面足迹（gx×gy）确实有面积 | ✅ 已满足，无需改 |
| 「正面看过去就是个斜线」 | **正视剖面**退化成线 | ❌ 缺陷，本文针对此 |

关键：俯视 OK **不等于**正视 OK。三维布阵要在**三个正交投影**（俯视 / 正视 / 侧视）里都读得出「有体积的队形」，而不是只在俯视成立、其余角度塌成线。

### 1.2 判据的数学形式

对某视角下的投影点集做 **PCA**，取两个特征值 `λ1 ≥ λ2`：

```
各向异性   aniso  = λ1 / (λ1 + λ2)          ∈ [0.5, 1]
                 → 1 表示点集退化为一条线（全部方差落在单一主轴）
垂直主轴展宽 bandW = 2 · √(3 · λ2)          （单位：世界 px；除 spacingEff 即得「格距」）
                 → 对 ~均匀分布，2√(3·var) ≈ 该方向的实测全宽
「读作一条线」判据：  bandW < 0.5 × spacingEff      （spacingEff = 26 时 ≈ 13px）
```

- `aniso → 1` 或 `bandW → 0` 都是「退化成线」的等价信号；`bandW` 更贴近视觉（它直接是**屏幕上的宽度**）。
- 判据要**遍历多视角取最差**：只测俯视会把 `line` 误判为「正常」，只测正视会把 `circle` 误判为「正常」。台架取了 10 个视角（`_v8c_final.json` 的 `views`），报「最差 aniso」与「最薄 bandW」。
- 阈值 `0.5 × spacingEff`：当最薄方向的展宽不到半个格距时，相邻两排在屏幕上分不开，肉眼读到的是**一条线**而不是一个面。台架里 `spacingEff = 26`，取常量 `13`（`_v8c_final_candidates.cjs:203-206`）；严格按定义它应随 `spacingEff` 定标（`line n=120` 的 `spacingEff = 20` ⇒ 阈值 10），此处 13 是偏宽松的近似，不影响结论方向。

### 1.3 旧判据为何失明

上一轮用的 `staircaseIndex == 0`（「不是整排抬升的阶梯」）**对「排内单调」结构性失明**：

- `rank % Leff` 让**同一排内名次连续** ⇒ 排内层号必然逐格变化 ⇒ 任何一排都**不是「整块抬升」** ⇒ `staircaseIndex` 恒为 0。
- 于是旧判据对每一支舰队都报「PASS」，**从未**能把「每排从侧面看是一条斜线」这个真实故障标红。

> 因此本文**新引入** `aniso` / `bandW` 这组判据，并把它落到台架里。这是本轮的方法论增量：**旧判据测的是「排与排之间有没有整块错层」，新判据测的是「点集在任意视角下有没有面积」。** 二者测的不是同一件事。

## 2. 根因（两条，附源码与实测）

### 根因 1 · 排内层号单调（"每排一条斜线"）

`formationLayerOffsets()`（`formationLayout.ts:288-298`）先按 `(gx, gy)` 排序取名次，再：

```ts
// formationLayout.ts:295-296
const order = offsets.map((_, i) => i)
  .sort((a, b) => (offsets[a][0] - offsets[b][0]) || (offsets[a][1] - offsets[b][1]));
for (let rank = 0; rank < n; rank++) out[order[rank]] = rank % Leff - (Leff - 1) / 2;
```

排序键使**每一排内名次连续递增**；当排宽 `w ≤ Leff` 时 `rank % Leff` 不折返 ⇒ **排内层号严格单调** ⇒ 该排从侧面看是一条**斜线**。（排宽 > Leff 时才会折返打断单调，而大 n 才可能排宽 ≥ 16。）

**实测（`_v8c_final.json`，候选 `A.baseline`）**：

| 指标 | 值 | 备注 |
|---|---|---|
| 多格排中「层号单调」的占比 | **73.3%** | `_v8c_final.log` 汇总行 |
| 最差 aniso 中位（跨 30 组） | **0.9884** | 逼近 1 = 一条线 |
| `scr12`（注视角）aniso 中位 | **0.9862** | |
| 被判「读作一条线」的档位 | **14 / 30** | 含 `wedge/n6(5.6) line/n12(3.7) spindle/n6(3.4) circle/n6(2.5) square/n6(1.9) …` |

其中 `line n=6/8` 的 `aniso = 1.0000`（`_v8c_final.json`：`worst = 1`、`minBand = 0`）—— 在所有 10 个视角里都退化成一条线（原因见 §5，属阵型定义使然）。

### 根因 2 · 恒定 16 层对小足迹舰队过度加高（"竖直的针"）

`TEAM_LAYERS = 16`（`fleetTierLayout.ts:65`）**无条件**被施加，而层距 `LAYER_GAP = max(0.3125×spacingEff, 1.2×maxShipH)`（`layerGapFor`，`fleetTierLayout.ts:96-100`）。当 `spacingEff=26` 时比例项胜出 ⇒ `LAYER_GAP = 8.125`，16 层名义厚度 `(16−1)×8.125 = 121.9` —— **与舰队平面大小无关的常量**。

⇒ 平面足迹小的舰队，纵向远超水平跨：

| 舰队 | 纵深 gx | 横向 gy | 纵向 vert | thin = vert / min(gx,gy) | 读作 |
|---|:--:|:--:|:--:|:--:|---|
| `line n=12`（A.baseline） | 26 | 130 | 89.4 | **3.438** | 竖直的针 |
| `line n=20`（A.baseline） | 26 | 234 | 121.9 | **4.688** | 竖直的针 |
| `spindle n=12`（A.baseline） | 156 | 52 | 89.4 | 1.719 | 偏瘦 |

（数据源：`_v8c_final.json` 对应 `cand = "A.baseline"` 条目；`thin` 列即字段 `thinRatio`。）

> **两条根因必须分别修**：只换分层算法（`E.r2(L16)`）能拆掉斜线，但 `line n=12` 的 `vert` 从 89.4 反而升到 105.6、`thin` 从 3.438 升到 4.063（更"针"）——这正是 `_v8c_final.log` 里 `E.r2(L16)` 的 `thin中位 1.875` 比 baseline 更差的原因。**必须同时引入"层数由足迹推导"。**

### 定案 · 候选 F（R2 分层 + 足迹推导层数）

```
li  = floor( frac(k·α + r·β) · L )                       // k = 排内序号, r = 排号
α   = 1/φ  = 0.6180339887498949
β   = 1/φ² = 0.3819660112501051
层低差异 → li − (L−1)/2

L = clamp( 1 + round( K × min(widCells, depCells) × spacingEff / layerGap ), 1, 16 )
K = 1.0
widCells = 最宽排宽度 − 1     depCells = max(排数 − 1, 1)
```

（实现：`_v8c_final_candidates.cjs:90-124`；工程落点建议见 §7。）

**30 组对比汇总**（`_v8c_final.log` 汇总段，逐字段可核）：

| 候选 | 排内单调占比 | 最差 aniso 中位 | scr12 aniso 中位 | scr12 bandW 中位 | thin 中位 | uniqL 中位 | 「读作一条线」档位 |
|---|:--:|:--:|:--:|:--:|:--:|:--:|:--:|
| `A.baseline`（现状） | 73.3% | 0.9884 | 0.9862 | 42.2 | 1.172 | 16 | **14 / 30** |
| `E.r2(L16)`（只换分层） | 6.9% | 0.8652 | 0.7704 | 88.3 | 1.875 | 8 | 2 / 30 |
| **`F.r2(足迹L)`（定案）** | **6.9%** | **0.8335** | **0.7289** | 73.5 | **0.938** | 7 | **2 / 30** |

> `E` 与 `F` 都把「读作一条线」压到 2 档；**F 额外把 thin 中位从 1.875 拉回 0.938**（≈1 = 纵向与平面最薄方向相当，等轴），而 `E` 反而把小舰队拉成更瘦的针。这是选 F 而非 E 的定量理由。

## 3. 五种阵型的三维语义表（后续改阵型的对照基准）

**读表约定**（与台架字段一一对应）：

- `wid` = **gx 方向世界跨**（舰队前进轴 = 纵深），`dep` = **gy 方向世界跨**（横向），单位 = 世界 px。
- 纵向厚度 `vert` = 实测层跨度 × 层距（`_v8c_final.json` 的 `vert`）；标称值 = `(L−1) × layerGap`（R2 可能少填最外侧一层，故实测常略小于标称）。
- `thinRatio` = `vert / min(wid, dep)`；`aniso` / `bandW` 见 §1.2；`(视角)` 为取得该最值的视角名。
- **俯视轮廓**（用户认可的部分）沿用既有几何定义；**正视轮廓**为本轮新增定义：沿 gx 轴反向投影，看到的是 **`dep`（横向） × `vert`（纵向）** 的剖面——本文要求它**恒为有面积的矩形带**。
- 取 `n ∈ {6, 12, 40, 120}`，逐行给「改造前 `A.baseline` vs 改造后 `F.r2(足迹L)`」。**所有数字直接取自 `_v8c_final.json`，未作估算。**

## 4. 设计决策与理由（第一性原理）

### ① 为什么用 R2 低差异序列，而不是随机 / 哈希

目标有三条硬要求，缺一不可：

1. **确定性**（工程硬约束：`12` §4「无随机（确定性）」；且 3D 层每帧重算层号，随机会导致**闪层**）。
2. **排内去单调 + 排间去对齐**：排内层号不能单调（否则斜线），且不同排的同一列不能落到同一层（否则出现**竖直的墙**）。
3. **无查找表**：n 会随兵力浮动（每帧可能变），任何按 n 硬编码的层序表都会失同步。

`li = floor(frac(k·α + r·β)·L)` 同时满足三条：

- **确定性**：纯整数算术，同 `(k, r, L)` 必得同 `li` —— 与 `tierIndexOf` 同类的"同输入同输出"。
- **低差异**：α=1/φ、β=1/φ² 是丢失最小的一般化黄金比，Kronecker 序列 `frac(k·α + r·β)` 在 `[0,1)²` 上**等分布**——这正是"排内去单调（k 方向铺开）+ 排间去对齐（r 方向错开）"的数学保证。
- **无表**：闭式 O(1)，无内存、无随 n 变化的表。

对比：**随机**虽也能去单调，但 (a) 违反确定性、(b) 有团簇方差（可能把两层堆在一处、另一处空着，`uniqL` 不稳）；**哈希**（如 `hash(k,r)`）确定性满足，但分布质量取决于哈希函数、不保证等分布，且是"魔法黑盒"，改 n 时行为不可预测。R2 是**能满足全部三条要求的最小复杂度选择**。

### ② 为什么厚度对齐**最薄**的平面方向（`min(widCells, depCells)`），而不是最宽

若按**最宽**方向定 L，则 `line`（纵深仅 1~3 格）会得到巨大的 L —— 但 `line` 在平面上本就是一根细线，给它大厚度只会造出**竖直的针/墙**。这正是 `E.r2(L16)` 的失败模式（`line n=12`：`vert 105.6`、`thin 4.063`）。

按**最薄**方向定 L 给出一个几何不变量：

```
vert ≈ K × min(平面跨)         ⇒  thin = vert / min(平面跨) ≈ K
```

即**纵向不得厚过舰队自己的最薄水平截面**——否则它"站起来"了，读作塔/墙而不是队形。这是从"队形应该在三个投影下都是二维有面积的形体"（§1.1）直接推出的：只有 `vert ≲ min(平面跨)`，侧视/正视的截面宽度才与俯视同量级。

### ③ 为什么 `K = 1.0`

`K` 决定 `vert ≈ K × min(平面跨)`：

- `K > 1` ⇒ 纵向 **超过**最薄水平跨 ⇒ 向"针/塔"退化（正是要修的缺陷）；`K` 越大越严重。
- `K < 1` ⇒ 纵向 **不足** ⇒ `uniqL` 塌到 1~2 ⇒ 读不出用户明确要的"**多层、大量的战舰**"（`12` §0）。
- `K = 1.0` ⇒ 恰好落在"不扁也不瘦"的边界，即最薄方向的**等轴**（`thin ≈ 1`）。实测 `F` 的 `thin 中位 = 0.938`（`_v8c_final.log` 汇总），`uniqL 中位 = 7` —— **既保住了"多层"读数，又不再成针**。

选 1.0 也是"最少魔数"原则：它让 L 的公式退化为「纵向跨≈最薄水平跨」，一个系数都不用调。

### ④ 为什么用足迹推导，而不是恒定层数

恒定 `L = 16` 的问题是：它把**同一个绝对厚度（121.9）**强加给所有舰队，而**正确的厚度应随舰队平面大小变化**（见 ②③）。于是：

- 小舰队（平面 ~52）：121.9 纵向 ≫ 平面 ⇒ 针。
- 大舰队（平面 300~520）：121.9 才数量级相当 ⇒ 正常。

⇒ 恒定层数**在任何单一尺度上至多是对的**，跨尺度必错一端。而"厚度 ∝ 平面最薄跨"这条物理需求，**只能**由足迹推导满足。附带好处：

- 与既有单一真源一致：推导只读 `formationOffsets` 的格位（`widCells/depCells` 由格位算出），**不引入新表**；
- 保留"单一杠杆"语义：舰队大小 ← 直接决定厚度，改 n 自动跟随，无需人工调参。

## 5. 反例与已知代价（诚实记录）

### ① 大编队（n ≥ 40）层数被 16 封顶 ⇒ 厚度不再随 n 增长

`LAYER_CAP = 16` 与既有 `TEAM_LAYERS = 16`（`fleetTierLayout.ts:65`）一致。后果：`n ≥ 40` 的 `L` 触顶，`vert` 固定为 121.9（`spacingEff=26`），而平面继续增大：

| 舰队 | 平面（gx×gy） | 纵向 | 形体比（gx:gy:vert） | 读作 |
|---|:--:|:--:|:--:|---|
| `wedge n=120` | 260 × 520 | 121.9 | **2.13 : 4.26 : 1** | 「板」（宽扁） |
| `circle n=120` | 312 × 312 | 113.8 | 2.74 : 2.74 : 1 | 「板」 |
| `square n=120` | 260 × 260 | 121.9 | 2.13 : 2.13 : 1 | 「板」 |

（数据源：`_v8c_final.json` 各 `n=120` 条目。）

**我的判断：n ≥ 40 的「宽扁板」可以接受，且不应通过抬高上限修掉。** 理由：

- 大舰队在现实中/观感上本就该是**宽正面 + 浅梯次**的"墙"，而不是一个球；`12` §2 已记 `120 舰横向足迹 ≈ 286`，厚:宽 ≈ 1:2.3 是当时**刻意追求**的读数。
- 抬高 `LAYER_CAP` 的代价是**牵一发动全身**：`LAYER_GAP ≥ 1.2×maxShipH` 的几何下限不变 ⇒ 层距不变 ⇒ 厚度 ∝ L 线性上升。`L=24` 时厚度 187，`TEAM_GAP = max(65, 187+8.8) = 195.8`，纵向包络从 `121.9+2×130.7 = 383` 抬到 `187+2×195.8 = 578` —— **巡航高度**（`Battle3DOverlay.computeCruiseClearance()`）随之抬升，最下面那一档更容易沉进地形，且与 `12` 已锁定的"16 层"口径冲突。
- 因此**建议维持封顶 16**，并在 §3.6 明确"大舰队 = 宽扁板"是**设计意图**，不是遗留缺陷。

### ② `line n=6/8` 改造后仍是单列（`bandW = 0`）

`lineCells(6)`：`W = ceil(√(6×8)) = 7` ⇒ `R = ceil(6/7) = 1`，**只排出 1 排**；`lineCells(8)` 同理 `R = 1`。单排在俯视下就是一根沿 gy 的线（`wid = 0`）⇒ `bandW (top90) = 0` 无法避免，`A` 与 `F` 读数相同（§3.2）。

**这不是缺陷，是"横阵"的定义使然**——"宽正面"在小 n 时物理上就是一排。**必须写明的前提**：用户看到的那张"斜线"截图，**极可能就是这种小舰队**（小 n + 少排数），此时同时踩到两个现象：

- 排内单调（根因 1）⇒ 正视看到一条**斜**线（`A.baseline` 的 `mono = 1/1`）；
- 平面本身单排 ⇒ 俯视也是线（§1.2 判据的 `bandW=0`）。

R2 分层**能且仅能**修掉前者（`F` 的 `line n=6/8` 的 `mono = 0/1`），后者是阵型定义，**需要产品决策**（见 §9 第 3 条）。

### ③ 小舰队的"队间档距"随之变小（`teamGapFor` 的厚度项降下来了）

`teamGapFor(spacingEff, layerGap, maxShipH, layers)`（`fleetTierLayout.ts:110-115`）：

```
TEAM_GAP = max( 2.5×spacingEff ,  (layers−1)×layerGap + 1.5×maxShipH )
```

`layers` 从恒 16 变为足迹推导的 `L` 后，小舰队厚度项骤降。以 `spacingEff=26`、`layerGap=8.125`、`maxShipH=5.89` 计：

| 舰队 | 旧（L=16） | 新（足迹 L） | 主导项 |
|---|:--:|:--:|---|
| `line n=12`（L=4） | 121.9+8.8 = **130.7** | 24.4+8.8 = 33.2 ⇒ `max(65, 33.2)` = **65** | 新：比例项 2.5×26 = 65 胜出 |
| `wedge n=6`（L=7） | 130.7 | 48.8+8.8 = 57.6 ⇒ `max(65, 57.6)` = **65** | 同上 |

**影响**：当**一方**的各支舰队**都很小**时，该方的档距从 130.7 降到 65（≈ 一半）；"队间 3 档叠放"的纵向分离随之变小。**间隙校验仍成立**：`boardGap = TEAM_GAP − 厚度 − maxShipH = 65 − 24.4 − 5.89 = 34.7 > 0` ✓，不会互穿。

**我的判断**：可接受，甚至偏好——小舰队占用的空间本就更小，档距按舰队实际厚度收缩是**自洽**的；且调用方按"一方取各舰队最大值"（`teamGapFor` 注释）统一，只要该方**存在**一支大舰队，档距仍取 130.7，档位包络不受影响。需注意的实现细节：调用方必须把**新的 `L`**（而非 `TEAM_LAYERS`）传进 `teamGapFor`，否则档距与厚度不一致。

|---|---|---|
| **A（推荐）** | 接受：档距按各舰队实际厚度收缩，`boardGap = 34.7 > 0` 不互穿 | 当一方全是小舰队时，三档纵向分离减半（更紧凑） |
| B | `teamGapFor` 的厚度项仍按 `TEAM_LAYERS = 16` 固定（档距不随层数下降） | 保持旧档距；但"档距"与"实际厚度"脱钩，小舰队之间会**多出一段无意义的空隙** |

**推荐 A**：档距按实际队形收缩是自洽的；且"一方取各舰队最大值"的既有规则保证只要该方有大舰队，包络就不受影响。

### 拍板项 3 · `line` 小 n（6/8）俯视即单线，是否要改阵型定义

| 选项 | 内容 | 代价 |
|---|---|---|
| **A（推荐）** | 不改：横阵在小 n 时物理上就是一排（§5 代价②），R2 已修掉其"正视斜线"部分 | `bandW=0` 保留（P3 豁免 2 档） |
| B | 小 n 时强制 ≥ 2 排（俯视也有面积） | 改变"横阵"语义与足迹（纵深从 1 排变 2 排），影响缩放大/格距压缩，需重跑台架 |
| C | 小 n 时把 `line` 自动降级/映射为更合适的阵型（如 `wedge`） | 引入"阵型 ≠ 用户所选"的隐性行为，与"阵型由玩家数字键 1–5 指定"冲突 |

**推荐 A**：小 n 的横阵本就是一根细线，这是定义；且用户的"斜线"投诉的主因（排内单调）已由定案 F 消除。若用户在真机复核后仍希望小 n 横阵"有面"，再走 B。
