## 0. 结论摘要

**一句话**：用户要的不是"再加六个功能"，而是**三个缺失的抽象**——而其中**一个（分舰队）是另外五个玩法的共同前提**。

| 缺失的抽象 | 现状 | 不补它的后果 |
|------|------|------|
| **A. 教范（Doctrine）** | 有表（`MILITARY_STYLE_PARAMS`）但**只接了 1/3 个字段** | 提督特性不生效（毕典菲尔特出场不是楔形） |
| **B. 计划（Plan）** | 有 `planFactionBattle`，但**按兵力分配角色、不看个性、不设阵型、只算一次** | 每支舰队"没有意图"，开局即定死 |
| **C. 分舰队（TaskForce）** | **完全不存在** | **迂回 / 包抄 / 诱饵 / 后勤战 / 分舰队 全部无法表达** ← 核心 |

**三条硬证据（全部代码级）**：

| # | 事实 | 锚点 |
|:--:|------|------|
| **1** | **`planFactionBattle` 按兵力排序分配角色**：`scored.sort(power 降序)` → `idx===0` 得 `assault`、奇数得 `support`、末位且保守得 `hold`。**个性只在"末位且 cautious"一个分支里出现** | 锚 `planFactionBattle`（`BattleScene.ts:985-1041`），`sort((a,b)=>b.power-a.power)` |
| **2** | **该函数据旧口径算 personality**：`agg>caut+20`，**只读 `admiralStats`、不读 tags** —— 与我在 v29 接入的"标签优先"（另一处 `:631`）**不是同一处** | 锚 `const personality = agg > caut + 20 ? ...`（`:997`） |
| **3** | **计划不设阵型**：`planFactionBattle` 全文**无 `formation` 赋值**；而 `MILITARY_STYLE_PARAMS.formation`（8 风格各自的阵型偏好）**在战术层仍零引用** | 锚 `planFactionBattle` 无 formation ✕ vs `tagConfig.ts:87-100` |

⇒ **毕典菲尔特（`frontal_assault` → 楔形 / 进攻 1.3 / 动摇线 20%）出场是"长条"，是必然的**：
他的人格**从未参与阵型决策**。

**推荐路线**：**外挂式分层重构**（不重写 `BattleScene`）：新建 3 个纯计算模块（教范 / 计划 / 编队），
`BattleScene` 降级为**执行器**。理由见 §6（今晚刚发生过一次"在 6025 行文件里改动导致回归"的事故）。

**落地顺序**：**A → B → C**（先让特性生效 → 再给意图 → 再给编队）。
其中 **A 是唯一能立刻兑现用户抱怨的一步**，建议先做。

## 1. 诊断：一次战斗的"意图"是怎么产生的（现状）

```
开战
 └─ planFactionBattle(aiFac)  ← 每秒 AI Tick 里调用？否：建场时调一次（锚 :975）
      · 按 calculateFleetPower 降序排队
      · 头号 → attack_fleet（打"敌方第一支可见舰队"）
      · 奇数位 → support_fleet（协同头号）
      · 末位且 cautious/easy → hold_point
      · 其余 → capture_planet（最近中立星球）
      · 断粮(<25) → retreat_supply
      · 写 fl.mission + fl._planRole
      ↓
 每帧：globalFleets.forEach(fleet => ...)  ← 反应式状态机（:3556 起）
      · 状态：retreating / engaging / flaring / exploring / assembling
      · 目标：closestEnemyFleet（最近敌人）/ 任务牵引 _missionDest / 信标
      · 阵型：战略层 1Hz 按 forceRatio 覆盖；战术层接敌时再覆盖
      · 目标选择：打分 = 补刀残血 + 距离 + 威胁
```

**读出的三个结构性问题**：

| # | 问题 | 表现 |
|:--:|------|------|
| **P1** | **计划与人格无关** | 谁当突击队由**兵力**决定，不由"谁更擅长突击"决定 |
| **P2** | **计划只有"角色"没有"战法"** | `role ∈ {assault, support, hold, capture, resupply}` —— 全是**任务类型**，没有一个描述"**怎么打**"（迂回？钳形？诱饵？） |
| **P3** | **舰队是原子的，不可再分** | `globalFleets` 里一支舰队 = 一个不可分的整体 ⇒ **所有需要"多队协同"的战法全部无法表达** |

> **P3 是根本**：`fleetSplitManeuver.ts`（完整的三幕包抄几何）之所以"不接任何玩法触发"（模块自述），
> 正是因为**没有"分舰队"这个容器**——几何算出来了，但没有"谁去执行左翼"的对象。

## 2. 第一性原理：缺的不是"更多 if"，是三个抽象

### 2.1 用户真正要的是什么

把用户的六个词拆开：

| 用户的话 | 拆解为"对系统能力的诉求" |
|----------|--------------------------|
| "特性没用上" | 人格 → 行为的**映射** |
| "给每个提督的任务" | 意图（objective）的**表达** |
| "分舰队" | 力量的**可分解性** |
| "迂回 / 包抄" | 多路协同的**空间战法** |
| "诱饵舰队" | 多路协同的**牺牲/欺骗战法** |
| "后勤战" | 多路协同的**非对称目标战法** |
| "变化 / 可玩性" | 上述能力的**组合空间** |

**⇒ 后四项（迂回/包抄/诱饵/后勤战）全部是"多路协同"** —— 而**多路协同的前提是"力量可分解"**。

> **第一性原理结论**：
> **多样性 ≠ 功能数量；多样性 = 抽象的组合空间。**
> 现在有 5 种角色 × 4 种状态 × 5 种阵型，看似很多，但**都作用在同一个原子（不可分的舰队）上**，
> 所以组合出来的东西全是"一支舰队换个方式冲"。
> **补上"分舰队"这一个抽象，"迁回/包抄/诱饵/后勤战"就从"四个功能"变成"计划的四种取值"。**

### 2.2 目标抽象：Doctrine → Plan → TaskForce → Execution

| 层 | 抽象 | 回答什么问题 | 生命周期 |
|:--:|------|-------------|:----:|
| **L0** | **人格**（tags + stats） | 这个提督**是谁** | 静态 |
| **L1** | **教范 Doctrine** | 他**偏好怎么打**（阵型 / 进攻性 / 动摇线 / 偏好战法） | 静态（每战算一次） |
| **L2** | **计划 Plan** | 这一战**要达成什么、分几路、各走什么战法** | 低频重规划（如 10s） |
| **L3** | **分舰队 TaskForce** | **哪几艘舰**去执行哪一路 | 事件驱动（分裂/合并） |
| **L4** | **执行** | 每帧怎么走、怎么打 | 每帧（既有代码） |

**关键**：L4（既有 `BattleScene` 每帧逻辑）**大量复用、不推倒** —— 它做"执行器"已经够好
（阵位、开火、补给、拖刀、包夹距离都已多轮调参）。**重构发生在 L1–L3，不在 L4。**

## 4. 六项玩法 → 架构映射（**不是六个功能，是三种取值**）

| 用户要的 | 在当前架构下怎么表达 | 依赖层 |
|----------|---------------------|:----:|
| **提督特性** | `Doctrine` 全字段接入；**AI 战略层与 `planFactionBattle` 统一读 tags** | L1 |
| **每个提督的任务** | `Plan.objective`，且**角色分配改为"按教范适配度"而非按兵力** | L1→L2 |
| **分舰队** | `Plan.detachments[]` + `TaskForce.split()` | L2→L3 |
| **迂回 / 包抄** | `maneuver: 'flank' \| 'pincer'` ⇒ 2 个 detachment，左/右翼 + `splitOffsetsFor()` 几何 | L2+L3 |
| **诱饵舰队** | `maneuver: 'decoy'` ⇒ 1 个高机动作诱饵（撤退倾向高）+ 主力侧击 | L2+L3 |
| **后勤战** | `maneuver: 'raid'` ⇒ 1 个 detachment 猎杀敌方运输舰（**补给链基础设施已完整**） | L2+L3 |
| **战术变化** | 由 `教范 × 战法 × 编队配比 × 目标` 的**组合**自然产生（数据驱动） | 全部 |

> **关键**：`pincer`/`decoy`/`raid` 三者**共用同一套"分裂-协同"机制**，
> 差别只在 `detachments` 的角色、配比与航路。**这就是"从底层实现多样性"的含义。**

## 6. 反方审查（为什么不"推倒重写"）

| 反方主张 | 我的裁定 |
|----------|----------|
| **"大构建"就该重写 `BattleScene`（6025 行）** | **反对**。`BattleScene` 的 L4 逻辑（阵位、开火、距离保持、拖刀、补给、护盾）是**六轮真机修复的产物**（文件内满是 `v6.8` / `R10-A1` / `v21 JIT` 的修复注释），重写等于把这些教训清零。**重构的正确位置是 L1–L3（新增），不是 L4（已有）。** |
| **直接接 `fleetSplitManeuver.ts` 做包抄** | **反对其顺序**。该模块只输出"整队偏移"，**没有"谁去左翼"的概念**；先有 `TaskForce` 才能正确驱动它。 |
| **一次性做完 A–E** | **反对**。今晚刚发生过一次回归（v29 角速度控制器 ⇒ 用户实报"波浪舞"，见 `23` §3.5）。**无自动化测试的单文件项目，必须小步 + 每步有可复跑判据。** |
| **用行为树 / ECS 全面替换** | **反对（现阶段）**。收益是"架构美观"，代价是**全部既有修复失效**；而用户要的是**玩得到的变化**，不是架构纯洁性。**若未来 L1–L3 稳定，再评估是否下沉到 L4。** |

**20% 复杂度换 80% 效果的落点**：**阶段 A + C** ——
"提督特性生效"（A）解决用户第一句抱怨；"能包抄"（C）解决"分舰队/迂回/包抄"三个词。
**B / D / E 是放大器，不是前提。**

## 8. 落地现状（v31-A/C-抽象 · 2026-09-19）

### 8.1 ✅ 已实施：阶段 A（教范全量接入）

### 8.2 ✅ 已实施：阶段 C 的**核心抽象**（尚未集成到 L4）

`frontend/src/game/taskForce.ts`（**纯计算，196 行**）：

- **`MANEUVERS`**：7 种战法 —— `frontal` 正面突击 / `flank` 一翼迂回 / `pincer` 两翼包抄 /
  `decoy` 诱饵诱敌 / `raid` 后勤猎杀 / `screen` 补给护航 / `hold` 固守要点。
  每种 = **分舰队的取值组合**（`role` / `share` / `lateral` / `intent` / `targetKind`）。
- **`selectManeuver()`**：教范偏好 → 态势可行性 → **降级链**（`pincer→flank→frontal`）。
- **`assignDetachments()`**：把 N 支舰队编成到各路（确定性、兵力不丢失、`main` 拿最强）。

**验证**（`_v31_taskforce_sim.cjs` · 5 条判据全 PASS）：

| 提督 | 选出战法 |
|------|:--:|
| 毕典菲尔特 | **正面突击** `frontal` |
| 米达麦亚 / 杨威利 | **两翼包抄** `pincer` |
| 梅克林格 | **后勤猎杀** `raid`（有敌方补给时） |
| 某谨慎提督 | **固守要点** `hold` |
| 无标签 · 劣势 | 固守要点 |

⇒ **用户要的"迂回 / 包抄 / 诱饵 / 后勤战"，现在是同一套抽象下的四种取值**（而非四个功能）。

### 8.4 ⚠ 风险登记

**`advMult` 动态范围被放大**：`1/attackMod` ∈ [0.71, 1.43]，叠加原 `personalityType` 的 0.8/1.2
⇒ `advMult ∈ [0.57, 1.71]`（原先 [0.8, 1.2]）。
后果：激进提督 **2.0×0.57 = 1.14** 倍优势就转攻坚（原先 1.6）；谨慎提督需 **3.4** 倍（原先 2.4）。
⇒ **行为分化显著**（正是"特性明显"的目的），但**战斗平衡会漂移，需回归**。

## 9. 阶段 C 集成落地（v31-C · 2026-09-19）

### 9.1 已实施

| 文件 | 新增 / 改动 |
|------|------|
| `frontend/src/game/taskForce.ts` | **新增 `splitUnitCounts()`** —— 确定性实体切分（按 `share` 取整 + 余数补齐 + 每路保底 1） |
| `frontend/src/game/scenes/BattleScene.ts` | **新增 `splitFleet()` / `applyManeuver()` / `splitSelectedFleet()`**；键盘 `X` 入口；**战法侧翼取代随机选边**；`DETACH_SPACING = 200` |

**三件事**：

1. **`splitFleet(parent, specs)`** —— 把一支舰队按战法规格拆成多个**独立 `fleet` 对象**（共享同一提督）。
   - 第 0 路（`main`）**留在母队** ⇒ 旗舰与指挥链不动；
   - 其余各路新建子编队（新 `id` / 新 `displayId` / 继承 `commanderId`）；
   - **运输舰不参与拆分**（留在母队，走既有补给链）；
   - 子编队 `formationSlot` **必须重编号**（否则阵位枚举错位 ⇒ 单位瞬移）；
   - 初始位置 = 母队位置 + `lateral × DETACH_SPACING(200px)`。
2. **`applyManeuver(fac, myFleets, enemyFleets)`**（**AI 自动分割**）—— 舰队数 ≥ 战法路数 ⇒ **直接分工**（不拆分，最省）；
   不足 ⇒ **拆最强的一支**补足路数。接在 `planFactionBattle` 末尾（唯一调用点 = 部署结束时，不会重复触发）。
3. **`splitSelectedFleet()`**（**玩家主动拆分**，用户裁定项）—— **战场点选己方舰队 → 按 `X`**。
   战法与 AI **同源规则**（教范 + 真实兵力态势 → `selectManeuver`），保证玩家与友军 AI 用同一套战法体系。

**附带修复**：战法侧翼**取代 `Math.random()` 选边** —— 「两翼包抄」因此才是真的**左右夹击**，
而不是两队各自随机绕圈；同时修掉 `v17_01` 登记的 **P8「包抄左右随机、看不出意图」**。

### 9.5 可用性补丁（用户反馈"找不到入口"）

**用户原话（逐字）**：
> 「我该怎么拆舰队呢？**没看到操作界面，没有什么提示**，左键点击我自己的舰队，右键就是指挥前进，其他就没有了」

**我的疏漏**：只加了键盘 `X`，但
1. `applyFleetSelectByPick` 的选中 toast **只提示「右键点地即可令其前往」**，完全没提拆分；
2. 没有任何**持久可见**的入口 —— 快捷键对未被文档告知的玩家等于不存在。

**修复（三处）**：

| 处 | 改动 |
|----|------|
| **3D 舰队浮标** | **新增「分兵」按钮**，与既有 3 个姿态按钮（索敌/攻坚/驻守）同一排 —— 点击**直接对本浮标舰队生效**，无需先选中 |
| **选中提示** | toast 改为「已选中：XX — 右键点地令其前往 · **浮标「分兵」或按 X 拆分**」 |
| **浮标意图文本** | `fleetIntentText` **优先显示分舰队意图**（如「左翼包夹」/「猎杀运输舰」/「示弱诱敌」）—— 这是玩家读懂"哪个分队干什么"的**唯一可视通道**。⚠ 仅己方显示（敌方仍按 F-2 脱敏，只留 `role` 粗意图） |

**新增公开入口** `splitFleetById(fleetId)` —— **浮标按钮 / 快捷键 `X` / 未来 UI 共用同一入口**（避免多套路径分叉）。

> **教训（写进记忆）**：**"功能能跑通" ≠ "玩家找得到"。**
> 加机制时必须**同时**给出**可见入口 + 文案提示**。
> 本项目里 `applyFleetSelectByPick` 的 toast 就是"选中后能做什么"的**唯一说明位** ——
> 新增能力应**同步更新该文案**，否则功能等于不存在。
