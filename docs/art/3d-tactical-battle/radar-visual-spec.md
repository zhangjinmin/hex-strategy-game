# 战术雷达视觉规格

> 配合 UX 侧 `docs/design/3d-tactical-battle/08-tactical-radar-spec.md`（结构/内容/交互归 UX，颜色与风格归本侧）
>
> 雷达是 DOM 层 Vue 组件，**不受 Three.js 后处理影响**。因此本文色值用 CSS `rgba()` 表示，而非 Three.js 材质参数。

## 1. 整体视觉风格

### 1.1 定位：战略层「四角全息悬浮板」的延续

雷达不应看起来像一个"小地图插件"，而应是**战略星图 `ThreeStrategicMap.ts` 四角全息竖牌在战术层的缩小版**。三者共用同一套视觉语汇：暗底 + 全息绿强调 + 四角 L 形角标 + 半透明。

### 1.2 具体色值与样式

| 项 | 规格 | 说明 |
|----|------|------|
| **背景** | `rgba(2, 4, 10, 0.85)` | 与 3D 场景背景 `0x02040a` 同色，85% 不透明（UX 侧已定） |
| **外边框** | `1px solid rgba(0, 204, 102, 0.35)` | `CRT_ACCENT` 绿 35% |
| **四角 L 形角标** | `2px`，`rgba(0, 204, 102, 0.75)`，臂长 14px，内缩 6px | **与 3D 主视图 HUD 的四角 L 形定位记号完全同款**（`CrtRenderer.drawCRTOverlays`），是"同一套系统"的关键视觉证据 |
| **外辉光** | `box-shadow: 0 0 12px rgba(0, 204, 102, 0.15)` | 弱，避免角落一团光 |
| **内辉光** | `inset 0 0 24px rgba(0, 204, 102, 0.06)` | 模拟全息板边缘的内透光 |
| **标题条** | 「战术雷达」9px `monospace`，`rgba(0, 204, 102, 0.7)` | 与 2D 的 `▣ TAC-PROJECTION` 标签同字体族 |
| **扫描线** | **加，但极弱**：CSS `repeating-linear-gradient`，周期 3px，`rgba(0, 0, 0, 0.10)` | 见 §1.3 |
| 折叠态 | 保留外框、角标与标题条，内容区隐藏 | |

### 1.3 扫描线的实现与豁免（重要）

**雷达扫描线必须用 CSS 实现，不能走 Three.js 后处理**——雷达是 DOM 层，WebGL 的 `crtPass` 影响不到它。用 `repeating-linear-gradient` 叠一层即可。

**雷达扫描线不跟随「CRT 强度」滑杆。** 雷达是 R-02 / R-06 / R-11 三条 S/A 级风险的**可读性承载面**，不是风格展示面。让它的清晰度随 CRT 滑杆劣化，等于把风险缓解措施本身削弱掉。

豁免规则（与接地投影同豁免类）：

| 场景 | 雷达扫描线 |
|------|-----------|
| 常规 / CRT 滑杆任意值 | 固定 `rgba(0,0,0,0.10)`，不变 |
| 色盲模式 | 不变 |
| **「全部归零」预设** | **关闭**（归零应得到完全干净的画面） |
| 悬停态（背景提到 0.95） | 保留 |

## 3. 阵型字形图标（R-11 的核心）

### 3.1 ⚠️ 先修正一处符号冲突（必须改）

UX 侧 `08` §3.1 的阵型字形为：`雁行 V / 单纵 │ / 纺锤 ◆ / 圆阵 ○ / 方阵 ▦`。

**其中「纺锤 `◆`」与「帝国阵营标记 `◆`」撞车——同一个符号在雷达上表达两种含义**（一个是阵型、一个是阵营）。这恰恰是 UX 侧自己提的约束（"字形必须与 L3 编队标记的 ▲/◆ 在视觉上可区分"）所不允许的情况：即便用线框/实心区分，**让 `◆` 同时表示"帝国"和"纺锤阵"是语义冲突**，玩家在密集雷达上极易误读。

**修正建议：纺锤阵改用「横向柳叶形」轮廓。**

```
纺锤（spindle）本义即为两端尖、中间鼓的纺锤状，柳叶形才是准确表达；
菱形（◆）是四条直边 + 四个尖角，语义与外形都不匹配"纺锤"。

画法：两条对称圆弧构成的长轴水平尖椭圆轮廓（stroke，不填充）
      长轴 12px × 短轴 5px，线宽 1.2px
```

这样五形各有独立轮廓，且与 ▲/◆ 零碰撞：

| 阵型 | 字形 | 轮廓特征 |
|------|------|----------|
| 雁行 `wedge` | `V` | 开口折线，无闭合 |
| 单纵 `line` | `│` | 单竖线 |
| **纺锤 `spindle`** | **横向柳叶形**（两弧闭合） | **唯一带曲线的字形** |
| 圆阵 `circle` | `○` | 圆 |
| 方阵 `square` | `▦` → 简化为 `□` | 直边闭合四边形 |

**方阵也建议简化**：`▦`（U+25A6）在 12px 下内部网格线会糊掉，且字形覆盖不稳（见 §3.3）。改为**空心正方形 `□`** 更清晰；与「帝国 ◆ 实心菱形」的区别是**旋转 45° + 空心 vs 实心 + 中性色 vs 阵营色**，四重区分足够。

### 3.2 颜色与描边风格（本侧定）

| 项 | 规格 | 理由 |
|----|------|------|
| **颜色** | **中性冷白 `0xe5e7eb`**，不透明度 0.90 | **关键决策**：阵型与阵营无关（双方都用 5 种阵型），因此字形**绝不能用阵营色**，否则会与阵营编码打架。中性白读作"HUD 信息"，与青绿/紫色系天然分离 |
| 激活/己方阵型 | `0x00cc66`（CRT 强调绿） | 己方当前阵型用强调色，便于"我是什么 vs 对面是什么"的对照 |
| 填充 | **永不填充**，仅描边 | 与实心阵营标记形成 fill/stroke 对立（UX 侧已定的区分手段） |
| 线宽 | 1.2 px（UI 缩放 1.25x/1.5x 时同步到 1.5/1.8） | |
| 尺寸 | 12 × 12 px | |
| 位置 | 阵营标记右侧，**中心间距 14px（净间隙 3px）** | 固定间隙，防止两符号贴连被误读为一个图形 |
| 色盲模式 | **不变**（中性白无阵营语义，三种色盲模式通用） | 少一套需维护的变体 |

### 3.3 ⚠️ 实现要求：用矢量路径，不要用 Unicode 文本字形

`◆`(U+25C6)、`▦`(U+25A6)、`○`(U+25CB) 等符号**字形覆盖不稳定**，缺字时会渲染成豆腐块 `□`，而 `□` 又与方阵字形同义——会直接导致误读。

**要求：五个阵型字形全部用 canvas path / SVG path 绘制，不使用文本字符。** 这也便于 §3.1 的柳叶形（无对应 Unicode）与统一线宽控制。

### 3.4 灰度可辨性验证（UX 侧硬要求）

| 字�� | 灰度下的判别特征 |
|------|------------------|
| `V` | 唯一不闭合的开口形 |
| `│` | 唯一单线形 |
| 柳叶形 | 唯一带曲线形 |
| `○` | 唯一圆形 |
| `□` | 唯一有直角的闭合四边形 |

五形在灰度下**轮廓类别互不相同**，满足要求。加上"实心=阵营 / 空心=阵型"的 fill 对立，双重保险。

### 4.1 屏幕外事件闪烁（解 R-06）

| 事件 | 色值 | 位置 |
|------|------|------|
| 受击 | `0xef4444` | **雷达内边框上的弧形段**（按方位角定位），持续 800ms |
| 损失 | `0xffffff` | 同上 |
| 旗舰事件 | `0xfbbf24` | 同上 |

**位置约束（重要）**：事件闪烁必须画在**雷达内边框的弧段**上，**不画在舰队标记上**。

理由：蓝黄色盲模式下帝国阵营色也是 `0xef4444`（红），若受击闪烁也用红色且叠在标记上，两者会混淆。限定在内边框弧段后，与雷达中部的舰队标记**空间分离**，冲突自然消解。

## 5. 编号徽章 renderOrder：31/32 确认可用

UX 侧 `07-target-selection-spec.md` §3.1 定编号徽章为 `renderOrder = 32`（必须在 L3 编队标记 31 之上）。**确认可用，31 之上本侧未占用。**

为避免后续继续往上叠导致混乱，本侧**预留一段徽章/覆盖层专用区间**：

| renderOrder | 用途 | 归属 |
|:-----------:|------|------|
| 30 | HUD 基础层（四角角标、刻度） | 美术 |
| **31** | **L3 编队聚合标记 ▲/◆** | 美术 |
| **32** | **命令候选编号徽章** | UX |

## 6. 目标选择脉动的实现路径（回答 UX 侧 §3.1）

### 6.1 直接回答：能调制，但**不建议**改线框层亮度

先回答技术可行性：可以。`MeshBasicMaterial.color` 可以在运行时逐帧改，且**不破坏材质复用**——只需为"选中态"额外缓存一套材质（按 `(faction, lod)` 分支，共 2×3 = 6 个），内存可忽略。

**但代价是破坏 instancing**：常规舰的线框层走 `InstancedMesh` 批处理，一艘被选中的舰若要单独改颜色，就必须**从批次中移出、改为独立 Mesh 渲染**（把实例缩放为 0 隐藏 + 另画一个独立副本）。实例↔独立切换是易错逻辑，且每次选中/取消都要动 instance buffer。

### 6.2 推荐方案：独立脉动轮廓壳（UX 侧给的替代方案，本侧采纳）

**不改基础线框层，而是叠加一层独立的、加法混合的脉动外壳。**

```ts
// 选中态：在舰船外包一层简化线框壳
const pulseShell = new THREE.Mesh(
  lod1WireGeometry,                       // 复用 LOD1 简化几何，~150 tris
  new THREE.MeshBasicMaterial({
    color: factionColor,                  // 阵营色满亮度
    wireframe: true,
    transparent: true,
    opacity: 0.0,                         // 逐帧调制 0.0 ↔ 0.85
    blending: THREE.AdditiveBlending,     // 加法混合 → 顺序无关
    depthWrite: false,
    depthTest: false,                     // 覆盖层，恒可见（被遮挡也能看到选中目标）
    renderOrder: 29,                      // 略低于 L3 标记 31
  })
);
pulseShell.scale.setScalar(1.06);         // 比本体大 6%，形成"轮廓壳"
```

脉动参数（沿用 UX 侧）：`0.83 Hz`（周期 1.2s），`Sine.easeInOut`。

**为什么这个方案更优**（四条）：

| # | 理由 |
|---|------|
| 1 | **不碰 InstancedMesh 批次**。选中/取消只在场景里增删一个壳对象，instance buffer 完全不动，没有实例↔独立切换的易错逻辑 |
| 2 | **加法混合顺序无关**（加法交换律）。本项目已有一堆半透明排序问题（`materials-and-lighting.md` §7.1），加法层天然免疫，不再增加排序负担 |
| 3 | **视觉更强**。"发光轮廓壳"是标准的选中反馈，比"基础线框忽明忽暗"更醒目，且不会让舰体在脉动低点显得"消失" |
| 4 | **成本极低**。选中数量天然有界（典型 1，编队选择最多 8），最坏 +8 draw call / +1,200 tris，相对 ≤180 draw call 与 36,000 tris 上限可忽略 |

### 6.3 与 Bloom 的交互（需要留意）

阵营色满亮度约 **0.69**，`> ` Bloom 阈值 **0.62**，因此脉动壳在峰值**会触发 Bloom**——舰体随呼吸节奏发光。

本侧判断这是**正面效果**（选中目标周期性发亮，是常见且有效的反馈），且选中数量有界，不会像全舰队那样把画面糊掉。但设一条保护：

- 默认峰值 opacity **0.85**（不取 1.0），把 Bloom 强度压在可控范围；
- 若后续在 8v8 混战中实测 R-03（半透明叠加糊成一片）恶化，**峰值降到 0.72**（合成亮度 0.50，低于阈值，不再 Bloom）。

### 6.4 与可访问性的交互

| 项 | 结论 |
|----|------|
| 光敏安全 | `0.83 Hz` **远低于 WCAG 2.3.1 的 3 Hz 闪烁阈值**，无光敏性癫痫风险 ✓ |
| Comprehensive 档 | **必须可关闭脉动**。加一条「目标高亮脉动」开关（`accessibility.md` §2.2），关闭后改为**静态轮廓壳**（opacity 恒 0.6，不呼吸） |
| 「全部归零」预设 | 脉动壳随之关闭 |
