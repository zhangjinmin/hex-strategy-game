# 3D 战术战斗层性能预算

> 修订版 R1 — 已重算：底面免建模（相机禁仰视）+ 旗舰独立复杂体 + CRT 强度滑杆
>
> 尾焰实现方式（cone shader / 粒子系统）**尚未拍板**，本文两套方案的成本均列出，待工程侧架构与性能预算出来后对账再定。

## 1. 运行环境

- **壳层**：Wails（Go）桌面应用，Windows 下使用 Edge WebView2。
- **渲染**：Three.js 0.160 + WebGL 2.0。
- **目标设备**：中低端集成显卡也能 1080p@60fps；高端显卡有余量。
- **目标帧率**：60 fps，允许复杂战斗场景降至 45 fps 时触发 LOD 自动降级。

### 3.3 省出的预算去了哪里（用户要求量化分配）

**纯底面免建模节省**：

| 来源 | 节省 |
|------|------|
| 常规舰（24 艘 × ~55 tris/艘） | 1,313 |
| 旗舰（若按常规战列 hull 计，8 × 90） | 720 |
| 棋盘棱柱（500 × 6 tris 底盖） | 3,000 |
| 地形符号 | 300 |
| **节省合计** | **5,333 tris** |

**重新分配**：

| 投向 | 分配 | 占比 | 理由 |
|------|------|------|------|
| **旗舰复杂度** | **4,020 tris** | **75.4%** | 旗舰是玩家视线焦点与情感锚点，辨识度收益最高；且数量少（8/32），成本集中可控，不会随舰队规模线性膨胀。名舰旗舰 1,100 tris 的单体预算让 Brunhild 的镰形舰首/金棱线、Hyperion 的宽舷台/双天线都有实现空间 |
| **特效余量** | **800 tris** | **15.0%** | 护盾/激光/尾焰的并发峰值难以预测（集中交火时可能瞬间翻倍）。800 tris ≈ **+12 个并发护盾弧线**（64 tris/个）或 **+12 个尾焰 cone**，足以吸收一轮齐射的峰值 |
| **同屏舰船数量** | **513 tris** | **9.6%** | 5v5+ 场景舰数浮动大。按常规舰均值 252 tris/艘计 ≈ **+2 艘**余量，避免边缘场景直接触发 LOD 降级 |
| **合计** | **5,333 tris** | **100%** | — |

**为什么不把省下的预算全给同屏舰船数量**：舰船数量是线性成本（+1 艘 = +1 套实体/线框/发光层 + 尾焰），而旗舰复杂度是一次性成本（8 艘封顶）。在单机策略游戏里，32 艘同屏已经覆盖绝大多数战斗，边际收益低；而旗舰辨识度直接影响玩家的代入感与操作判断。

### 3.4 修订后的 tris 上限

| 项 | R0 | **R1** | 变化 |
|----|-----|--------|------|
| 实际峰值（32 舰，极端） | ~21,400（低估，未含旗舰与棋盘底盖修正） | **~30,000** | 更真实 |
| **硬上限** | **50,000** | **36,000** | **−28%** |

**新上限 ≤ 36,000 tris**（对实际峰值 ~30,000 留 20% 余量）。R0 的 50,000 是基于低估的峰值设的，实际余量过大、失去约束意义；36,000 是 tighter 且仍安全的数字。

## 4. Draw Call 预算

### 4.1 大规模场景（32 舰）逐项核算

| 来源 | Draw Calls | 说明 |
|------|-----------|------|
| 常规舰实体层（InstancedMesh：6 舰种 × 2 阵营 × 2 LOD） | ≤ 24 | `depthWrite=false`，排序错误在 opacity 0.22 下不可见 |
| 常规舰线框层（InstancedMesh） | ≤ 24 | 同上 |
| 常规舰发光部件（InstancedMesh） | ≤ 24 | Additive 混合**免疫排序问题**（加法交换律），可安全 instancing |
| **旗舰（独立 Mesh，8 × 3 层）** | 24 | 不 instancing，保证精确排序（见 `materials-and-lighting.md` §7.1） |
| 棋盘（填充 + 边线，合并） | 2 | |
| 地形符号（合并） | 1 | |
| 护盾涟漪（对象池，≤16 并发） | 16 | |
| 激光束（对象池，≤8 并发） | 8 | |
| 尾焰 cone（对象池，按舰种合并） | ≤ 16 | cone 方案；粒子方案见 §5 |
| 命中光晕 | 4 | |
| **接地投影**（R1 新增，instanced） | **2** | 轮廓 + 填充各 1；32 舰共用 InstancedMesh |
| **垂线**（R1 新增，合并为单个 LineSegments） | **1** | 舰体→投影的深度线索，见 `materials-and-lighting.md` §8.5 |
| **L3 编队聚合标记**（R1 新增） | **≤ 8** | 每舰队 1 个，`depthTest:false` 不能与舰体合批 |
| HUD | 1 | |
| 后处理（Render + Bloom + CRT） | 3 | 若采用选择性 Bloom 则为 5 |
| **合计** | **≈ 161** | R0 核算为 ~147 |

### 4.2 修订后的 draw call 上限

| 场景 | R0 目标 | **R1 修订** | 变化说明 |
|------|---------|-------------|----------|
| 小规模（≤4 舰） | < 80 | **< 100** | +10 半透明实体层；+11 投影/垂线/标记 |
| 中等（≤16 舰） | < 150 | **< 150** | instancing 收益抵消新增层 |
| **大规模（>16 舰，32 艘）** | < 200 | **< 180** | 实测核算 ~161，仍在原上限内 |

**硬上限维持 ≤ 180 draw calls**。虽然 R1 新增了接地投影（+2）、垂线（+1）、编队标记（≤8）、半透明实体层，但 instancing 与底面免建模（消除腹部 greeble sub-mesh）抵消了大部分增量，**核算值从 ~147 升到 ~161，仍在上限内，无需上调**。

### 4.3 三角面增量（R1 新增元素）

| 元素 | 单体 | 数量 | 小计 |
|------|------|------|------|
| 接地投影圆盘（16 边扇形） | 16 tris | 32 | 512 |
| 垂线 | 2 verts（非三角面） | 32 | 0 |
| L3 编队标记（billboard quad） | 2 tris | 8 | 16 |
| **新增合计** | - | - | **≈ 528 tris** |

相对 36,000 tris 硬上限，增量 1.5%，**不需要调整 tris 预算**。

### 4.4 目标选择脉动轮廓壳（R1-D 新增）

选中态采用独立加法脉动壳（`radar-visual-spec.md` §6），复用 LOD1 简化线框几何：

| 项 | 最坏值 | 说明 |
|----|--------|------|
| 选中数量 | 8（编队全选） | 典型为 1 |
| 三角面 | 8 × 150 = **1,200 tris** | 复用 LOD1 简化几何 |
| Draw call | **+8** | 每壳 1 个（不可 instancing，需独立 opacity 调制） |

合计最坏 +1,200 tris / +8 draw call → 峰值 ~31,700 tris / ~169 draw call，**仍在 36,000 与 180 上限内**（余量分别 12% 与 6%）。

> 余量已收窄到 6%，若后续还要加覆盖层元素，优先从「降低尾焰精度」或「合并发光部件」里腾，不要继续上叠。

## 5. 粒子预算（含尾焰方案对比 — 待拍板）

### 5.1 两方案成本/效果对比

| 维度 | **方案 A：程序化 cone + Shader** | **方案 B：粒子系统** |
|------|----------------------------------|----------------------|
| 粒子数 | **~800**（仅爆炸/损毁） | **~2,720**（32 舰 × 1.5 发射器 × 30 + 爆炸 800） |
| 三角面 | **+3,072**（48 cones × 64 tris） | **+5,440**（2,720 quads × 2 tris） |
| Draw call | **+16**（按舰种合并/instanced） | **+1**（单个 Points / instanced quads） |
| **Overdraw 影响** | **低**：实心锥体，层数可预测（1 层） | **高**：粒子互相重叠，局部可达 6-10 层 |
| 与 §7.2「4 层半透明上限」的冲突 | 无冲突 | **有冲突风险**，需放宽到 5 层或降低实体层 opacity |
| 视觉自然度 | 中：形状规整，湍流靠 shader 顶点扰动模拟 | **高**：天然拖尾、消散、随机感 |
| GC / CPU 压力 | 低（对象池，无每帧分配） | 中（粒子池需谨慎管理，易产生 GC spike） |
| 实现复杂度 | 中（需写 GLSL 顶点扰动 + 纵向渐变） | 低-中（现成 `Points` / `InstancedMesh` 方案多） |
| 与 CRT 后处理叠加 | 好（锥体轮廓清晰，扫描线打上去有质感） | 一般（粒子细碎，扫描线/噪点下易显脏） |

### 5.2 权衡结论（供对账用）

- **方案 A 的优势在 overdraw**，而这正是半透明 + Bloom 方案的命门。若采用 A，overdraw 层数可控在 4 层内。
- **方案 B 的优势在 draw call 与视觉自然度**（+1 vs +16），但会把 overdraw 推高，可能反过来吃掉省下的性能。
- **建议倾向**：若工程侧实测 GPU 瓶颈在 fill rate / overdraw → 选 A；若瓶颈在 draw call / CPU → 选 B。

### 5.3 粒子上限

| 方案 | 上限 | 实际用量 |
|------|------|----------|
| 通用硬上限 | **≤ 3,000 粒子** | — |
| 若选 A（cone） | — | ~800（仅爆炸/损毁） |
| 若选 B（粒子） | — | ~2,720（含尾焰） |

两种方案都在 3,000 上限内。

## 6. 纹理预算

- 不使用外部模型贴图。
- 程序化 CanvasTexture：星空噪点 512×512、尾焰渐变 128×128（若不用纯 shader）、扫描线/噪点 LUT 256×256。
- **总纹理内存 < 16 MB**（与 R0 一致）。

## 7. 后处理开销

| 配置 | Pass 数 | 说明 |
|------|---------|------|
| 基础（R1 默认） | **3** | Render + Bloom（半分辨率）+ CRT Shader |
| 若采用选择性 Bloom | **5** | +1 render target，+2 pass。**约 +30% 后处理开销**，仅在其他缓解手段（见 `materials-and-lighting.md` §7.3 方案 1-4）不足时才采用 |

CRT 强度滑杆**不增加 pass 数**，只改 4 个 uniform 值，性能影响可忽略。

## 9. 性能档位与自适应降级

| 档位 | Bloom 分辨率 | CRT 强度 | 舰船 LOD | 特效 | 触发条件 |
|------|--------------|----------|----------|------|----------|
| **High** | 全屏 | 用户设定 | LOD0 全开 | 全开 | FPS ≥ 55 |
| **Normal** | 半屏 | 用户设定 | 按距离自动 | 全开 | 默认 |
| **Low** | 半屏 | **强制 ≤ 50%** | 强制 LOD1+ | 减半 | FPS < 35 连续 3 秒 |

**降级顺序**（与 R0 一致，补充 CRT 相关项）：

1. 降低尾焰复杂度（cone → 发光点 / 粒子数减半）。
2. 常规舰降 LOD（LOD1 → LOD2 → **LOD3** → 关闭实体层只留 billboard）。
3. 降低 Bloom 分辨率。
4. **CRT 强度强制压到 ≤ 50%**（低配下扫描线/噪点是纯开销）。
5. 关闭 Bloom，仅保留 CRT 暗角。
6. **旗舰最后降级**（玩家视线焦点，保到最后）。
7. **接地投影与 L3 编队标记永不降级**（R1 新增，硬约束）。

> **第 7 条是硬约束，不是优化建议。** 接地投影是 UX 侧 R-02（S 级深度误判）的唯一解法底座；L3 编队标记是灰度/全色盲下**唯一幸存的敌我识别通道**（见 `accessibility.md` §6.3）。两者合计成本仅 ~528 tris / ~10 draw calls，却承载着三条 S/A 级风险的缓解——**性能再紧张也不能砍**，否则会直接触发可读性崩塌。

### 9.1 LOD 判据改为像素后对峰值的影响（R1-C，观察项）

§3 的 ~30,000 tris 峰值是按「32 艘全部 LOD0」核算的。LOD 改用屏幕投影像素判据（`ship-assets.md` §7）后，**这个最坏情况在物理上几乎不可达**：

- 要让全部 32 艘都 > 48 px（LOD0），相机必须近到只能看见其中一小部分 → **视锥剔除**。
- 拉远到能看见全部 32 艘时（相机距 ≈ 100 单位），战列舰 26.9 px、巡洋 17.1 px、舰载机 5.8 px → **大部分已自动降级到 LOD1-LOD3**。

即 **拉远 → 自动降级；拉近 → 视锥剔除**，两者天然互补。

**但不因此下调 36,000 tris 硬上限** —— 保留余量应对「多舰队集结于一点且相机较近」的极端情况（此时视锥内可能同时容纳大量 LOD0 舰船）。`[PLACEHOLDER · 附验证路径]`

```ts
private adaptQuality() {
  const avg = this.fpsHistory.reduce((a, b) => a + b, 0) / this.fpsHistory.length;
  if (avg < 35) { this.setQuality('low'); }
  else if (avg < 50) { this.setQuality('normal'); }
  else { this.setQuality('high'); }
}
```

## 10. 待工程侧对账的数字

以下数字需与工程侧架构文档 / 实测对账后才能锁定：

1. **尾焰方案**（cone vs 粒子）— 取决于实测瓶颈是 fill rate 还是 draw call。
2. **是否采用选择性 Bloom**（+2 pass，+30% 后处理开销）— 取决于零成本缓解手段是否已足够。
3. **InstancedMesh 在半透明场景的实际排序表现** — 若视觉验收不通过，常规舰需退回独立 Mesh，draw call 将从 ~161 涨到 ~265+。
4. **MSAA 开销** — 线框摩尔纹需要抗锯齿，`WebGLRenderTarget({ samples: 4 })` 在中低端集显上的代价需实测。
5. **`minDistance ≥ 8 世界单位` 是否可接受**（R1 新增）— 这是 `ship-assets.md` §3.4 底面免建模约束集的一条，需确认与「最近缩放体验」不冲突。若工程侧要求更小的 `minDistance`，底面免建模的余量会从 2.0× 收窄。
6. **实体层 alpha 0.55 对 overdraw 的实际影响**（R1 新增）— alpha 从 R0 的 0.22 提到 0.55，重叠舰船的 overdraw 贡献上升。需实测验证 `materials-and-lighting.md` §7.2 的「平均 ≤ 3.0× / 峰值 ≤ 5.0×」是否仍成立；若超标，优先降远处舰船的实体层而非降近处。
7. **线框加粗的技术路径**（`Line2` vs 放弃）— 决定 Comprehensive 档「线框粗细」选项能否落地，需架构阶段定。
