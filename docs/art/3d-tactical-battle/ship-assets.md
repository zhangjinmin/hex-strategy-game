# 3D 战术战斗层舰船资产规格

> 修订版 R1 — 已纳入用户决策：半透明实体 + 线框叠加 / 旗舰单独复杂程序化体 / 相机禁仰视（底面免建模）

## 1. 现状与约束

- 当前 `frontend/src/assets/ship/` 只有 2D PNG：`alliance_ship.png`、`empire_ship.png`、`brunhild.png`、`hyperion.png`、`flame.png`、`flame_round.png`。
- 没有任何 3D 模型资产，也没有 glTF/GLB 导入管线。
- 战略层（`ThreeStrategicMap.ts`）已使用 Three.js 原生几何体（`BoxGeometry` + `ConeGeometry`）组合出线框舰队，运行稳定。
- 战术层战斗规则/数值/AI 零改动，仅更换呈现。

## 2. 实现路径：程序化几何 + 半透明实体 + 线框叠加

### 2.1 决策依据

| 方案 | 优势 | 劣势 | 结论 |
|------|------|------|------|
| **程序化几何 + 半透明实体 + 线框叠加**（已定） | 无需建模资产；与战略层一致；支持 LOD/Instancing；半透明实体提供体积与纵深，线框保留 CRT 轮廓 | 透明排序复杂度上升；overdraw 增加 | **采用** |
| 纯线框 | 排序简单；最贴近战略层观感 | 暗背景下舰体“散掉”，3D 旋转时体积不可读 | 已否决 |
| 低模建模 + glTF | 表现力高 | 需要建模资源、UV、导出管线、加载器；无现有基础 | 不推荐当前阶段 |
| 2D 精灵 billboard | 性能最低 | 丢失 3D 旋转可读性，与“3D 化”目标冲突 | 仅作为 LOD2 回退 |

### 2.2 三层材质结构（半透明实体 + 线框叠加）

每个舰船由**同一个 `BufferGeometry`** 渲染 2-3 遍。三层职责严格分离：

| 层级 | 材质 | 颜色 | 不透明度 | 混合 | 职责 |
|------|------|------|----------|------|------|
| **① 实体层（体积）** | `MeshBasicMaterial` | 阵营色 × **0.35 亮度** | **0.18 - 0.28** | Normal | 提供体积、遮挡感、纵深。亮度压到 0.35 是为了**不触发 Bloom**（见 `materials-and-lighting.md` §7） |
| **② 线框层（识别）** | `MeshBasicMaterial` `wireframe: true` | 阵营色 × **1.0 亮度** | **0.80 - 0.95** | Normal | CRT 轮廓与敌我识别的主要来源，是唯一允许轻微 Bloom 的舰体层 |
| **③ 发光部件层（细节）** | `MeshBasicMaterial` | 引擎 `0xffcc66` / 炮口 `0xffffff` / 舰桥高光 | 0.6 - 0.9 | **Additive** | 引擎喷口、主炮口、旗舰标志、舰桥灯 |

**关键约束**：实体层只负责“体积”，不负责“亮度”。识别靠线框层，不靠实体层。这样半透明叠加时不会互相糊掉，也不会被 Bloom 放大成光团。

### 2.3 半透明的具体参数

```ts
// 实体层（同盟示例）
const hullSolidMat = new THREE.MeshBasicMaterial({
  color: new THREE.Color(0x2dd4bf).multiplyScalar(0.35), // 亮度压制，避开 Bloom 阈值
  transparent: true,
  opacity: 0.22,
  depthWrite: false,      // 必须关，见 materials-and-lighting.md §6
  depthTest: true,
  side: THREE.FrontSide,
});

// 线框层
const hullWireMat = new THREE.MeshBasicMaterial({
  color: 0x2dd4bf,
  wireframe: true,
  transparent: true,
  opacity: 0.88,
  depthWrite: false,
  depthTest: true,
  side: THREE.FrontSide,
});
```

`renderOrder`：实体层 = 10，线框层 = 11，发光部件 = 12。**线框层必须严格晚于实体层渲染**，否则会被实体层吞掉。

### 2.4 实现结构

建议新增 `frontend/src/game/three/ship/ShipGeometryFactory.ts`：

```ts
// 伪代码
ShipGeometryFactory.create({
  faction: 'alliance' | 'empire',
  class: 'battleship' | 'fast_battleship' | 'cruiser' | 'destroyer' | 'carrier' | 'fighter',

```

返回结构：`{ solid: THREE.Mesh, wire: THREE.Mesh, glow: THREE.Mesh[] }`，由调用方统一设置 `renderOrder`。

## 3. 底面免建模（相机禁仰视派生）

### 3.1 前提与修订（R1：仰角从 0.45π 收紧到 0.35π）

用户决策：**限制相机仰角，禁止看到舰船底部**。

R0 版沿用战略层的 `maxPolarAngle = π × 0.45`，但该值对应**仰角仅 9°**（`polarAngle` 自 +Y 轴量起，仰角 = 90° − polarAngle），是掠射角。design-strategist 在 `05-readability-risks.md` R-01 中指出：9° 仰角下一艘长 2.2 单位的舰船可遮蔽其后方 200+ 像素内的全部单位，且接地投影被压成一条线与舰体重叠（R-09）——这是 S 级必解风险。

**采纳 UX 侧意见，`maxPolarAngle` 收紧为 `0.35π`（仰角 27°）**，Basic / Standard / Comprehensive 三档统一（Comprehensive 不再单独收紧，理由见 §3.5）。

**关键**：底面免建模并不依赖某个特定的 `maxPolarAngle`，它依赖的是「相机始终高于最高舰船的底面」。见 §3.4 的可验证约束集。

### 3.2 规格

| 项 | 规格 |
|----|------|
| **底面处理** | **零细节封口面**。每个闭合体块在 −Y 方向用一个平面封口（三角形扇或单个 quad），不加倒角、不加装甲板分段、不加底部结构 |
| **封口是否必需** | **必需**。半透明实体若底部开口，会看到“空心穿帮”——背面被剔除后直接透视到舰体后方的场景，破坏体积感 |
| **封口成本** | 每个凸体块 2 tris（1 quad）。六边形截面舰体底面 = 4-6 tris |
| **可省略的几何** | 腹部装甲板分段、下缘倒角/斜切、底部引擎舱外壳、龙骨线、机腹挂架下盖、起降甲板底面内构、机腹细节 |
| **不可省略** | 侧面轮廓线（旋转视角下侧轮廓 = 剪影，是识别关键）、引擎喷口后半环、尾部收口 |

### 3.3 侧面必须保留的原因

虽然底面不可见，但**侧轮廓是敌我识别的第一载体**。旋转视角下玩家主要靠剪影分辨舰种与阵营。因此：

- 侧缘倒角、舷台、舰桥侧面层级、翼面厚度 **必须建模**。
- 底面封口面不参与线框层渲染时，可只给实体层使用（减少线框视觉噪音）。`[PLACEHOLDER · 附验证路径]`

### 3.4 悬空高度与「底面永不可见」的可验证约束集（R1 新增）

R0 版未给出悬空高度数值，导致底面免建模缺少可验证的前提。此处补齐。

**悬空高度（继承 2D `CrtRenderer.ts` 的 hover 值，按 §5.0 换算）**：

| 舰船 | 2D 悬空 | 世界单位 |
|------|---------|----------|
| 常规舰 | 10 px | **0.67** |
| 旗舰 | 26 px | **1.73** |

**约束集（五条同时成立时，底面在数学上永不可见）**：

| # | 约束 | 值 | 作用 |
|---|------|-----|------|
| **C1** | `maxPolarAngle` | **≤ 0.35π**（63°） | 保证 `cos(polar) ≥ 0.454` |
| **C2** | `minDistance`（最近缩放距离） | **≥ 8 世界单位（常量）** | 相机高度下界 = `8 × cos(0.35π) = 3.63` |
| **C3** | 旗舰悬空高度上限 | **≤ 2.0 单位** | 最高舰船底面 = `2.0 − 0.18(半高) = 1.82` |
| **C4** | 悬空高度离散度（旗舰 − 常规） | **≤ 1.5 单位** | **前瞻性约束，验算中未使用** —— 见下方说明 |
| **C5** | 公转目标点高度 `target.y` | **≥ 0** | 见下方说明 |

**C2 取常量 8，不用 `hexRadius` 表达。** UX 侧原公式 `dMin = hexRadius × 2.5` 已作废：1v1 小规模战斗 `hexRadius` = 26 px = 1.73 单位，该式给出 **4.3 单位 < 8**，会击穿 C2。**已由 UX 侧确认为常量，无体验冲突。**

**C4 是冗余的（UX 侧指出，本侧确认）。** C3 已经是绝对上限（2.0 单位），离散度在逻辑上不可能突破绝对上限，因此 §3.4 的验算**没有用到 C4**。保留它的真实目的是**约束未来的舰船尺寸/悬空扩展**——防止后续加入"巨型旗舰""轨道平台"等更高悬空的单位时，C3 被悄悄放宽而侵蚀余量。当前实际离散度 = `1.73 − 0.67 = 1.06 ≤ 1.5`，有余量。

**C5 是验算的隐含前提，必须显式化（UX 侧指出，本侧采纳）。** 验算假设相机公转目标在 `y = 0`：

- 若 target 跟随选中舰队（`y ≈ 1.73`），相机高度只会更高 → **更安全**，无需额外处理。
- 若实现 `dolly-to-cursor`（向光标方向推拉），**必须保证 `target.y ≥ 0`**，否则在低仰角下会把相机压到棋盘平面以下，届时底面免建模失效。

**验算**：相机最低高度 3.63（C1×C2，target.y = 0） > 最高舰船底面 1.82（C3）→ **余量 2.0×**（UX 侧独立复核：3.63 / 1.82 = 1.995 ✓）。

**结论**：在 `maxPolarAngle = 0.35π` 下，即使相机绕棋盘平面（y = 0）公转，底面免建模依然成立，**无需改变公转目标点**。

**C2（`minDistance ≥ 8`）已由 UX 侧确认无体验冲突，采纳为常量。** C5（`target.y ≥ 0`）是本次新增，需在相机实现时显式保证。

**失效后果评估**（若工程侧无法满足 C1-C4）：
- 舰船底面封口面（2 tris/体块）**已经在预算内**，不会超支。
- 最坏情况是玩家在极近距离看到若干块无细节的纯色封口面 —— 视觉降级，但**不破坏预算、不产生穿帮**。相比棋盘底面（永远在 y = 0 之下，任何仰角都不可见，可放心省略 6 tris/格），风险可控。

### 3.5 为什么 Comprehensive 不再单独收紧仰角

R0 版给 Comprehensive 单独设 `π × 0.35`，是把它当「晕动症更强限制」。但 UX 侧指出 0.45π 对 **Basic 档同样不可用**（R-01 是 S 级，影响所有人，不只是敏感用户）。

**修订**：`maxPolarAngle` 三档统一 `0.35π`。Comprehensive 的额外收益改由「方位角/仰角旋转速度上限更低」（UX 侧 `06` §1.1：60°/s vs 120°/s）与「完全锁定相机」提供 —— 这些才是真正针对晕动症的手段，仰角下限解决的是可读性问题，两者不应混为一谈。

## 4. 同盟 vs 帝国识别性设计

### 4.1 阵营色

沿用战略层：
- 同盟：`0x2dd4bf`（青绿） / CRT 强调 `0x00cc66`
- 帝国：`0xc084fc`（紫）
- 第三方/中立：沿用 `0xfbbf24`

### 4.2 轮廓语言

| 阵营 | 整体轮廓 | 舰首 | 上层建筑 | 旗舰标志 |
|------|----------|------|----------|----------|
| **同盟** | 方正、厚重、模块化、直角多 | 垂直或微前倾的平头/梯形 | 盒式舰桥、平板侧翼 | 顶部十字锚标 / 双天线 |
| **帝国** | 修长、前倾、弧线、锐角多 | 尖锐的锥形/镰形前倾 | 高耸塔式舰桥、后掠翼 | 顶部冠状/翼状装饰 |

### 4.3 旋转视角下的敌我识别

仅靠颜色对色盲玩家不友好，必须同时提供：
1. **底部椭圆投影**：同盟为圆角矩形/菱形投影，帝国为尖椭圆投影。
2. **旗舰顶部标志**：同盟十字，帝国冠羽，普通舰无标志。
3. **HUD 括号**：选中/悬停时显示阵营色 L 形角标。
4. **剪影差异**：同盟方正、帝国前倾（在底面免建模前提下，剪影是唯一不依赖颜色的识别通道，优先级最高）。
5. **编队尾焰数量**：帝国舰尾焰更细长、分叉；同盟尾焰更粗短、集中。
6. **L3 编队聚合标记**（R1 新增，形状由 UX 侧定义、颜色由本侧定义）：见 §4.4。

### 4.4 L3 编队聚合标记（新增，配合 UX 侧 `01` §4）

UX 侧新增了一层本规格原先没有的信息层级：当舰体轮廓与接地投影都退化到不可辨时（L3 编队聚合档），由编队标记承载敌我识别。**形状由 UX 定（同盟 ▲ / 帝国 ◆），颜色与渲染规则由本侧定**。

| 项 | 规格 |
|----|------|
| 形状 | 同盟 = ▲（正三角，尖端朝上）；帝国 = ◆（菱形，长轴沿舰队朝向） |
| 尺寸 | **屏幕空间恒定**（不随距离缩小），基准 24×24 px，随信息 LOD 档位缩放 |
| 颜色（默认） | 同盟 `0x2dd4bf`；帝国 `0xc084fc` |
| 颜色（色盲模式） | 红绿色盲：同盟 `0x3b82f6` / 帝国 `0xfacc15`；蓝黄色盲：同盟 `0x22c55e` / 帝国 `0xef4444` |
| 渲染 | `depthTest: false`，`depthWrite: false`，`renderOrder = 31`（高于 HUD 基础层 30，低于选中高亮） |
| 亮度 | 用阵营色**满亮度**（不乘 0.35）—— 标记是信息层不是体积层，且需要过 Bloom 阈值以获得描边辉光，保证远处可读 |
| 灰度可用性 | ▲ 与 ◆ 是**纯形状差异**，灰度化后仍可分辨 → 全色盲模式下本标记是主要识别通道，必须保留 |
| **雷达复用** | 战术雷达（`radar-visual-spec.md` §2）**完全复用本标记的形状与配色**（含两种色盲模式），3D 主视图与雷达共用一套编码，尺寸减半为 12px |

**渲染 LOD ↔ 信息 LOD 映射**（R1-C 更新为 4 档，消除两套命名体系的歧义）：

| 本规格（渲染 LOD） | 屏幕投影 | UX 侧（信息 LOD） | 标记可见性 |
|--------------------|:--------:|-------------------|-----------|
| **LOD0** | > 48 px | **L0** 全信息 | — |
| **LOD1** | 24 – 48 px | **L1** | — |
| **LOD2** | 12 – 24 px | **L2** | — |
| **LOD3** | < 12 px | **L3** 编队聚合 | **▲ / ◆ 出现，接管敌我识别** |

> R1-B 版写过「LOD2 对应 L3」——**该表述不准确**，已废弃。LOD2 对应 L2（12-24 px，仍逐舰显示舰种图标与 HP），**只有 LOD3（<12 px）才进入编队聚合**。这也是本次新增 LOD3 的原因：让渲染侧与信息侧的档位一一对应，避免实现时两个系统对不上。

**覆盖层 renderOrder 区间预留**（R1-D，配合 UX 侧编号徽章）：31 及以上全部为 `depthTest: false` 的屏幕空间覆盖层，不再承载世界空间物体，避免后续层层上叠。

| renderOrder | 用途 | 归属 |
|:-----------:|------|------|
| 30 | HUD 基础层（四角角标、刻度） | 美术 |
| **31** | **L3 编队聚合标记 ▲/◆** | 美术 |
| **32** | 命令候选编号徽章 | UX |
| 33 | *预留*：徽章选中态高亮 | UX |
| 34 | *预留*：tooltip / 悬停边框 | UX |
| 35-39 | *预留*：未来覆盖层 | — |

**成本**：每支舰队 1 个标记，按 8 支舰队计 = 8 个 billboard ≈ **16 tris / 8 draw calls**（标记需 `depthTest:false` 不能与舰体 instancing 合并）。相对 36,000 tris 预算可忽略。

## 5. 六类舰船规格（常规舰）

坐标系约定：+X 右，+Y 上，+Z 前（舰首朝向）。尺寸单位为“世界单位”，1 单位 ≈ 当前 `hexRadius=26` 像素的 1/13（约 2 px）。

### 5.0 世界单位与 2D 像素的换算（R1 修正：上一行有错）

**R0 版写错了**：按「1 单位 ≈ 2 px」，2.2 单位的战列舰只有 4.4 px，而 2D 实际是 33 px —— 与下方尺寸表自相矛盾。**正确换算如下**。

以 2D 标准战舰长度 33 px ↔ 3D 长度 2.2 单位 为锚点：

> **1 世界单位 ≈ 15 px**

| 2D 量 | 像素值 | 世界单位 |
|-------|--------|----------|
| `hexRadius` | 26 | **1.73** |
| 战列舰长度 | 33 | 2.20 |
| 旗舰长度 | 42 | 2.80 |
| 常规舰悬空高度 | 10 | **0.67** |
| 旗舰悬空高度 | 26 | **1.73** |
| 护盾涟漪 rx（14→32） | 14 → 32 | 0.93 → 2.13 |
| 接地投影半径（6→9） | 6 → 9 | 0.40 → 0.60 |

**本文档后续所有尺寸均用世界单位**，`[PLACEHOLDER · 附验证路径]` 表示需 playtest 验证。

> ⚠️ **与 UX 侧的单位冲突（已回退给 design-strategist）**：`05-readability-risks.md` R-09 写「抬升投影至平面上方 **2 单位**」、R-15 写「网格线与平面间留 **0.5 单位** 偏移」。按本表，2 单位 = **30 px**，比旗舰悬空高度（26 px）还高 —— 投影会浮到舰船上方。技术解法见 `materials-and-lighting.md` §8：改用 `polygonOffset`，与单位无关。

棋盘平面为 y = 0，舰船悬空于 y = hover 之上（悬空高度见 §3.4）。

面数已按 §3 底面免建模规则下调（较 R0 版约 −18%）。`[PLACEHOLDER · 附验证路径]` 表示需 playtest 验证。

### 5.1 Battleship（标准战舰）

| 项 | 规格 |
|----|------|
| 定位 | 最大、最重、火力核心 |
| 长×宽×高 | 2.2 × 0.7 × 0.35 世界单位 |
| 主形体 | 长方体船体（长 2.0，高 0.3，宽 0.6）+ 前部梯形舰首 |
| 舰桥 | 顶部居中盒式舰桥（0.4×0.25×0.25） |
| 侧翼 | 左右各一块矩形舷台（0.25×0.08×0.6） |
| 引擎 | 2 个朝后圆柱喷口，直径 0.08，长 0.15 |
| 主炮 | 左右舷台各 2 个短圆柱炮管（长 0.2，直径 0.04） |

## 7. LOD 分级策略（R1-C 重写：改用屏幕投影像素为唯一判据）

### 7.0 为什么必须改（采纳 UX 侧 C-7）

R0/R1-B 的距离阈值（LOD0 <8 / LOD1 8-20 / LOD2 >20 单位）**是错的**。按 fov 50°、1080p 换算，20 单位处战列舰投影约 **135 px**——而全图档（相机距 ~100 单位）才 **27 px**。原阈值意味着**玩家一拉远就看到满屏 billboard 图标**，而拉远恰恰是"想看全局"的时候。

根因：我把「相机距离」当成了「可读性」的代理量，但两者不成正比——同一距离下战列舰 135 px 与舰载机 29 px 需要完全不同的细节度。

R0 末尾标了"按距离还是按像素"未决，**此处给出答案：统一用屏幕投影像素，不再保留距离判据**。两套并存必然打架（同一个 switch 会有两个触发条件）。

### 7.1 换算公式

透视投影，垂直 fov = 50°，屏高 1080 px：

```
px = char × 1080 / (2 × d × tan(fov/2))
   = 1158 × char / d                       // tan(25°) = 0.4663

反解：  d = 1158 × char / px
```

**`char` = 包围球直径 = `√(L² + W² + H²)`**，取包围球而非 XZ 对角或长度，因为**相机绕转时包围球直径恒定**，不会因为舰船朝向变化导致 LOD 在阈值附近抖动。

> 注：UX 侧用 XZ 对角（战列舰 2.309）算得 20 单位处 133 px；本侧用包围球（2.335）算得 135 px。差 1.7%，不影响结论。

### 7.2 LOD 定义（与 UX 侧信息 LOD 1:1 对齐，新增 LOD3）

| 渲染 LOD | **屏幕投影** | 内容 | 层策略 | 特效策略 | ↔ UX 信息 LOD |
|:--------:|:------------:|------|--------|----------|:-------------:|
| **LOD0** | **> 48 px** | 完整几何（侧缘倒角、舰桥层级、天线） | 实体 + 线框 + 发光部件全开 | 尾焰全精度、护盾全采样、激光全精度 | **L0** |
| **LOD1** | **24 – 48 px** | 合并为 3-5 个体块，隐藏炮管/天线 | 实体层保留 + **降密度线框**（线数减 ~60%，**线亮度保持 0.90 不衰减**） | 尾焰静态锥，护盾降采样 | **L1** |
| **LOD2** | **12 – 24 px** | billboard 精灵 / 6-8 面锥形图标 | 单层 | 仅发光点，关闭尾焰 | **L2** |
| **LOD3** | **< 12 px** | **不渲染个体**，由 L3 编队聚合标记 ▲/◆ 承担 | — | 全部关闭 | **L3** |

**关键约束**：LOD1 的线框是**降密度不是降亮度**。远处舰船线数变少但每条线依然 0.90 不透明——这来自 UX 侧 R-17（暗背景下远处舰船必须保持可辨轮廓），我 R0 写的"远处线框淡出"已因此撤回。

### 7.3 各舰种的切换距离（`d = 1158 × char / px`，世界单位）

| 舰种 | `char`（包围球直径） | LOD0→1<br>(48 px) | LOD1→2<br>(24 px) | LOD2→3<br>(12 px) |
|------|:-------------------:|:-----------------:|:-----------------:|:-----------------:|
| 名舰旗舰（Brunhild / Hyperion） | 2.926 | **70.6** | **141.2** | **282.4** |
| Battleship | 2.335 | **56.3** | **112.7** | **225.4** |
| Fast Battleship | 2.083 | **50.3** | **100.5** | **201.0** |
| Carrier | 2.074 | **50.0** | **100.1** | **200.2** |
| Cruiser | 1.487 | **35.9** | **71.7** | **143.5** |
| Destroyer | 1.042 | **25.1** | **50.3** | **100.5** |
| Fighter | 0.504 | **12.2** | **24.3** | **48.6** |

> 名舰旗舰 `char` 按长 2.80 / 宽 0.75 / 高 0.40 估算。

### 7.4 三个直接推论（重要）

**① 战列舰与旗舰在可达距离内永不进入 LOD2 / LOD3。**

全图档相机距离 ≈ 100 单位（战场 2500 px = 167 单位宽，fov 50° + 16:9 下可视宽 `= 1.658 × d`，覆盖 167 单位需 `d ≈ 100.5`）：

| 舰种 | 全图档（d≈100.5）投影 | 落在 |
|------|:---------------------:|------|
| 名舰旗舰 | **33.7 px** | LOD1 |
| Battleship | **26.9 px** | LOD1 |
| Cruiser | 17.1 px | LOD2 |
| Destroyer | 12.0 px | LOD2/L3 边界 |
| **Fighter** | **5.8 px** | **LOD3** |

→ **LOD2 / LOD3 主要服务巡洋、驱逐、舰载机**；战列舰与旗舰的 LOD2/LOD3 几何基本用不上（但仍需实现，以防未来加长地图）。

**② 舰载机是全表最早降级的舰种** —— 48.6 单位就到 LOD3，而战列舰此时（48.6 单位）投影 56 px 仍在 LOD0。这印证了 UX 侧 R-14 的判断：**拾取困难的主体是舰载机，不是"远处舰船"**。

**③ 最近档（`minDistance = 8`）下战列舰投影 338 px ≈ 屏高 31%**，适合"贴近检视旗舰"。与 UX 侧复核一致。

### 7.5 滞回与防抖

阈值上下各 **15%** 滞回：

```
LOD1 → LOD2  在 24 px 触发
LOD2 → LOD1  需回到 24 × 1.15 = 27.6 px
```

即 LOD 升级用 `px < T`，降级用 `px > T × 1.15`。避免在阈值附近因相机微动导致 LOD 高频抖动（这比距离判据更容易发生，因为像素值对距离更敏感）。`[PLACEHOLDER · 附验证路径]`

### 7.6 降级顺序（性能不足时）

与 R1-B 一致，补充 LOD3：

1. 常规舰 LOD0 → LOD1 → LOD2 → LOD3
2. 关闭常规舰实体层（只留线框）
3. **旗舰最后降级**（玩家视线焦点）
4. **接地投影与 L3 编队标记永不降级**（见 `performance-budget.md` §9）

**性能降级与 LOD 是两套机制**：LOD 由屏幕投影驱动（自然降级），性能降级由 FPS 驱动（强制降级）。后者可覆盖前者，例如帧率不足时强制把 LOD0 降到 LOD1 而不管像素值。

### 7.7 对性能预算的正面影响（观察，未改预算）

R1-B 按"32 艘全部 LOD0"核算了 ~30,000 tris 峰值。改用像素判据后，**这个最坏情况在物理上几乎不可能同时发生**：要让全部 32 艘都 >48 px，相机必须近到只能看见其中一小部分（视锥剔除）。

即：**拉远 → 舰船自动降级；拉近 → 视锥剔除大部分**。两者互为补充。

**但本侧不因此下调 36,000 tris 上限** —— 保留余量应对"多舰队挤在视锥内同时接近"的极端情况（如所有舰队集结于一点）。`[PLACEHOLDER · 附验证路径]`

## 8. 命名与文件组织建议

```
frontend/src/game/three/ship/
  ShipGeometryFactory.ts      # 入口
  ShipMaterials.ts            # 阵营/LOD/层 材质缓存
  ShipRenderOrder.ts          # renderOrder 常量集中定义

    AllianceBattleship.ts

    ...
  flagships/

    GenericAllianceFlagship.ts
    GenericEmpireFlagship.ts
```

- 材质按 `(faction, layer, lod)` 复用，不 per-ship 新建，避免泄漏。

- **底面封口统一在几何生成阶段完成**，不在运行时判断。
