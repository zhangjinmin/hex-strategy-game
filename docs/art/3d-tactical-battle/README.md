## 1. 战场“应该长什么样”

把 3D 战术战场看作**战略星图“阿凡达全息沙盘”的近距离战斗投影**：

- **空间基调**：极暗虚空背景（`#040810` / `0x02040a`），散布稀疏星点与 faint 参考网格。没有地表、没有天空盒，也没有写实太空光照。一切物体都是悬浮的“全息作战台”元素。
- **棋盘**：六边形格子以**立体棱柱**形式存在，高度按地形/建筑类型分层（`castle/fortress/planet` 更高，`sea/ruined` 更低）。顶面与侧面由细线框勾勒，填充极淡， faction 控制格用阵营色点亮棱柱边缘。棋盘本身微微发光，像是从下方托盘投影出来的战术图层。
- **舰队**：舰船是**半透明实体 + 线框叠加**的低多边体，悬浮在棋盘上方（旗舰更高，普通舰更低），底部拖有一道淡淡的引擎光柱，正下方投射一个椭圆全息投影。半透明实体提供体积与纵深，线框提供 CRT 轮廓与敌我识别——两者职责严格分离。舰队在移动时尾部喷出锥形离子尾焰。
- **交战反馈**：主炮射击是一道瞬间拉亮的细激光束；命中护盾时，目标周围出现一道从受击点向两侧扩散的弧线涟漪；被命中舰体会短暂闪烁。
- **镜头**：默认等轴俯视，略高于棋盘平面，允许玩家旋转/缩放，但**限制仰角，永远看不到舰船与棋盘的底部**。
- **CRT 痕迹保留**：画面叠加扫描线、径向色差、暗角与微噪点，四角有 L 形 HUD 定位记号，顶部有细刻度。这些不是“复古滤镜”，而是同一套全息投影 UI 的延续。**强度全局可调（0-100%，默认 75%），重度敏感用户可归零。**

## 4. 半透明方案的技术要点（速查）

半透明实体 + 线框叠加放大了 R0 风险清单里的「Bloom 过曝」与「线框混叠」。已在 `materials-and-lighting.md` §7 给出可直接落地的参数，要点：

| 问题 | 缓解手段 | 成本 |
|------|----------|------|
| 透明排序翻车 | 所有 transparent 材质 `depthWrite = false` + **显式 renderOrder 分层**（棋盘 0-3 / 舰船 10-12 / 特效 20-23 / HUD 30）；Additive 层可安全 instancing（加法交换律免疫排序），旗舰单独 Mesh 精确排序 | 0 |
| Overdraw 失控 | 半透明层数上限 **4 层**；平均 overdraw ≤ 3.0×、峰值 ≤ 5.0×；超限时按 LOD 降级顺序处理 | 0 |
| Bloom 过曝 | ① 实体层亮度 ×0.35（使其低于阈值）② Bloom threshold 0.52 → **0.62** ③ Bloom strength 与 CRT 强度**反向联动** ④ ACESFilmic tone mapping 兜底 ⑤（可选）选择性 Bloom，+2 pass | ①-④ 零成本，⑤ +30% 后处理 |
| 线框摩尔纹 | MSAA（`samples: 4`）+ 线框 opacity 收敛为 0.90 + **远处用 LOD 降「线数」而非降「亮度」**（R1 修订，原「远处淡出」与 UX 侧 R-17 冲突已撤回） | 低 |

| UX 要求 | 本侧响应 |
|---------|----------|
| 接地投影 alpha ≥ 0.8、不随特效滑杆归零 | **部分采纳**：改为「轮廓 0.85 + 填充 0.25」（实心 0.8 亮盘会喧宾夺主且逼近 Bloom 阈值）。**豁免条款完全采纳**——投影不随滑杆归零，且特效越低投影越强；z-fighting 用 `polygonOffset`，**驳回「抬升 2 单位」** | `materials-and-lighting.md` §8 |

**发现并修正的两处自身错误 / 冲突**：

1. **单位换算错误（本侧 R0 遗留）**：原写「1 单位 ≈ 2 px」，与舰船尺寸表自相矛盾。正确为 **1 单位 ≈ 15 px**。这直接暴露了 UX 侧 R-09「抬升投影 2 单位」= 30 px 会浮到舰船上方——已回退。
2. **与 UX 侧 R-17 的直接冲突（本侧 R0 遗留）**：我原先写「远处线框按距离淡出」，但 R-17 要求「边缘光强度不随距离衰减」。已撤回，改为**远处降线数（LOD）保亮度**。
3. **渲染 LOD 距离阈值过早起效（本侧 R0 遗留，UX 侧 C-7 指出）**：距离判据把「拉远」误判为「看不清」，实际 20 单位处战列舰投影 135 px，是全屏最清晰的时候。详见下方 §4.5.1。

### 4.5.1 C-7 详解：LOD 判据从「距离」改为「屏幕投影像素」

**换算公式**（`char` = 包围球直径 = √(L²+W²+H²)，取包围球是因为**相机绕转时直径恒定**，不会因舰船朝向变化导致阈值抖动）：

```
px = 1158 × char / d        // fov 50° 垂直、屏高 1080 px
d  = 1158 × char / px       // 反解
```

| 渲染 LOD | 屏幕投影 | 内容 | ↔ UX 信息 LOD |
|:--------:|:--------:|------|:-------------:|
| **LOD0** | > 48 px | 完整几何，三层全开 | L0 |
| **LOD1** | 24 – 48 px | 简化几何，**降线数但线亮度保持 0.90** | L1 |
| **LOD2** | 12 – 24 px | billboard / 6-8 面图标 | L2 |
| **LOD3** | < 12 px | **不渲染个体**，由 ▲/◆ 编队标记承担 | L3 |

**各舰种切换距离**（`d = 1158 × char / px`）：

| 舰种 | `char` | →LOD1 (48px) | →LOD2 (24px) | →LOD3 (12px) |
|------|:------:|:------------:|:------------:|:------------:|
| 名舰旗舰 | 2.926 | 70.6 | 141.2 | 282.4 |
| Battleship | 2.335 | 56.3 | 112.7 | 225.4 |
| Fast Battleship | 2.083 | 50.3 | 100.5 | 201.0 |
| Carrier | 2.074 | 50.0 | 100.1 | 200.2 |
| Cruiser | 1.487 | 35.9 | 71.7 | 143.5 |
| Destroyer | 1.042 | 25.1 | 50.3 | 100.5 |
| Fighter | 0.504 | 12.2 | 24.3 | 48.6 |

**三个推论**：

1. **战列舰与旗舰在可达距离内永不进入 LOD2/LOD3**。全图档（d ≈ 100 单位，覆盖 167 单位宽战场）时战列舰 26.9 px、旗舰 33.7 px，仍在 LOD1。→ LOD2/L3 主要服务巡洋、驱逐、舰载机。
2. **舰载机最早降级**：48.6 单位就到 LOD3，而战列舰此时（48.6 单位）投影 56 px 仍在 LOD0。印证 UX 侧 R-14——**拾取困难的主体是舰载机，不是「远处舰船」**。
3. **像素判据与视锥剔除天然互补**：拉远则自动降级，拉近则视锥剔除大部分。R1-B 按「32 艘全 LOD0」核算的 ~30,000 tris 峰值在物理上几乎不可达。**但不因此下调 36,000 上限**——保留余量应对「多舰队挤在视锥内同时接近」的极端情况。

**为什么不再保留距离判据**：同一距离下战列舰 135 px 与舰载机 29 px 需要不同细节度；距离 + 像素两套判据并存必然打架（同一个 switch 会有两个触发条件）。R0 标为未决，此处定案。

**滞回**：阈值上下各 15%（LOD1→LOD2 在 24 px 触发，LOD2→LOD1 需回到 27.6 px），避免相机微动导致高频抖动。

### 4.5.2 舰载机（Fighter）不参与单体拾取 — 部分采纳

UX 侧建议 Fighter 不参与单体拾取、LOD2 起不画个体。**交互侧采纳，渲染侧不采纳**：

| 项 | 结论 | 理由 |
|----|------|------|
| 不参与单体拾取 | **✅ 采纳** | 规则层不存在作用于单机的玩家指令（2D 舰船本就不可选中）。纯交互变更，美术侧零成本 |
| LOD2 起不画 Fighter 个体 | **❌ 不采纳** | Fighter 仅 50 tris，同屏数量受舰队编制限制（≤8/阵营），节省 < 400 tris。为此新增一条特殊代码路径的维护成本高于收益。Fighter 走**标准 LOD 阶梯**即可——它本来就是全表最早降到 LOD3（<12 px 即不渲染个体）的舰种，已自动达成省渲染的目的 |

**触发重评的条件**：若未来实现「航母释放舰载机群」（同屏 Fighter > 16），改用 **instanced swarm renderer** 统一处理，届时再单独定 LOD 策略。

| 三角面 | +3,072 | +5,440 |

**对账判据**：若工程侧实测瓶颈在 fill rate / overdraw → 选 **cone**；若瓶颈在 draw call / CPU → 选 **粒子**。

### 7.2 需工程侧对账后锁定（7 项）

1. **是否采用选择性 Bloom**（+2 pass，+30% 后处理开销）— 取决于零成本缓解手段是否已足够。
2. **InstancedMesh 在半透明场景的实际排序表现** — 若视觉验收不通过，常规舰需退回独立 Mesh，draw call 将从 ~161 涨到 ~265+，需重开预算。
3. **MSAA 开销** — 线框摩尔纹需要抗锯齿，`WebGLRenderTarget({ samples: 4 })` 在中低端集显上的代价需实测。
4. **线框加粗的技术路径** — WebGL `linewidth` 在多数桌面浏览器恒为 1px，必须改用 `Line2`/`LineMaterial`。**需在架构阶段确认**，否则 Comprehensive 档「线框粗细」选项无法落地（本侧已预置替代方案：提高 opacity + 实体层 alpha）。
5. **`minDistance ≥ 8 世界单位` 是否可接受**（R1-B 新增）— 底面免建模约束集 C2。若工程侧要求更小值，底面余量会从 2.0× 收窄，需重算。
6. **实体层 alpha 0.55 的 overdraw 实测**（R1-B 新增）— alpha 从 0.22 提到 0.55 后，需验证「平均 ≤3.0× / 峰值 ≤5.0×」仍成立。超标时优先降**远处**舰船实体层，而非近处。
7. **是否同步改造战略层阻尼**（R1-B 新增，低优先级）— 战略层 `controls.dampingFactor = 0.08` 仍是逐帧 lerp。战术层改指数形式后，低帧率下两层手感会分叉。不属于本次改造范围，仅记录。
