## 2. 验收方法（本轮的关键变化）

上一轮**只有源码级 harness**（`_verify_*.cjs`，读源码断言），看不到"实机像不像 demo"。
本轮补齐**真机闭环**（任务原文要求："构建产物 → 起本地服务 → 用 Playwright/无头 Chromium 实跑会战"）：

```
_v2_shot.html + _v2_shot.ts   ← 把**真实** Battle3DOverlay 挂进真实 Chromium/WebGL
        │                        （Phaser BattleScene 用只实现"读取契约"的替身；舰位由与
        │                         BattleScene 同一套阵型公式解出稳态）
_v2_play.cjs                  ← 起 Vite(5199) → 无头 Chromium + SwiftShader → 按场景摆相机 → 截图
        └─ _v2_shots/*.png + manifest.json（含 __b3dStats / __b3dVLayout / __b3dPerf 原始读数）
_v2_report.cjs                ← 把 manifest **机器抽取**成下表；并用 config/ 单一真源**独立重算**
        └─ 渲染值 vs 重算值 交叉核对（源码级 harness 给不出这一类证据）
```

**为什么这些数字可信**（三条防线，缺一不可）：

1. **数字不进人眼/人手**：报告里所有读数由 `_v2_report.cjs` 从 `manifest.json` 抽取，截图与读数同一帧采集。
2. **独立重算**：`layerGap` / `teamGap` / 档位高度不是"截图上看着差不多"，而是用 `formationLayout.ts` +
   `fleetTierLayout.ts` 的公式**重算一遍**再和真机渲染值比（§3 B/C）。判据：`|渲染 − 重算| < 0.01`。
3. **每条断言配"能失败的对照"**：例如 WS5 的比值换算是否非平凡 —— 若照搬 demo 绝对值（门宽 3），
   则 **3 < 舰宽 26.93**，必然互穿（§3 E 与源码级 F 段都有该对照）。

**判据设计上踩过并修正的两个坑**（如实登记，见 §8）：

- **三级分级是"逐舰"的**，不是"整队"的：一次机位下同队里战列舰可能已进实体档、战机还在远景档。
  故**不能**断言"某档单位数 == 全队数"。已改为断言**换档链**（实体数单调增 / 光点先涨后收 / 标记单调退场 / 三档互补）。
- **`rowsSpanAllLayers` 是计数不是布尔**（满层排数），`sides.ys` 是**去重后**的档位高度
  （perSide=6 时 6 支舰队只占 3 个高度）。断言口径已按真实语义修正。

## 8. 诚实备注（证据强度与局限）

1. **本报告证明的是"渲染与几何"，不是"打起来的完整流程"。**
   真机台架用的是**替身 `BattleScene`**（只实现 overlay 读取的那部分契约：`tilesList/factionMap/globalFleets/hexRadius/mapStyle/supplyInfo/auxShips/handleTileClick`），
   舰位由与 `BattleScene` **同一套阵型公式**解出稳态。因此"战斗过程、伤害、减员、命中判定"**不在本轮证据范围内**，
   需要严守真在真机跑一遍会战才能盖章。
2. **SwiftShader 软渲染 ≠ 真实 GPU。** `50_perf_governor_on` 的 47.61 ms 只用来证明"降档机制真的会动"，
   **不能**用来推断用户机上的帧率。高密档（k=125）、6v6 满编的真实帧率**必须在用户机上复测**。
3. **截图为低 LOD**（`detail=low`，lod2 ≈5% 面数）。
