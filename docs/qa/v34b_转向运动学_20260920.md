## 1. 转向问题的数值链（修前，L2 实测）

`_probe_turn.mjs`：真实战场、给舰队一个与当前航向成 90° 的目标点、页面内逐帧采样。
修前 3 队一致：

| 指标 | 实测 | 对应你的描述 |
|---|---|---|
| `framesToTurnVel` = **49** | 位移方向 49 帧就转完 90% | 「舰队先通过诡异的移动 / 都已经快速移动了」 |
| `framesToTurnNose` = **127** | 舰首 127 帧才转完 | 「然后再看到那个船在慢慢地转」 |
| 时间差 = **+78 帧（2.6×）** | 位移**先行**、转身**滞后** | 「先移动…然后再慢慢转」 |
| `misalignMaxDeg` = **57.9°** | 速度方向与舰首差近 58° | 「横着走」/ 诡异 |
| `speedMinRatio` = **0.483** | 转向期航速掉到 48% | 「**暂停**」 |
| 单位相对位移 早/晚 = **3.34 / 1.23（2.7×）** | 前半段大范围重排、后半段几乎不动 | 「先大范围舰船变化，然后暂停」 |

### 代码根因（一句话）

**位移方向用 `moveAngle`（瞬时目标方向），而速度大小用 `thrustFactor`（舰首 vs 目标的对齐度）
⇒ 方向与大小不自洽**：目标方向一变，舰队立刻朝新方向平移，舰首还在慢慢转。

v30 的注释写明了这是刻意的（"位移方向 = 目标方向，转身只由舰首姿态完成"），
目的是修 v29 的"沿弧线飞 = 诡异/像风暴"——**结果制造了另一组诡异**。

## 2. 本轮改动（3 处，均可独立回退）

| 位置 | 改动 |
|---|---|
| `BattleScene` 位移计算 | **位移方向 = 推力方向 = 舰首朝向** `facingSmooth`（物理：主引擎只能沿舰首推进）。唯一例外：**拖刀**（撤退+接敌，舰首朝敌、位移朝补给）保留目标方向 |
| `THRUST_IDLE` | 0.05 → **0.45**：转向期间不再把舰队压到"几乎停船" |
| 常量 | `FLEET_BASE_SPEED` 从内联 `0.30` 提为常量（**值未改**），并注明它是转弯半径的唯一杠杆 |

### 2.1 为什么必须三处一起改（单独改任一处都更糟）

- 只改**方向**（下限仍 0.05）⇒ 舰首未对齐时几乎停船 ⇒ 回到 v29「原地画小圈」；
- 只改**下限/航速**（方向仍取目标）⇒ 位移更超前于舰首 ⇒「横着走」更明显；
- 台架 `_v34b_kinematics_sim.cjs` §1 的对照列已包含这两种组合的后果。

### 2.2 「中心对称阵型（圆/方）」不再享受例外

初版给圆/方阵保留了旧逻辑（怕复活 v30 的"圆阵风暴"）。L2 同场对照证明这会造成
**两套行为并存**：

| | `misalignMax` | `speedMinRatio` | 位移/转身帧差 |
|---|---|---|---|
| wedge（新逻辑） | **12.2°** | **1.018** | **−3** |
| square（旧逻辑） | **62.0°** | 0.720 | **+80** |

同一编队里一半舰队利落转弯、另一半横着走，比单一缺陷更难读 ⇒ **统一为沿舰首推进**。
"风暴"担忧的根因是半径过小（v=0.30 时 R=23px）；半径的解法见 §2.3。

### 2.3 转弯半径：v29 的推导漏掉了一条路

`R = v / ω`。v29 的注释只算了"**降低 ω**"（结论：ω < 6°/s ⇒ 180° 掉头要 35s，不可玩），
**漏掉了"提高 v"**：

| v (px/帧) | R = v / ω (ω=45°/s) | 相对舰长 25px |
|---|---|---|
| 0.30（现状） | **22.9px** | 0.9 倍 ⇒ 读作"原地打转" |
| 0.60 | 45.8px | 1.8 倍 |
| 0.90 | **68.8px** | **2.8 倍** ⇒ 读作"划弧前进" |

⚠ 提高 v 同时把"接近 800px 交战距"由 ~44s 压到 ~15s（**节奏变更**）
⇒ 本轮**不擅自改**，把 `FLEET_BASE_SPEED` 提为常量并标注推荐区间 **0.30 ~ 0.90**，由你按真机观感决定。

场景 = 最苛刻的一类：目标在**正后方 800px**（必须掉头再追）。

换来"舰首与位移同步、不掉速"⇒ 收敛性验证通过（无极限环），代价可接受。

`import('/src/game/GameInstance.ts')` 在 **HMR 之后会拿到另一个模块实例**

## 4. 分舰队「一片 + 浮在最上档」：机制已定位（未实施）

### 4.1 实测数据（真源码纯计算）

层距 `layerGap = 8.13`、体高 5.89、队间档距 `teamGap = 130.7px`（hexR=50 会战期）。

| 规模 | 阵型 | 足迹(宽/深格) | minSpan | **层数** | **纵向厚度** | 厚:宽 |
|---|---|---|---|---|---|---|
| 200 | wedge | 25/14 | 364 | 16（cap） | **121.9px** | 0.19 |
| 40 | wedge | 9/6 | 156 | 16（cap） | 121.9px | 0.52 |
| **20** | wedge | 6/4 | 104 | 14 | **105.6px** | 0.68 |
| **8** | wedge | 3/2 | 52 | **7** | **48.8px** | 0.63 |
| **4** | wedge | 2/1 | 26 | **4** | **24.4px** | 0.47 |
| 12 | line | 5/1 | 26 | 4 | 24.4px | 0.19 |

⇒ 小队厚度 **24~49px**，而队间**档距 130.7px** —— 一支几十 px 厚的薄片，被放到与母队相距
**131px** 的档上 ⇒ **"一个平面的一层，漂浮在最上面"** ✔ 描述与数字完全吻合。

### 4.2 两个独立成因

1. **薄**：`layerCountForFootprint()` 按**该队自身平面足迹**推导层数。
   这是用户此前明确要过的（"小队不要成竖直的针"），本身没错；
   但对**分舰队**场景产生了"从大队里削掉一层"的观感。
2. **浮在最上档 + 母队同时跳档**：档位 = `tierIndexOf(数组序号, tiers)`，即 `index % tiers`：

```
 1 队 → tiers=1  各队 tierY = 0
 2 队 → tiers=2  各队 tierY = -65, +65            ← 母队
 3 队 → tiers=3  各队 tierY = -131, 0, +131        ← 分兵后：分舰队拿到 +131（最上档）
 4 队 → tiers=3  各队 tierY = -131, 0, +131, -131
```

- 分舰队被 push 到数组末尾 ⇒ 序号大 ⇒ **落到最上档**（+131px）✔
- 更糟：舰队数 2→3 会让 `tiers` 从 2 变 3 ⇒ **所有队**的档位重算
  ⇒ **母队从 +65 跳到 0**（下沉 65px）、另一队从 −65 跳到 −131（下沉 66px）
  ⇒ 这就是你说的「舰队会先经过一些**大范围的变化**」的**一部分来源**（此前只归因于阵位重排）。

### 4.3 建议修法（下一批次，未实施）

| 目标 | 做法 |
|---|---|
| 母队不跳档 | 档位改为按**舰队身份**而非数组序号：舰队首次出现时分配一个持久 `_tierSlot`，之后**保持不变**；tiers 变化时只做 `min(_tierSlot, tiers-1)` 的钳制 |
| 分舰队不"浮在天上" | 分舰队**继承母队档位**（它们是同一支部队的分队），而不是另占新档 |
| 分舰队不"薄成一片" | 分舰队厚度设**下限 = 母队厚度 × 0.6**（或直接继承母队 `layerGap` 与层数），避免"被削掉一层" |

**为何本轮不做**：这是一次**3D 层/档系统**的改动，与转向运动学（本批）无耦合但会动到
`__b3dVLayout` 的既有判据体系，按本仓"一批次一交付、可独立验证"的纪律应单独成批。
