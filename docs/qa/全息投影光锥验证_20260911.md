## A. 渲染正确性

### A1 shader 能编译通过 —— PASS【实测 + 静态】
- 【实测】锥体 shader 程序已链接：`programs=1, diagnostics=[]`；`glError=0`；整页无 GLSL/`THREE.WebGLProgram` 报错。光池 shader 单独渲染出 **29730** 个非背景像素，证明其亦编译成功。
- 【实测】连续 3 轮复跑，均为 12 PASS / 0 FAIL（排除 SwiftShader 首轮编译竞态假警报）。
- 【静态】`pow()` 底数为负的未定义行为**不存在**：
  - `pow(1.0 - h, 1.5)`：`h = clamp(vY/max(0.001,uH) + 0.5, 0.0, 1.0)` → `1.0-h ∈ [0,1]`，非负。
  - `pow(clamp(1.0 - d, 0.0, 1.0), 2.2)`：先 clamp 到 `[0,1]` 再取幂，非负。
  - 结论：两处 `pow` 均被 clamp 兜住，**判定安全**。

## B. 回归检查

### B1 资源释放 / 无泄漏 —— PASS【静态】
- 清理段（L1080–L1087）：`holoPillars.forEach(grp => grp.traverse(o => { if (o instanceof Mesh) { o.geometry.dispose(); o.material.dispose(); } }))`。三件子对象（锥/环/光池）均为 `Mesh`，**geometry + material 全部被 dispose**。环材质（`MeshBasicMaterial`）虽未进 `holoProjMats`，但同样被 traverse 释放，无遗漏。
- **`holoProjMats = []` 在 L1087 被重置**（且位于 `buildNodes()` 循环之前、无条件执行）→ 重复调用 `buildNodes` **不会**导致数组无限增长，也不会把 `uTime` 写到已 dispose 的材质上。
- `holoPillars` 类型由旧 `Map<number, THREE.Mesh>` 改为 `Map<number, THREE.Group>`（L271）；全文件仅 L1080/1086/1230 三处使用，无其它消费者仍按 Mesh 使用 → 类型改动无副作用。

### B2 每帧 / 每节点成本 —— 数据【实测 + 静态】
- 地图实际节点数：**59**（`mapTopologyData.ts`：首都 3 / 要塞 2 / 空节点 4 / 普通 50）。
- 单节点新增：**3 个 Mesh**（锥 `ShaderMaterial` + 环 `MeshBasicMaterial` + 光池 `ShaderMaterial`）、3 个 geometry、3 个 material。
- 全图新增：**177 mesh / 177 geometry / 177 material**（场景遍历实测 `sceneMeshes = 177`）。
- **新增 draw call：实测 236**（仅含投影的隔离场景 `renderer.info.render.calls`，= 59 × 4）；triangles **11328**。逐件归因（实测）：锥 1 趟、**环 2 趟**、光池 1 趟。
  - 环为 2 趟的原因：THREE r160 对「`transparent && side===DoubleSide && !forceSinglePass`」材质分**背面/正面两趟**绘制（`three/build/three.module.js` L29963）。`ShaderMaterial` 默认 `forceSinglePass=true`（实测材质属性），故锥/光池各 1 趟。→ **236 为精确值，非估算。**
- **每帧 uniform 写入：118 次**（`holoProjMats` = 59 节点 × 2 个 ShaderMaterial；L2172 每帧 `for (const m of this.holoProjMats) m.uniforms.uTime.value = t`）。
- 判读：+236 draw call 相对本项目既有场景（星球/航线/板块/后处理）属**可观但不致命**的量级；若要优化，可考虑环形光环改用 `forceSinglePass` 或改为 shader 内的环（可省约 59 次 draw call），或对小星球（radius≤0.5）做合批/LOD。**是否可接受请主程按目标机型裁决。**

### B3 显示模式行为不变 —— PASS【静态】
- `setDisplayMode()`（L642–646）与 `updateHoloBoardAnchors()`（L650–653）**只操作 `holoBeams`**（CSS 悬浮板的细线光柱），**从不引用 `holoPillars`/`holoProjMats`**。
- 对照 HEAD（改动前）：旧 `holoPillars` 同样不被 `setDisplayMode` 触碰（旧代码仅在 buildNodes 清理与写入处引用）。
- 结论：新旧投影在 `'universe'` 与 `'holo'` 两种模式下**行为完全一致**（均始终显示），**未引入「某模式下凭空多出/少了投影」的变化**。

### B4 图层/排序（不遮星球、无 z-fighting）—— PASS【静态推理】
- 光锥 `AdditiveBlending + depthWrite:false`；星球大陆球材质亦为 `AdditiveBlending + depthWrite:false`；阵营辉光 Sprite 亦 additive。
- 加法混合满足交换律（`dst = src·a + dst`），**与绘制顺序无关**；且加法只能提亮、不能遮盖 → 光锥**不可能把星球盖住看不见**。
- 双方 `depthWrite:false` → 互不写深度，**不产生 z-fighting 闪烁**。
- 唯一细微点（非缺陷）：云层 `MeshPhongMaterial`（`opacity 0.25`，普通混合、`depthWrite:false`）与光锥在星球局部重叠时，理论上可能对光锥有极轻微的调暗；因云层半径 `radius*1.02` 远小于锥口半径 `radius*1.30`，影响区很小，实际观感可忽略。
