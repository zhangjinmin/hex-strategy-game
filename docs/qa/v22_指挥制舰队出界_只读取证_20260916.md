## 0. 结论（一句话）

**「地图」在这套实现里只是 3D 层的一块装饰性扫描网格，没有任何坐标系语义；而出生点写入用的是「上一局残留 / 字段初值」的 `commandSpawnDist`（3150），且只有"真正持有城堡地块"的阵营才会被正确覆写 ⇒ 拿不到城堡地块的阵营，其城堡/出生点被放在 `x = ±3150`，而当局平面半跨只有 1792 ⇒ 直接落在网格外 2.27 格。**

出界有两条独立路径，视觉症状相同：

| 路径 | 机制 | 实测越界量（random_large，planeHalf=1792.7，主格=597.6） |
|---|---|---|
| **A. 出生点用了过期/初值口径**（主因） | 见 §2 链路 | `x = ±3150` ⇒ 超出 **1357 = 2.27 格** |
| **B. 同方多舰队错开与地图尺寸脱钩** | `dy = (i−(n−1)/2)×gap`，gap 只按本队阵型足迹 | y = **+2918 / −2017** ⇒ 超出 **1125 = 1.88 格** / **225 = 0.38 格** |

## 1. 现场判读：那张截图是什么场景

- **场景 = 指挥制（`mapStyle === 'command'`）+ 3D 覆盖层**。
  - 绿色方格网 = `Battle3DOverlay.buildSpaceWorld()` 的 `GridHelper`（细格 `0x117a55` α0.20 / 主线 `0x1fd28f` α0.45；`planeSize = span×1.15`，主线 **6 格**）。
  - 橙色辐条盘 = 同函数 5 个"引力异常"线框圆柱（`CylinderGeometry(…,14,3)` wireframe，正俯视即辐条状）。
  - 舰队头顶标签 = `updateBillboards()` 的 DOM（名字=`fac.name`，副行=`fleetIntentText` 含 `[PLAN_ROLE_LABEL]` 前缀）。
  - 判定依据：`spaceMode = tacticalState.mapStyle === 'command' || scene.mapStyle === 'command'`（`Battle3DOverlay.ts:1349`）。
- 演习轨道**默认**就是指挥制：`launchSimBattle(mapStyle = 'command')`（`gameStore.ts:654`）。

## 2. 主因链路（逐行可核，全部命中）

```
create()                                    BattleScene.ts
 244  scaleMapForFleetCount()                → hexRadius = 50（Σ实体 336）
 304  initFactions()                         → store.factions 重建，castlePos 先置 {0,0}
 305  buildMapData()
       ├─ … 生成矩阵 …
       ├─ 3420-3465  forEach(factions)      ← 每个阵营抽一个出生节点
       │      3448-3452 if (command) f.castlePos = { x: ∓commandSpawnDist,
       │                                              y: rand×commandHalfX×0.4 }
       │            ⚠ 此刻 commandSpawnDist/commandHalfX 仍是**字段初值 3150 / 3000**
       │            （computeCommandSpawnExtent 在本函数**最后一行**才调用）
       ├─ 3454-3463  dist<=2 光环：t.ownerId = f.id   ← ★ 会把邻近阵营的 castle tile 抢走
       └─ 3496  computeCommandSpawnExtent(matrix)   → 才把 half=2000 / dist=2100 写回
 306-317  forEach(matrix, type==='castle')   → fac.castlePos = 该地块坐标（**修正** BS:3449-3452）
 319-335  兜底：仅当 castlePos 缺失或 (0,0)     → 用 commandSpawnDist 重写
 380  spawnInitialFleets() → applyFleetDeploySpacing()
```

两处关键缺陷：

1. **时序错**：`computeCommandSpawnExtent()`（`BS:188-194`，唯一调用点 `BS:3496`）与它供数的 castlePos 赋值（`BS:3451`）**在同一个函数里，赋值在前**。⇒ 写进 castlePos 的是 3000×1.05 = **3150**（首战=字段初值；后续战斗=**上一局残留值**，跨局不可预测）。
2. **覆写不是全覆盖**：`BS:306-317` 只按"地块 ownerId → faction"反推著色，只要某阵营名下**没有 castle 地块**，就永远拿不到修正 ⇒ 停在 ±3150。
   - 而"名下没有 castle 地块"由 `BS:3454-3463` 的 `dist<=2` 光环造成：后处理的阵营会把**先前阵营城堡地块的 ownerId 改成自己**。

### 2.1 台架实测（random_large / 8 我方 + 3 敌方 / hexR=50）

```
commandHalfX = 2000    commandSpawnDist = 2100    overlaySpan = 3117.7
planeSize = 3585.3     planeHalf = 1792.7         主线格 = 597.6

castleTiles（终态矩阵里 type==='castle' 的地块归属）
  owner 113  ×3  (-1212,300) (-1212,0) (-1126,150)   ← 独占 3 块（抢了队友的）
  owner 10083×2  (779,-750) (779,-900)
  owner 110/111/103/102/101/10065 ×1 ...
factionsWithoutCastleTile（名下 0 块）
  106 伍兰夫舰队   castlePos.x = -3150   y = -116
  112 阮文绍舰队   castlePos.x = -3150   y = -250
  10018 克拉杰舰队 castlePos.x = +3150   y = -307

```

**相关性完全吻合**：`factionsWithoutCastleTile` ⟺ `castlePos = ±3150` ⟺ 出界。
（6v3 复跑同样命中：「卡尔先舰队」castlePos = (−3150, 567.36)；567.36 = 0.189×3000，正是初值 `commandHalfX=3000` 的口径，铁证。）

### 2.2 路径 B：错开位移（同方多舰队）

`applyFleetDeploySpacing()`（`BS:1277-1301`，演习）/ `deploySide` 的 dy（`BS:1026-1042`，战役）：
`gap = max(160, (2·halfSpan+1)×spacing×1.35)`（`deployGapFor`，`BS:1153-1159`）**只由本队阵型足迹决定，与地图尺寸无关**；`dy = (i−(n−1)/2)×gap` 直接加在 castlePos.y 上。

实测（random_large 6v3，n=6，gap=837 → 理论 ±2093）：

```
阿普顿   y = -2017  → 超 0.38 格
卡介伦   y = +2918  → 超 1.88 格   （castlePos.y=825 + dy≈2093）
```

即：**舰队数 × 阵型足迹任一变大，最外侧舰队必然被推出网格**（地图不随舰队数连续扩容，`scaleMapForFleetCount` 只给 26/32/38/44/50 五档）。

## 3. 结构性成因（为什么"迟早会出界"）

1. **平面是正方形**：`planeSize = max(xSpan, ySpan, hexR×20) × 1.15`（`Battle3DOverlay.ts:2080`）⇒ 长条图（`standard` 61×29：xSpan 6408 / ySpan 2100）纵向留大片空地、横向只余 9%；小图（`random_large`：span 3118）纵向余量被 castlePos.y(±1050) + dy(±2093) 直接吃穿。
2. **全仓没有"地图边界"这一概念**：
   - 逐帧坐标写入只有 `BS:4579-4580`（`fleet.x += rawVX; fleet.y += rawVY`），**无任何钳制**；
   - 出生点 3 处（`BS:324 / 3450 / 1018 / 2166`）只按公式算，不与平面联动；
   - 信标/`hold_point` 目标、`castlePos` 撤离点均可落在平面外 ⇒ **就算出生在里面，开战后也会合法地开出去**。
3. **战役轨道更严重**：`computeCommandSpawnExtent` 只在 `buildMapData` 里调用，而**战役轨道从不调用 `buildMapData`**（走 `buildCampaignEnvironment` 自建矩阵）⇒ 战役 + 指挥制下 `commandSpawnDist` 恒为初值 3150，而战役通用图（radius 6）的平面半跨仅 ≈600 ⇒ 出生/补给源/撤离点在平面外约 **5.3 倍**。

## 4. 修复建议（按性价比排序，均未实施）

| # | 改动 | 说明 | 风险 |
|---|---|---|---|
| 1 | **`computeCommandSpawnExtent` 调用提到 `buildMapData` 开头**（矩阵生成后立刻算） | 一行搬家，直接灭掉 ±3150 的初值/残留 | 无（仅影响正确性） |
| 2 | **战役轨道补调一次 `computeCommandSpawnExtent(campaignMatrix)`** | 放在 `buildCampaignEnvironment` 建矩阵之后 | 无 |
| 3 | **出生点改为"数据出口"而非"扫描反推"**：让 `buildMapData` 返回 `assignedNodeByFaction`，`create()` 直接用它写 castlePos，删掉 `BS:306-317` 的 ownerId 反推 | 根治"抢地块 ⇒ 丢修正"；同时让 `dist<=2` 不再改写 ownerId（只做区域归属的视觉） | 中：会改变双方出生分布（当前是"散在各自城堡点位"），需真机确认观感 |
| 4 | **错开自适应压缩**：`gap ← min(gap, 2×可用半场/(n−1))`，可用半场由 `mapBounds` 与城堡自身 y 余量给 | n 大时自动压缩而非出界 | 低 |
| 5 | **位移/目标钳制**（建议先做"目标点钳制"而非"位置硬钳制"） | `_missionDest`/信标点先夹到 `mapBounds`，舰队自然不出界 | 中：可能改变 AI 绕后/包抄路径，需真机回归 |

配套：把"平面尺寸"提为单一真源 `mapBounds`（`BattleScene` 算、`Battle3DOverlay` 读），消除现在 overlay 自己从 `tilesList` 再算一遍的分叉。
