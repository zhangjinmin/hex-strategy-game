## 1. 被验机制（从源码客观读取，非实现方自述）

脚本在开跑前**正则解析**生产源码，得到判定所需的全部阈值真值：

| 常量 | 值 | 出处 |
|---|---|---|
| `DOT_N` | **1** | `Battle3DOverlay.ts:527` |
| `MAX_MESHES` | **400** | `:498` |
| `DOT_SLOTS` | `N_MAX * DOT_N`（运行时 = **1400**） | `:574`（`DOT_CAP = DOT_SLOTS`，`:3206`） |
| `DOT_PITCH_MIN_PX` | **3.2** | `:556`（屏幕空间点阵最小点距） |
| `DOT_DIAM_K` | **0.85**（点径/点距 < 1 ⇒ 有间隙） | `:558` |
| `DOT_MIN_PX` | `= DOT_PITCH_MIN_PX × DOT_DIAM_K = 2.72`（派生） | `:565` |
| `DOT_IN_LO / DOT_IN_HI` | 3.2 / 5.0 | `:464-465` |
| `MESH_KEEP / MESH_IN_HI` | 17 / 26 | `:480 / :473` |
| `N_MAX` | **1400**（运行时由 `dotCapSlots` 反证） | `config/shipScaling.ts:130` |

**现行写入规格（`writeDotLayers`，`:3204`）**：
1. 遍历全部 `unitVis`，按**屏幕坐标**分格：`cellKey = floor(sx / DOT_PITCH_MIN_PX) + ',' + floor(sy / DOT_PITCH_MIN_PX)`；
2. 每格只留 1 个**胜出者**（优先级：已持 3D 实体 > px 大 > key 字典序小）；
3. 第二遍只给每格胜出者写点，**alpha 有下限** `a = (1−grow) × (0.78 + 0.22·sstep(3.2,5.0,px))` ⇒ 只要该格胜出者"未长实"，**必有可见点**（**不存在** alpha 被距离打到 0 的分支）。

> **这就是两条核心诉求的机制来源**：远景"并格"⇒ 点距恒 ≥ `DOT_PITCH_MIN_PX`（不糊成块、也不空白）；近景"一格一舰"⇒ 自然退化为"1 舰 1 点"（看得见的点组成阵型）。

## 2. 验证方法：三路独立证据 + 判据推导

台架走**真实演习入口**（`enterSimMode()` → `simSelectedAdmirals` → `launchSimBattle('3d')`），
无头 Chromium + SwiftShader，视口 1600×900 @DPR1。每档用 `__b3dFocus({fleetIndex:0, dist:D})` 取景，
每档拍 **5 帧**：`nothingA`/`nothingB`（全隐藏，测背景噪声地板）、`dots_only`（只留光点层）、`marks_only`（只留标记层）、`full`（全开）。
战区裁剪框 = 屏幕中央 60%×60%（960×540；取景把目标放在视野中心，故中央即战区）。

### (a) 覆盖完整性 / 隐形洞 —— 判据推导

**朴素判据是错的（必读）**：直觉写 `meshes + points >= unitCount`。**该式在原理上就不成立**，原因有二：
1. `meshes` 是**全场**实体数，而 `points` 只在**每格胜出者**上累加；两者属**不同格**，直接相加会**重复计数**；
2. 正确口径是对**格**做账，而不是对**舰**。

**正确判据（三条并列）**：
- **(a1)** `drawRange == 期望点数`：期望点数由**我按源码规格独立重算**——用 `unitVis` 的屏幕坐标自行分格、自行选胜出者、自行套 alpha 公式（去均值沉降见脚本 `recount`）。两路实现**逐位相等** ⇒ 实现无隐藏分支、无越界丢弃。
- **(a2)** `drawRange < DOT_SLOTS`：槽位上限**未触顶** ⇒ 没有一艘因缓冲不足被截断。
- **(a3)** `dots + meshOnlyCells == distinctCells`：每个被占屏幕格，要么出点（`dots`），要么其胜出者是**已长实的实体**因而不出点（`meshOnlyCells`）。两者之和应恰好等于总格数 —— 这是**格级**的"无遗漏"证明。

### (b) 远景看得见 —— 判据推导

**为什么不能用"绝对亮度阈值"**：空域里有星点、地形网格、标记底框，全都会产生亮像素；绝对阈值会把它们当光点。
**Δ 法**：点掩膜 = `lum(dots_only) − lum(nothingA) ≥ 16` 的像素（只有光点层被单独打开才会新增的亮度）。
- 噪声地板由 `nothingA vs nothingB`（两帧相同内容）估计；
- 判据 `dotPixels > 0`（远景档，D≥3000 或离域档）——即"拉远后光点层**没有**整层变 0"。

### (c) 点阵不糊成块 —— 判据推导

对 (b) 的点掩膜做 **8 邻接连通域**（flood fill，最小亮斑 4px 剔除星点噪声）：
- `blobCount ≥ 10`（**远多于 1 块** ⇒ 是"分离的点"而非"一整块实心色斑"）；
- `largestBlobShare ≤ 0.5`（最大亮斑占总亮面积不到一半 ⇒ 没有主导性大色块）。
- 阈值理由：用户第 3 轮投诉是"一个个方块"。若糊成实心块，`largestBlobShare` 会趋近 1 且 `blobCount` 跌到个位；反之分离点阵 `blobCount` 高、`share` 低。

## 5. 逐项判定

### (a) 覆盖完整性 / 隐形洞 → **PASS**
- (a1) `drawRange == 独立重算期望点`：**10/10 档逐位相等**（693/745/809/877/875/739/735/223/87/36）。
- (a2) `drawRange < DOT_SLOTS(1400)`：**10/10 档 PASS**，最大值 877。⇒ 缓冲不再被 `MAX_MESHES(400)` 卡死。
- (a3) `dots + meshOnlyCells == distinctCells`：**10/10 档 PASS**（见 §4.3）。
- 对账：`unitVis = 920` = 场景逐队 `hp>0 && sprite` 之和 = 920（**独立**取自 `BattleScene.globalFleets`，非 overlay 自报）。
- **结论**：在提交版本上，**不存在**"既无实体也无光点"的隐形洞。

### (b) 远景看得见 → **PASS**
- 判据：远景档（D ≥ 3000 及全部离域档）隔离光点像素 > 0。
- 实测：**10/10 档全部 > 0**（最小 = 60000 档 `148 px`）。远景档噪声地板 p99 = 10~11，`deltaGe16 = 1476~1823`（3000/6000/7560 档）**远高于噪声**。
- **目视旁证**（我逐张打开确认）：`d800_full.png` 可见**数百个分离圆点组成楔形阵**；`d3000_full.png` 楔形标记内可见成片光点。⇒ 远景**不是**只剩一块空标记底板。
- 判据边界：**用户可达最大视距 = 实际 7560**（`controls.maxDistance = 7560.06`）。该视距下 `dotPixels = 1526 > 0`。
- **结论**：**"拉远后光点整层消失"（H2）在提交版本上不成立。**

### (c) 点阵不糊成块 → **PASS**，唯 60000 档 **CONCERNS**
- 用户可达域（200~7560）：`blobCount` 101~322（≫ 1），`largestBlobShare` 0.042~0.245（≤ 0.5）⇒ **分离点阵**，未糊成块。
- 离域档 15000/30000：`blobs` 42/19，`share` 0.228/0.171 ⇒ 仍达标。
- 离域档 **60000：`blobs=8 < 10`**（`share=0.203`）⇒ **FAIL**。
- **此 FAIL 判为 CONCERNS**：60000 是**用户不可达**的离域档（用户在 `maxDistance` 下最多 ~7560），该档全场仅 36 个并格点、单点已缩到亚像素，`blobCount` 低是"点太少"而非"糊成块"（`share` 仍 0.2，没有主导大色块）。**不与 200~12000 的 PASS 混为一谈**，登记为"离域、暂不修"。

### (d) 点阵对全场的几何覆盖 → **PASS**（覆盖 85.7%~100%，缺口定量归因）
- `dotCoverage = dots / distinctCells`：近景 **0.857~0.929**，`≥1500` 档 **0.998~1.000**。
- 近景那 7%~14% 的"无点格" = `meshOnlyCells`（其格胜出者已获**完全长实**的 3D 实体，按规格**故意不写点**）——
  这些舰**由 3D 实体表达**，不是洞（已由 (a3) 的格级账本封口）。
- 按 `px` 分档（team-lead 给的判据）：`px` 落到 `DOT_IN_LO(3.2)` 附近或更小时，`dotCoverage = 1.000`（3000 档起全部 1.000 ✓）；
  `px` 明显更大（近景实体档）时 `coverage < 1`（0.857~0.929）——**属预期**，缺口正是实体接管的部分。
- **结论**：光点阵对全场的覆盖**完整**，近景的部分覆盖是"实体接管"这一设计使然。

### (e) 点/格随距离的单调性 → **CONCERNS**（非缺陷；**修正判据**）
- **数列非单调**：`points` 为 693→745→809→877→875→739→735→223→87→36，**200→1500 段递增**，之后递减。
- **递增段的机理解释（良性）**：
  · **网格↔点交接**：近景许多格由**实体胜出**（`meshOnlyCells`：116→115→62→2→0→0…），这些格**不写点**；
    拉远后实体减少 ⇒ 更多格轮到写点 ⇒ 点数上升（693→877）。
  · **屏幕面积缩放**：单位在屏上的铺开面积 ∝ `refPx²`；`refPx` 由 122.5 降到 0.408，`distinctCells` 从 809 涨到 879 后随并格回落。
- **正确判据（替换"单调不增"）**：**无"非解释性"尖峰** —— 相邻档的相对变化必须能由 (i) 网格/点交接 或 (ii) 屏幕面积缩放解释。
  按此口径，实测**无无法解释的尖峰**：递增段 = 交接主导，递减段 = 并格主导。⇒ **判据成立，无缺陷**。
- **结论**：`points` 非单调是**设计使然**（点/网格双层表示交接），**不是闪烁或跳变**；但因"单调不增"曾被当作判据，故标 **CONCERNS** 以引起注意。

### (g) 跨帧稳定性（闪点） → **PASS（真判据）；本节 Jaccard 判据系主理人误设，作废**　〔补测轮 v7〕

| D | drawRange min/max/mean | contestedMean | cellsMean | 候选集合不变的对数 | **其中胜出者改变** | flapFrames |
|---|---|---|---|---|---|---|
| 3000 | 854 / 867 / 861.03 | 23.19 | 861.03 | 70300 | **0** | 0/120 |
| 6000 | 752 / 791 / 775.02 | 89.42 | 775.02 | 87403 | **0** | 0/120 |

- **真判据（成立）**：**条件于"该格候选集合逐位相同"，胜出者改变次数 = 0 / 157703 帧-格对。**
  即源码的胜出规则**确实是跨帧确定的**（`(hasMesh, px, key)` 三元组只依赖当帧状态，无隐藏随机/时序依赖）——
  这正是"不闪烁"的充分条件。⇒ **(g) PASS。**
- **`drawRange` 逐帧 854~867（D=3000）、752~791（D=6000），无零帧、无触顶**（`DOT_SLOTS=1400`）。⇒ PASS。
- **本节的 `winnerKeyJaccard ≥ 0.98` 判据作废（主理人误设）**：实测 mean 0.5214（D=3000）/ 0.9441（D=6000），
  `min` 分别为 0.4692 / 0.9110。**但该判据测的是"屏幕格集合的帧间留存率"，而演习中单位本身在持续移动**
  （`contestedMean` 23→89 说明并格程度随视距上升），格键churn 是**舰船运动的必然结果，不是闪烁**。
  这与 §5(e)"单调不增"是**同一类错误**（把运动/交接的良性变化误判为缺陷）。
- **为何"胜出者改变"也不是闪烁（有界性论证）**：胜出者只会在**同一格内**（边长 3.2px）易主，
  故任何一次易主造成的点位置跳变 **≤ 格对角线 ≈ √2 × 3.2 ≈ 4.5px**，且新旧点在同一格内 ⇒ 视觉上无闪光感。
  这条**上界**是 `DOT_PITCH_MIN_PX` 分格机制的固有性质。
