# v34c 分舰队「一片平面 + 浮在最上层」定位与修复（2026-09-20）

> **触发**：用户实机截图（2026-09-20）——
> 「这个分出来的舰队是个平面 … 相当于在原来箭头上削掉一层，然后一个平面的出去。
> 原舰队是个立体的三维的、有层层叠叠的状态，然后分出来的舰队是一个平面的一层，
> 然后还漂浮在最上面一层，这种状态反正很诡异。」
> **方法**：L2 无头浏览器运行时取证（`_probe_split.mjs`）→ 修正假设 → 改档位分配 → 台架 + L2 复测。
> **结论**：**"薄"不成立（数据推翻）；"浮在最上档"成立且已修**。分舰队与母队档位落差
> **129.7px → 0.0px**。

## 1. 先把两条假设分开，再取证

上一轮（v34b 报告）我给的静态量化结论是「小队 4~7 层 / 厚 24~49px ⇒ 读作薄片浮在天上」。
那是**在台架里用 `spacing = 26` 手算的**——而真实 `spacing` 由 `formationSpacing(offs, hexR)`
给出（实测 8~10.6），且 `layerCountForFootprint` 是 `1 + minSpan/layerGap` 的形式
⇒ **我上一轮的薄厚估算从前提上就是错的**。用 L2 打进真实战场重取：

### 1.2 假设判定

| # | 假设 | 判定 | 依据 |
|---|---|---|---|
| **S1** | 分舰队**薄**（层数/厚度远小于母队） | ❌ **推翻** | **实用层位 = 16 / 16（满层）**，厚 **121.9px**，比母队（106.0px）**还厚 15%**。厚度比 1.15 |
| **S2** | 分舰队**浮在最上档** | ✅ **成立** | 母子档位 **−64.8 vs +64.8**，落差 **129.7px = 16.0 个层距**；两队各自只有 ~110px 厚，中间还空 15.7px |
| **S3** | 一次分兵让**母队下沉** | ✅ **成立** | 档数按**舰队对象总数**算：分兵把 1 队变 2 队 ⇒ `tiers 1→2` ⇒ 母队从 `0` 变 `−64.8`（**下沉 64.8px**），分舰队出现在 `+64.8` |

**S1 之所以读起来"像一层"**（我的判断，非实证）：分舰队 79 舰铺在 16 层上 ⇒
**4.9 舰/层**，而母队是 12.5 舰/层 ⇒ 同厚度下**层内密度低 2.5 倍**，加上俯角透视压缩，
观感是"稀疏的一排"而不是"实心的一块"。**这条属观感判断，需要人眼定**（见 §5）。

## 2. 根因：两条都在**档位分配**上，与层数无关

`fleetTierLayout.tierIndexOf(index, tiers) = index % tiers`，配合 `tierOffsetOf` 的**居中对称**档位
`[−(T−1)/2 … +(T−1)/2]`：

- ① **分舰队被 push 到 `globalFleets` 末尾**（`BattleScene.splitFleet` `:3481`），
  与该方母队**序号相邻**；而在对称档位下"相邻序号"恰好落在**两端** ⇒ 分舰队必然跑到母队的**最远端**。
- ② **档数按"舰队对象总数"计**（`tierCountFor(list.length)`）⇒ 分兵改变对象数 ⇒
  **档数与所有根舰队的档位一起重算**（母队凭空下沉）。这是"分兵瞬间整场舰队先大范围变化"
  的一部分来源——此前一直被归因于阵位重排（v31-D / v34 那条线）。

> 第一性原理：**档位是"编制身份"的属性，不是运行时数组位置的属性**。
> 数组序号是偶然的（谁先被 push），血缘才是稳定的。

## 3. 修复

### 3.1 代码（3 个文件）

| 文件 | 改动 |
|---|---|
| `config/fleetTierLayout.ts` | 新增 `rootFleetOf()`（沿 `_detachedFrom` 回溯到根，防环）、`assignFleetTiers()`（逐队档位 Y 的**单一真源**）、常量 `DETACHED_TIER_OFFSET` |
| `game/three/Battle3DOverlay.ts` | `syncShips` 第零遍与 `__b3dVLayout` **两处重复实现收口**到 `assignFleetTiers`（此前各抄一份 ⇒ 探针读数与实际渲染有静默分叉的风险） |

规则：
1. 档数 = `tierCountFor(根舰队数)`（根 = 无 `_detachedFrom`）⇒ **分兵不改变根数 ⇒ 档位恒定**。
2. 根舰队按**根内序号** round-robin 取居中对称档（原设计不变）。
3. 分舰队**继承其母队的档位**（多级拆分沿链回溯）。
4. 链条断裂（母队已全灭）⇒ 退回第 0 档，不悬空、不 NaN。

## 4. 必须说清的取舍：同档的代价

**同档后两队纵向完全重合，分离只剩平面间距。** 实测：

```
同方两队平面间距        = 198~199px（= DETACH_SPACING 200 + 机动偏移）
两支足迹"不重叠"所需间距 = 母队 300/2 + 分舰队 208/2 = 254px
⇒ 边缘约 55px 的水平交错
```

三个选项的量化对比：

| 方案 | 母队↔分舰队纵向差 | 后果 |
|---|---|---|
| **同档（本轮默认，`DETACHED_TIER_OFFSET = 0`）** | 0px | 纵向完全重合；平面边缘交错 ~55px。读作"母队里分出来的一块、在同一层空间并排" |
| 错开 0.5 档 | 65px | ⚠ **最差**：半厚之和 114px ⇒ 纵向重叠 ~49px **且**纵向又不重合 ⇒ 既糊又飘 |
| 错开 1 档（= v34b 及以前的行为） | 130px | 完全不互穿，但**这就是用户实报的"漂浮在最上面一层"** |

**0 与 1 之间没有观感更好的中间档**——这不是偏好问题，是几何：
不互穿要求错位 ≥ `(106/2 + 121.9/2) / 130 = 0.88` 档。

⇒ 若要回到"错开一档"，把 `balance` 之外的这个常量改成 `1` 即可（`fleetTierLayout.DETACHED_TIER_OFFSET`），
不必回滚代码；台架已断言 `offset=1` 与 v34b 行为等价。

**另一个缓解因素**：分舰队的战法（实测「右翼迂回」）会主动横向拉开距离，
所以平面交错主要出现在**分兵瞬间**，随后自然分离。

## 5. 未做 / 必须真机确认

1. **"边缘 55px 水平交错"是否可接受** —— 这是本轮唯一未经人眼验证的点。L2 无头 3fps +
   SwiftShader 的渲染质量不足以判断"读得顺不顺"。可选处置见 §4。
2. **"稀疏感"（S1 的观感部分）** —— 数据显示分舰队**不比母队薄**，但 4.9 舰/层 vs 12.5 舰/层
   的密度差是客观的。**是否要给分舰队单独降层数**（既有的 `layerCountForFootprint`
   本来就是"按足迹收缩"，只是 79 舰的足迹已足够大到撞 `TEAM_LAYERS=16` 的上限）
   —— 这需要先确认"稀疏"确实碍眼，否则会撞上"竖直的针"那条历史缺陷（`thin` 比值 0.5~0.6，
   仍在健康区）。
3. **真实战役模式**（本轮全部取证在**演习模式**）—— 演习与战役的舰队规模/布阵不同，
   档位逻辑与模式无关，但值得在战役里扫一眼。

## 6. 顺带发现（本轮未改，仅记录）

1. **`layerGapFor` 的比例项实际上从未生效**：`0.3125 × spacing` 与几何下限 `1.2 × maxShipH`
   比较，实测 `spacing ≈ 8~10.6` ⇒ 比例项 2.5~3.3，而下限 = `1.2 × 5.89` = **7.07**
   ⇒ **永远是几何下限胜出**（比例项要胜出需 `spacingEff > 22.6`，而 `formationSpacing` 对任何阵型都给不到）。
   `teamGapFor` 同理恒由**厚度项**决定。⚠ `fleetTierLayout.ts` 文件头原注释写着"缩舰后比例项胜出"
   —— 那是缩舰前按 `spacing = 26`（名义值）推导的，**与实测相反**。本轮的定位本就是"手抄常数推导"造成的，
   **已一并订正该文件的两处实算注释**（并注明 `LAYER_GAP_K` / `TIER_GAP_K` 在现行 scale 下是死参数）。
2. **`rootFleetOf` 的血缘真源 `_detachedFrom` 此前全项目零消费**（仅 `splitFleet` 写入）
   —— 本轮是它的第一个消费者。后续"分舰队继承母队属性"都可复用它。
3. **L2 探针的两个坑**（已写入记忆）：
   - `__b3dVLayout` / `__b3dMarkProbe` / `__b3dFocus` 挂在 **`window`** 上，
     **不是** `window.__b3dOverlay` 的实例属性（`Object.keys(overlay)` 里看不到）——
     读 `ov.__b3dVLayout` 会**静默拿到 `undefined`**，本探针首跑即因此只拿到一半数据。
   - 无头 + SwiftShader 下**连续多张全分辨率 PNG 会超 30s** ⇒ 报 `CDP 超时: Page.captureScreenshot`。
     `_browser_probe.screenshot()` 现已支持 `{ quality, timeoutMs }`（JPEG + 长超时）。
   - `__b3dFocus` 的 `elev` 是**俯角**：`0` = 正俯视（**看不出高度差**），`π/2 ≈ 1.57` = 水平侧视。
     判断"两队在不在同一高度"**必须**用 `elev ≈ 1.2`。
