# v39 · 地形改为等高线（否掉 v38 扫描线）+ 模型填充建议（2026-09-20）

> **用户反馈**：「这个太奇怪了，太整齐了，应该是随机的线条，现在这个状态就好像是单元格填充纹理…
> 就是太密集，还不如一开始的六边形格子好看，有没有更好的方式？或者我可以去找些模型填充」
> **结论**：v38 的扫描线**方向错了**（不是调参问题）。改为**等高线**，密度从 2.5× 提到 **118×**（间距/线宽）。

---

## 一、为什么 v38 是错的（第一性原理，不是审美口味）

**规则等距平行线只能编码"方向"，不编码"高度"。** 我把"起伏"交给扫描线承载是**符号错配** ——
无论怎么调间距/亮度，近景下它必然读作 hatch 纹理。用户判断准确。

**等高线天生就是高度的可视化**：每条线 = 一个高度层，线疏＝坡缓、线密＝坡陡、线弯曲＝地形起伏。
这是拓扑图 / 雷达回波的标准语言，与"指挥制 = 全息读数界面"同源。

| | v38 扫描线 | v39 等高线 |
|---|---|---|
| 线形 | 等距平行直线 ⇒ 纹理 | **随噪声弯曲的闭合曲线** ⇒ 地形 |
| 数量 | 每格 17 条 ⇒ 密集 | 全图 **5 条**高度层 ⇒ 疏朗 |
| 三维感 | 靠 y 位移（缩放下 ≈0.5 屏幕像素，不可见） | **每条线就是一个高度层** ⇒ 天然分层 |
| 边界 | hex 阶梯锯齿 | Chaikin 切角 ⇒ 有机轮廓 |

## 二、实现

### 新增 `frontend/src/config/terrainField.ts`（192 行，纯函数、无 THREE 依赖）

`hash2` / `valueNoise2D` / `fbm2D` / `contourLevels` / `marchingSquares` / `chaikin`

抽成独立模块的唯一理由：本项目铁律要求「台架必须 `require` 真源码」，而这些函数
**错了不会抛错** —— 噪声退化成常数、case 表错位、掩码失效，都只会让画面空白或变丑。

### 三层结构（缺一层都会出问题）

1. **区域外轮廓** —— 六边形格拼出的边界天生是"六边形锯齿"（近景读作像素化块）；
   `chaikin` 切角 2 次后读作有机空域轮廓。⚠ Chaikin 会**向心收缩 8.3%**（台架实测），
   故配 `OUTLINE_GROW = 1.035` 补偿。
2. **内部等高线** —— `marchingSquares` 带**掩码**（四角掩码全同才取线）
   ⇒ 自动内缩约一格，所以第 1 层是必需的，否则区域边界不可读。
3. **高度分层** —— 每条线的 y = `level × amp`（等高线的定义就是"等高"）。

### 关键实现决定

- **不做"世界坐标 → 轴坐标"的解析反变换**：那要押注 pointy-top 的间距/角度约定，
  押错会静默错位。改用**空间哈希求最近格中心** —— 对正六边形铺砌恒正确。
- **噪声必须归一化到 [-1,1]**：否则固定 level 数组会全挤在一侧，等高线只出现在半边。
- **`contourLevels` 偶数层时刻意不含 0**：0 层会把画面切成上下两块，读作"地图中线"而非地形。
- 高处线更亮（`LEVEL_BASE_MUL 0.55 → LEVEL_TOP_MUL 1.35`）⇒ 峰顶发光，读作高程。

### 参数（`balance.TERRAIN_CONTOUR`，全部以 hexR 为分母）

`GRID_K 0.40`（R=50、跨度 2000 ⇒ 100×100 网格）· `NOISE_CELL_K 9.0` · `OCTAVES 3` ·
`SEED 20260920` · **`LINES 5`**（"疏朗 vs 纹理化"的核心参数）· `HEIGHT_SPAN 0.85` ·
`HEIGHT_AMP_K 0.42` · `WIDTH_K 0.028` · `CHAIKIN_ITERS 2` · `OUTLINE_GROW 1.035` ·
`ALPHA_ENV 0.62` / `ALPHA_HAZARD 0.92`

**三种画法可 A/B 对比**（`TERRAIN_ZONE.MODE`）：`'contour'`（默认）/ `'scanline'`（v38）/ `'fill'`（v36c）。

### ⚠ 台架抓出的一个真 bug（静默型）

**marching squares 的底边 / 左边插值方向写反了**：

```
B：角2(c+1,r+1) → 角3(c,r+1)     ⇒ x = c + 1 − t     （初版误写成 c + t）
L：角3(c,r+1) → 角0(c,r)         ⇒ r = r + 1 − t     （初版误写成 r + t）
```

判据是**线性场**：`v = c/20` 在 `level=0.5` 的等值线必须是**竖直线 c=10**，
实际却输出 `(10,r) → (11,r+1)` 的**对角线**。
同时"段中点高度偏差"从 **0.059 → 0.004**（15 倍改善）印证了修正。

**判据设计教训**：能抓住这个 bug 的是「**端点必须精确在等值线上**」
（`|双线性值 − level| < 1e-9`，对方向错零容忍）；
而"段中点偏差 < 0.05"这种**容差型**判据抓不住（0.059 只算"稍微超一点"）。

### ⚠ 我自己写错的三处判据（记录以免复发）

1. **拿"顶点数"当密度**：两种画法每段都是 6 顶点，但等高线段长 ≈20px、扫描线段长 ≈100px
   ⇒ 顶点数与密度无关。正解 = **线长/面积 ⇒ 平均间距**。
2. **拿"条数"比密度**：等高线是贯通的长 iso-line，v38 是逐扫描行的短 span ⇒ 苹果比橘子。
3. `Math.min` 初值给 0（上一轮已记）。

## 四、模型填充：我的建议（不替代等高线，而是叠加）

**等高线给"地形"语义，模型给"实体感"。** 建议只给**需要实体感的两类**配模型，其余保持线条：

| 地形 | 建议模型 | 理由 |
|---|---|---|
| 小行星带 `asteroid` | **2~4 种小行星岩块**（低模、可分块） | 实体感收益最大；用 `InstancedMesh` 撒 60~120 颗，y 取等高线高度 |
| 残骸区 `debris` | **舰船残骸 / 碎片板** | 与"战场遗迹"叙事一致 |
| 星云 `nebula` | **体积雾片（billboard 贴图）**，不要实体网格 | 星云是"云"，实体模型会变"棉花糖" |
| 引力点 `gravity` | **保留纯线条 + 一个涡旋环** | 引力是"场"，不是"物" |
| 机雷区 / 粒子云 | **保留线条**（危险靠"更密更亮"已可读） | 加了反而干扰"危险区要躲"的判读 |

⚠ 关键约束：**模型的位置必须复用同一份高度场**（`fbm2D`）作为 y，
否则模型会浮在等高线之上/之下、两者语义脱节。
⚠ 每类只加 **1~2 个 draw call**（`InstancedMesh`），否则会重演"200 舰"的性能问题。

**需要你确认**：① 要不要做模型层；② 若做，先做哪两类。
