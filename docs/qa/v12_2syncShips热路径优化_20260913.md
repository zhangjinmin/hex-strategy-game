## 1. Phase 1｜syncShips 内部细分埋点 —— **推翻 WS13 归因，锁定真正主因**

### 1.1 埋点方法

`window.__b3dProbe` 门控式包裹（不改语义）：对 `syncShips` **五遍**逐一 `performance.now()` 计时，
并计数关键调用（`heightAtPx/pxOf/shipLenOf/shipWOf/fleetVLayout/addMesh/writeDotLayers/writeFleetMarks`）
与分配量（`unitVis.set` 新建对象数 / `unitVis.clear` / `dotGrid.set` / `ships.has` / `flagshipSet.has`）。
细分之和与 `syncShips_total` 的差记为 `syncShips_residual`（未单独计时的循环体 + 计时器开销）。

### 1.3 结论：**`writeFleetMarks`（而非 `heightAtPx`/对象分配）才是 `syncShips` 的真正主因**

- 基线 A 段 `syncShips = 192.3 ms`，其中 **`writeFleetMarks` = 168.9 ms（占 87.9%）**。
- WS13 §7 R1 给出的三条候选（① `heightAtPx` 同格缓存、② `unitVis` 对象池化、③ `pxOf` 平方比较）中，
  **① 的实测成本仅 1.3ms**、②的分配确实存在（720 对象/帧）但**不是耗时主因** ⇒ **WS13 初步归因需要修正**。
- 根因定位到 `writeFleetMarks` 每帧每队调用 `formationOffsets(formation, n)`；
  `formationLayout.ts` 的 `spindleCells(n)` 对 **`spindle` 阵型近似 O(n²·log n)**（逐 L 3→n 试算剖面 +
  每个候选 `Array.from(L).filter().sort()`），单次 n≈120 约 **60 万次操作 + 近千次小数组分配**，
  而它被 **每帧每队**重算（6 队 ⇒ 每帧 6 次）⇒ 帧内 156~169ms。
  > 这正是用户"帧数很低 / 舰队整体移动卡顿"的**结构性来源**（`syncShips` 恒定成本，与是否接火无关）。

## 2. Phase 2｜三项低风险优化（派单明列，措施已核）

### 2a. `UnitVis.h` 字段：第三遍复用第一遍算出的地形基准高度

- `UnitVis` 接口（`:243`）新增 `h: number`；第一遍写 `vv.h = h`（`:3171`）；**第三遍改读 `const h = v.h`（`:3267`）**，
  删除原先对同一 sprite 坐标的**重算**。
- 同帧同参 ⇒ 同值，**语义逐位等价**。效果：`heightAtPx` 调用数在**有实体段**由 879.3 → 720 次/帧（B 段实测，−18%）。
  A 段（无实体）本就 720 次/帧，故 A 段此项无差；其杀掉的是一处无谓重复（耗时 ~0.2ms 级）。

### 2b. `heightAtPx` 的字符串 key → 整数 key

- `tileByKey` 改为 `Map<number, {h, idx}>`；新增 `private tileKey(q, r): number`，
  编码 **`(q + 2048) * 8192 + (r + 2048)`**（`:1046-1048`）。
- **范围核对（防冲突）**：`random` 图 q/r ≤ ±32（最大）；`standard` 图 q ±30 / r ±14；
  custom 来自编辑器（数百内）⇒ `q,r ∈ [-2048, 6143]` 完全覆盖，编码对 `r+2048∈[0,8191]` 单调单射、**无碰撞**。
  运行期只编码不解码。
- 三处调用**同时**改：填充 `:1949`、查询 `:1857`（get）、声明 `:1037`。
  消除每次查询的 `` `${q},${r}` `` 临时字符串分配（`heightAtPx` 内部逐候选格查询 ×9 ⇒ 每帧数千次字符串操作/GC）。
- **注**：`writeDotLayers` 内的 `cellKey`（`:3469`）**刻意仍用字符串**（原注释明确：防"数值打包取整碰撞"）——
  **与 `tileByKey` 不同，不可改整数**。本单未动。

### 2c. `writeDotLayers` 是否重复算 `px/sx/sy`？（读码确认：否）

- 逐字段核对 `writeDotLayers` / `writeOneDot` 消费 `v.x/y/z/px/shipLen/grow/yaw`——**均复用第一遍结果，未重复计算**。
- 其成本（A 段 3.3→3.9ms）已在噪声量级，**按"据证据执行"不改**；该遍的改善来自 Phase 3d 的就地更新。

### 🔴 2d.（本单最高价值项）`formOffsets` memo —— 消除真正主因

> 派单未列此项；由 Phase 1 细分表**据证据新增**。它是 A 段 −87.7% 的**绝对主贡献**。

```ts
// Battle3DOverlay.ts:1059-1065
private formOffsetsMemo = new Map<string, FormationCell[]>();
private formOffsets(formation: string, n: number): FormationCell[] {
  const k = `${formation}:${n}`;
  let v = this.formOffsetsMemo.get(k);
  if (v === undefined) { v = formationOffsets(formation, n); this.formOffsetsMemo.set(k, v); }
  return v;
}
```

- 替换全部 3 处 `formationOffsets(...)` 调用：`:1633`（`__b3dFocus` 取景）、`:2393`（`fleetVLayout`）、**`:2592`（`writeFleetMarks`）**。
- **安全性论证**：`formationOffsets` 是**纯函数**（只依赖 `(formation, n)` 且确定性）；
  已核全部调用方**只读**返回值（无 `offs[i]=` / `push·splice·sort·reverse` 等原地修改）⇒ 结果可长期缓存。
- **语义等价**：换阵 / 减员改 `n` 时自然 miss 重算，与逐帧现算**逐位相同**；不改限流/降档/三级 LOD 任何语义。
- 效果：A 段 `writeFleetMarks` **168.9 → 0.76 ms（−99.6%）**。

## 3. Phase 3d｜`unitVis` 就地更新（消 720 对象/帧）—— 含**消费点审计**

### 3.1 审计（派单硬性前置：必须先确认无跨帧持有）

`UnitVis` 全部消费点：

| 消费者 | 消费时机 | 跨帧持有？ |
|---|---|---|
| `syncShips` 第一/二/三遍 | 同帧内 | 否 |
| `writeDotLayers`（第四遍） | 同帧内 | 否 |
| `writeFleetMarks`（第五遍） | 同帧内 | 否 |
| `updateBillboards` | 同帧内 | 否 |
| `fxYAtPx`（特效取地面高度） | 同帧内 | 否 |
| `__b3dMarkProbe`（调试口） | 同帧内 | 否 |
| `dotGrid` / `flagVisBuf` | **持引用，但 `writeDotLayers` 开头即 `clear()`**，同帧内用完即弃 | 否（同帧内失效） |
| `captures` | 只存 `shipKeys: string[]`（**不持 `UnitVis`**） | 否 |

> **审计结论：全部消费点均在本帧内消费、无任何跨帧持有 `UnitVis` 引用 ⇒ 就地更新安全，实施。**

### 3.2 实施

- 顶部删除 `const alive = new Set<string>()`；`vis.clear()` → `for (const v of vis.values()) v.seen = false;`（`:3118`）。
- `UnitVis` 新增存活标记 `seen: boolean`（`:245`）。
- 第一遍 get-or-create：命中即改写字段（`:3169-3176`），首见才 `vis.set`（字段集合/顺序固定 ⇒ hidden class 稳定）。
- 第一遍后做"就地 GC"：`for (const [k, vv2] of vis) { if (!vv2.seen) vis.delete(k); }`（`:3182`）——
  阵亡/离场条目在此剔除，二/三遍与后续消费者见到的只剩本帧存活单位，**语义与旧 `clear()+重建` 一致**。
- 第三遍后 `this.ships.forEach` 存活判据改 `if (vis.has(key)) return;`。

### 3.3 效果

- `unitVis.set 新建对象/帧`：**720 → 0**（A 段）；`unitVis_clear`：**1 → 0**。
- 消除每帧 720 个对象分配 + 720 次 Map 插入的 GC 压力（这是 WS13 R1 候选②的正确落点，但其耗时贡献远小于 `writeFleetMarks`）。

### 3.4 Phase 3e｜`writeDotLayers` 定向优化？（结论：**不做**，说明理由）

- 细分实测 `writeDotLayers` A 段 3.3→3.9ms、B 段 4.2→4.7ms，**非大头**；
- 其字符串 `cellKey` 是为**防数值打包碰撞**而刻意保留（见 2b 注）；
- **无证据支持改动，按"据证据执行"不做**（避免无收益的高风险改光点层）。

## 5. Phase 5｜口径修正（修 WS13 §5.1 的 A 段噪声）

**WS13 缺陷**：A 段相机由"framing 全部舰队"计算，而舰队初始位置/朝向来自**未固定种子**的随机 ⇒ 三次运行相机 `dist`
不一致（10309 / 8040 / 8784），波动 ±50% 远大于修复效应 ⇒ A 段数字不可引用。

**WS14 修正**：

| 修正项 | WS13 | WS14 |
|---|---|---|
| 相机 | framing 全舰队（随负载变） | **固定机位** `dist = hexR × 160 = 8000`（`CAM_DIST_K=160`）、`CAM_ELEV=0.72`、`CAM_AZIM=0.5`，**与地图/舰队无关** |
| 随机 | 未固定 | **定种 PRNG**（mulberry32，探针在 `page.evaluate` 内全局替换 `Math.random`） |
| 地图 | — | `selectedMapId='standard'` 固定 |

**同口径验证**（before/after 逐位一致）：
`cam={"dist":8000,"target":[0,0,0],"hexR":50,"mapSpan":6408.6,"tiles":1769}`、

## 7. Phase 4｜R3 接火 FX 验证（**用户"打着打着就卡"最未被回答的一环**）

### 7.1 方法

- 探针 `mode=fx` **强制推进至交战**：把 6 支舰队**重定位到战场质心半径 70px 的圆内** + 置 `state='engaging'` + `speed=3`（3× 速度档）。
- 记录每帧 `lasers/hits/shields/missiles/strikes/boats` 池长度（`p4_fx.json`），逐秒聚合（`_ws14_fx_series.txt`），观察**峰值与回收**。

### 7.2 结果（A 段 60s，`forceEngage={fleets:6, states:全 engaging, speedSet:3}`）

- **真实战损发生**：`units 702→694`（−8）、`sumHp 177352 → 166424`（**−10928**）⇒ **确已接火**（非硬造）。
- FX 池逐秒（峰值 → 末值）：

| 池 | 峰值 | 末值(60s) | 零值秒数 | 判定 |
|---|---:|---:|---:|---|
| `lasers` | **158 @5s** | 0 | 48/60 | **交火后回收至 0**（splice 回收，正常） |
| `hits` | **353 @8s** | 0 | 46/60 | **峰值后回落至 0**（正常） |
| `missiles` | **610 @6s** | 0 | 43/60 | **峰值后回落至 0**（正常） |
| `shields` | **275 @6s** | **275** | 0/60 | ⚠ **恒 275**（见 7.3） |
| `strikes` | 0 | 0 | 60/60 | 本窗口未触发（无行星打击/登陆） |
| `boats` | 0 | 0 | 60/60 | 同上 |

### 7.3 结论：**lasers/hits/missiles 交火后正常回收；`shields` 恒 275 = 对象池（设计），非泄漏**

- **查码证实**：`spawnShield`（`:4601`）与 `updateShields`（`:4688`）用的是**对象池**——
  `find(x => !x.active)` 复用，**容量 = 历史高水位**；动画结束只置 `active=false; visible=false`，**不 splice**。
  ⇒ 「常驻 275」是**设计行为**（池容量），不是累积泄漏。**R3 结论：未发现 FX 池泄漏。**
  （对比：`lasers/hits/missiles/strikes/boats` 走 splice 回收 ⇒ 峰值后归零。）
- **⚠ 遗留提示（§8 R3-a）**：`destroy()`（`:5067`）**未显式清空 `shields` 数组** ⇒ 跨场次重开时池容量可能残留（潜在跨场内存残留）。
  WS14 主单**未改**（属 FX 生命周期治理，且无当前可见故障证据）；**已由 WS14 补丁对称清空引用表修复**（见 §8 R3-a 补记）。
