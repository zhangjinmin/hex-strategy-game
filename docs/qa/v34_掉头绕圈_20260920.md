# v34 · 掉头「围绕一个点转圈」定位与修复

> **用户复报**：「舰船的掉头还是围绕着点转圈，改过吗？」
> **日期**：2026-09-20
> **验证**：`vue-tsc` EXITCODE=0；`_v34_spin_sim.cjs` **28 PASS / 0 FAIL**；真机（L2）`ffMaxJumpDeg=180` 确认吸附生效

## 0. 直接回答：改过，但只改了一半

| | 状态 |
|---|---|
| **v31-D 改过没有** | **改过** —— 阵位旋转真源从 `facingSmooth`（舰首）改为 `formFacing`（实际航向低通），并给**中心对称阵型**（横/圆/方）加了"掉头跳过旋转" |
| **为什么你还在看到绕圈** | **非对称阵型（楔 / 纺锤）从未被改**，仍是连续刚性旋转 ⇒ 整队格位沿弧线绕中心转 180°。而 **`DEFAULT_FORMATION = 'wedge'`** ⇒ **这是默认体验**，不是边缘分支 |
| **为什么之前没人发现** | `_v31d_formfacing_sim.cjs` 把"楔形掉头 163.4px"标成了 **PASS（未误跳过）** —— 它只测"格位路程"，没有回答"这段路程**是否必须走弧线**" ⇒ **判据对真正的缺陷维度结构性失明** |

**量化证据（`_v31d` 台架原样输出）**

```
───────── 掉头 180°（横阵 line）─────────
  v31d2 阵位跟航向 + 对称跳过   格位路程     0.0 px   ← 已修好
───────── 掉头 180°（楔形 wedge · 非对称对照）─────────
  v31d2 阵位跟航向 + 对称跳过   格位路程   163.4 px   ← 一字未改，却被标 PASS
```

`163.4px = π × 52px` —— 正是**半径 52px 的半圆周长**。这就是"围绕一个点转圈"的精确数值形态。

## 1. 根因链

```
① 舰队掉头 → 推力对齐衰减（THRUST_IDLE=0.05）把航速压到 12% ⇒ 舰队近乎停船
② 速度≈0 时 formFacing 被 FORM_FACING_MIN_SPD2 冻结（设计如此，防 atan2 抖动）
③ 舰队重新加速 ⇒ 实际速度方向 moveDir 反向
④ |moveDir − formFacing| = 180° > 150°（掉头级）
   · 对称阵型 → 跳过旋转 ✔（v31-D）
   · 非对称阵型 → rateLimitAngle(formFacing, moveDir, FORM_FACING_RATE × dt)  ← 病灶
⑤ 每帧转 π/120 rad ⇒ 180° 需 120 帧 ⇒ 整队格位**刚性旋转**，每个格位
   沿"以舰队中心为圆心、半径 = 格位距"的圆弧走半圈 ⇒ **绕圈**
```

**持续时间**：实测 220~251 帧（≈3.7~4.2 s @60fps，见 §4 表）。比"2 秒"更久，
因为瓶颈不是旋转速率常数，而是**速度反转本身的耗时**。

### 3.1 台架（28 PASS / 0 FAIL）

| 策略 | 阵型 | 路程px | 效率 | 最小半径px |
|---|---|---|---|---|
| v31c 阵位跟舰首 | wedge | 236.4 | 1.570 | — |
| v31d2 **现状** | wedge | **222.3** | **1.539** | **50.1** |
| **v34 吸附** | wedge | **151.2** | **1.000** | **0.3** |
| v31d2 / v34 | line | 0.0 | 1.000 | —（跳过，原地转身） |
| v34 | 90° 转向 | 81.5 | 1.099 | —（**仍走弧线，未被误吸附**） |

- **路径效率** `Σ路程 / 净位移`：1.000 = 直线最短；π/2 = 1.571 = 半圆绕圈。
- 楔形掉头：**效率 1.539 → 1.000，路程 222.3 → 151.2px（−32%）**。
- **90° 转向未受影响**（台架断言 v34 与 v31d2 逐位一致）—— 垂直轴不同，阵位确实要重排，且弧线只比直线长 11%，观感自然。

`ffMaxJumpDeg = 180` **确证吸附在真实游戏里生效**（若是连续旋转，该值必然 ≈1.5°/帧）。

## 4. ⚠ 必须说清的代价：绕圈与穿心，二选一（没有第三种）

非对称阵型掉头时，格位集合**必须**整体翻到新航向一侧（否则阵型会"倒着飞"）。
起点与终点关于舰队中心**点对称** ⇒ 几何上只有两种走法：

| | 弧线（v31-D 现状 / `MODE:'arc'`） | 吸附（v34 / `MODE:'snap'`） |
|---|---|---|
| 轨迹 | 以中心为圆心、半径 = 格位距的圆弧 | 穿过中心的**直线** |
| 半径 | 恒定（50.1px） | 过 0（0.3px） |
| 路径效率 | 1.539 | 1.000 |
| 观感 | **绕圈**（用户复报） | 单位**穿心重排**（200 舰时中心拥挤，与 R1「缩团/穿心」同类） |
| 物理性 | 刚体旋转，正确且不拥挤 | 最短路径，但穿越中心 |

### 4.1 「调快旋转速率」被实测否决

```
uturnMul  转完帧  @60fps秒  效率   最小半径px  路程px
×1        251     4.183    1.539  50.1       222.3
×2        241     4.017    1.516  49.7       218.8
×4        236     3.933    1.501  48.8       216.6
×8        230     3.833    1.478  47.2       213.4
×16       221     3.683    1.434  44.1       207.3
×32       220     3.667    1.429  43.7       206.6
∞(吸附)   132     2.200    1.000   0.3       151.2   ← 只有吸附是质变
```

**×32 仍是 1.43 / 43.7px** —— 因为瓶颈是**速度反转耗时**（`formFacing` 跟的是实际速度方向），
不是速率常数。⇒ 中间档全部无效，**不存在"转快点就不像绕圈"的折中**。

### 4.2 结论与回退

- 默认 `MODE: 'snap'`（用户明确不要绕圈）。
- **若真机上"中心拥挤"比"绕圈"更难受**：把 `balance.FORMATION_SPIN.MODE` 改成 `'arc'`，
  **一键回到 v31-D 行为**（台架已断言 `'arc'` 与 v31d2 逐位一致），无需回滚代码。
- 这条**只能由眼睛定**（L3）—— 无头截图与台架都给不出"哪个更难看"。

## 5. 顺带纠正的两个判据错误（防止复发）

1. **`_v31d` 只测"格位路程"** ⇒ 无法区分"必须走弧"与"可以走直线" ⇒ 把缺陷标成 PASS。
2. **本次初稿又用"绕心累计转角"当判据** ⇒ 台架当场打脸：**弧线与直线穿心的绕心转角都是 180°**
   （穿心时位置矢量从中心一侧穿到另一侧，角度同样翻 π）⇒ 该指标对本问题**零判别力**。
   已写入台架并断言，标注为「陷阱标注」。

**本次可用的判据**：① **路径效率** `路程/净位移`（1.000 vs 1.571）；② **最小半径**（恒定 vs 过 0）；
③ 真机 **`formFacing` 单帧最大跳变**（1.5°/帧 vs 180°/帧）。

## 6. 顺带记录：游戏时间基准 = 帧 × dt（不是墙钟）

`FORM_FACING_RATE`、`HEADING_TURN_RATE`、`thrustFactor`、`atkInterval / dt` 全部是**每帧步长**，
只乘 `store.currentSpeedFactor`，**不乘真实 `delta`**。这与位移（也是每帧 `speed × dt`）一致
⇒ 相对时序不变，但**墙钟速度随帧率变化**：无头 SwiftShader 只有 3fps，实测 234 帧 = 75 秒。
**这不是缺陷**（Wails 桌面端 60fps 下即为设计值），但排查时必须以**帧数**而不是秒数思考。
