# v34d 分兵「单位归属」缺陷（2026-09-20）

> **触发**：用户 15:26 带截图复报，两条问题 ——
> ①「我第一次分兵的时候，分兵的舰队正常组成了正向；第二次分兵的时候，还是和原来一样，是**只有一层**的」
> ②「部队下面的代表阵型的绿色托盘，分兵1 和分兵2 的这个绿色托盘并不是在部队下面，而是**各走各的**，
>    就是模型往左走，但是托盘就没跟上」
> **方法**：L2 无头浏览器取证（`_probe_split2.mjs`，**连续两次分兵**，状态断言级 + 判据自证）
> **结论**：**两个问题是同一处根因** —— `BattleScene.splitFleet` 把单位交给子编队却**未从母队移除**，
> 同一 unit 被两支舰队同时引用。

---

## 1. 假设（静态阅读 `splitFleet`，`BattleScene.ts:3449`）

| # | 假设 | L2 判据 |
|---|---|---|
| **H1** | `parent.units` **从未裁剪** ⇒ 同一 unit 被两支舰队同时引用 | 同一 sprite 出现于 >1 支舰队 |
| **H2** | 末尾"母队重编号"遍历**全量** `parent.units` ⇒ 覆盖子队 `formationSlot` ⇒ 越界 ⇒ 全在第 0 层 | `formationSlot ≥ formationCount0` 的单位数；**实占层位** |
| **H3** | 托盘按 `offs` 画、而单位被 `ringCell` 摆到兜底环 ⇒ 各走各的 | 托盘覆盖 / 单位越出量 |

---

## 2. 取证（修复前）

```
① 开战后（AI 已自动分兵）    共享 sprite = 79
② 第一次分兵后              共享 sprite = 158
③ 第二次分兵后              共享 sprite = 158
```

逐队读数：

| 时刻 | 队 | units / n0 | slot 范围 | 越界 | **实占层位** | 血缘 |
|---|---|---|---|---|---|---|
| ① | 母队 | 200 / 198 | −1..197 | 2（运输舰） | 17 | — |
| ① | **分舰队** | 79 / 79 | **119..197** | **79 / 79** | **1** | ← 母队 |
| ② | **第一次分兵的子队** | 79 / 79 | **119..197** | **79 / 79** | **1** | ← 母队 |
| ③ | **第二次分兵的子队** | 32 / 32 | **47..78** | **32 / 32** | **1** | ← 二级子队 |

⇒ **母队正常（16 层满层），只有分舰队塌成一层**；`slot` 是其 `n0` 的 1.5~6 倍。
⚠ **敌方 AI 自动分出的舰队同样中招**（① 的 79 就是敌方分舰队）⇒ 不是玩家侧特有。

---

## 3. 根因（两步，都在 `splitFleet` 内）

```ts
// 缺陷 1：子编队拿到 slice，但 parent.units **没有移除**那些单位
const child: any = { ...parent, units: slice, … };

// 缺陷 2：末尾"母队重编号"遍历的是 **全量** parent.units
let fs0 = 0;
for (const u of parent.units) { if (isSup(u)) continue; u.formationSlot = fs0++; … }
parent.formationCount0 = fs0;     // ← 也仍是"全量非运输舰数"，不是"剩下的"
```

后果链（以子编队为例）：

| 环节 | 读数 | 结果 |
|---|---|---|
| `fleetVLayout` 的 `offs` / `layK` 长度 = `child.formationCount0` | 79 | — |
| 单位 `formationSlot` 被母队循环覆盖 | 119..197 | **全部越界** |
| 3D 层 `layK[laySlot] ?? 0` | 全取 0 | **整队塌成一层**（症状 ①） |
| BattleScene `formOffsets[slotIdx] \|\| ringCell(slotIdx)` | 全落兜底环位 | 阵型形状与托盘**无关** |
| 同 sprite 每帧被两支队各写一次目标位 | — | 位置被来回拉扯（症状 ②） |

> **一句话**：单位归属没做干净 ⇒ 子队既"不知道自己该站哪"（层号被覆盖），
> 又"同时听两个人指挥"（位置被拉扯）。

---

## 4. 修复

`BattleScene.splitFleet` 内，切分时把划出去的单位登记进 `moved: Set`，
**先 `parent.units = parent.units.filter(u => !moved.has(u))`，再重编号**。

⚠ **顺序不可交换**：先重编号就会被母队口径覆盖 —— 这正是缺陷的成因。
⚠ 该 `Set` 只收 **i ≥ 1** 的 slice（`i === 0` 的 main 路留在母队，不进 `moved`）。

## 5. 验证（修复后）

### 5.1 归属与层数（L2 状态断言，**16 PASS / 0 FAIL**）

| 判据 | 结果 |
|---|---|
| `sharedSprites` | 79 / 158 → **0** |
| 每队 `oorUnits`（越界单位数） | 79 → **0**（5/5 队） |
| 每队 `n0 ≥ 当前战斗舰数` | ✅ |
| **实占层位** | 1 → **14~16**（5/5 队，含三级血缘链的孙队） |

三级血缘链实测：`0.8417(119舰) → 0.1886(47舰) → 0.0156(32舰)`，
`slot` 分别为 `−1..118 / 0..46 / 0..31`，与各自 `n0` 精确对应 ⇒ 每支队**只由自己重编号**。

### 5.2 问题 ②：托盘覆盖（**这才是"托盘在不在部队下面"的判据**）

| 队 | 战斗舰 | 托盘整跨 (X,Y) | **越出单位** | 最大越出 | 探针自证 |
|---|---|---|---|---|---|
| 0.9824 | 119 | 582.4 × 291.2 | **0 / 119** | 0px | 0px |
| 0.5930 | 79 | 118.6 × 336.0 | **0 / 79** | 0px | 0.9px |
| 0.1370 | 60 | 112.0 × 336.0 | **0 / 60** | 0px | 1.1px |
| 0.7466 | 59 | 112.0 × 336.0 | **0 / 59** | 0px | 1.1px |
| 0.8894 | 47 | 349.4 × 174.7 | **0 / 47** | 0px | 0px |
| 0.0873 | 32 | 233.0 × 145.6 | 6 / 32 | **9px** | 0px |

⇒ **5 / 6 队：全部战斗舰落在托盘内**。唯一越出的是**刚分出的二级子队**（32 舰），
6 艘越出、最大 **9px = 托盘整跨的 3.9%（≈ 半格）** ⇒ 判为**收敛中**
（分兵后仅 25s 墙钟，无头 3fps 下 75 帧；`formOffsets[slotIdx] || ringCell` 的兜底已不再触发）。

**对照修复前**：子队 **100% 的单位**都被 `ringCell` 摆在阵型外的兜底环上，
托盘**完全无法覆盖**（且同批 sprite 还被两支舰队来回拉扯）。

「探针自证」列 = 用 `markerAxes` 公式反算的托盘中心 ↔ 渲染出的顶点均值，全部 **< 1.1px**
⇒ 判据的投影口径与渲染一致，读数可信。

## 6. ⚠ 判据陷阱（本轮第三次犯同类错误，务必记住）

排查症状 ② 时我先立了一条判据：**"托盘中心 vs 舰船质心 < 21px"**，结果 FAIL（21.8~159px）。

**这条判据是错的**，逐项排除后：

| 被排除的候选 | 实测 | 结论 |
|---|---|---|
| 托盘朝向用 `facingSmooth`、阵位旋转用 `formFacing`（v31-D 铁律要求同源） | `Δθ = 0.0°`（**5/5 队**） | 直航时两者相同 ⇒ **本次不是成因**（保留为观察项） |
| 质心含**运输舰**（其 sprite 由 `aux` 独立驱动、不参与阵型定位） | 2 艘即可拉偏 20~40px | 改用"战斗舰质心"后重测 |
| `markerCenter` 取的是 `ShapeGeometry` 的**顶点均值**（剖分边缘密、内部疏） | 偏离几何中心 | 测量伪影 |
| **托盘中心取"足迹包围盒中心"，质心是"格位均值"** | 偏移 / `\|mid\|` **恒 = 0.34**（5/5 队） | **几何恒等式，非缺陷** |

**0.34 这个恒定比值是决定性的**：随机误差或"未到位"不可能给出跨 5 支舰队恒定的比例。
楔形（尖顶 1 格、尾部最宽）的**包围盒中心**本就与**格位均值**不同 ——
而 `writeFleetMarks` 的注释明确写着"底板中心取**足迹包围盒中心**，不是舰队锚点"，
这是**设计**（目的：让标记包住编队）。

⇒ 正确判据 = **每个战斗舰是否落在托盘覆盖范围内**（越出量 = 0），见 §5。

> **教训**：判据必须与**实现意图**对齐。"两个中心重合"不是本功能的目标；
> "标记包住编队"才是。立判据前先读被测量对象的注释。

## 7. 顺带发现（未改，仅记录）

1. **兵力重复计算**：修复前 `calculateFleetPower(parent)` / AI 决策把同一批单位在
   母队与子队**各算一次** ⇒ 战力虚高、`forceRatio` 失真。本修复顺带修正。
2. **托盘朝向源与阵位旋转源不一致**（`markerAxes(facingSmooth)` vs 落位 `formFacing`）——
   本批实测 `Δθ = 0`（直航），**未改**；但按 v31-D 铁律两者应当同源，
   一旦出现"边转向边看托盘"的场景就会偏。**留作观察项**（`markerAxes` 全项目仅 1 个消费者，改动面安全）。
3. **探针坑**：页面快照函数若以模板字符串注入，**内部不得出现反引号**（会截断模板导致
   `SyntaxError`，且报错指向注释行、极难定位）。
