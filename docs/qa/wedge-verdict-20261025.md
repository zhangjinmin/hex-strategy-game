## Q1 「帝国侧正常、同盟侧异常」能否由 B 解释？

**判定：归因不完整。机制成立，实例不成立。**

1. **机制层（成立）**：同一帧同一相机，两侧可读性**可以**不同 —— 因为 `formFacing` 是**每队**的，而相机方位是**全局一个**。我的二维扫描：仰角 58.5° 时，δ=0 ⇒ 可读、δ≥30° ⇒ 形状比 0.85 超上限、δ=90° ⇒ 排序 |ρ|=0.16（排不再"叠"）。机制无争议。
2. **但上游证据是"构造出来的"**：`_diag_wedge_view2.cjs` 的 C 帧是把相机**手动搬到侧向**（第 132–146 行 `camera.position.set(cx + lat*700, 260, …)`）才拍到的，不是从用户复现路径（战术模拟→同盟→比克古→开战）上观测到的。**"我搬出一个坏角度"≠"用户看到的就是坏角度"。**
3. **帝国侧样本 0 条**：该探针第 69–70 行只挑 `type === 'player'` 的舰队。所以"帝国正常"没有任何测量支撑，只有用户口述。
4. **单变量未隔离**：A/C 两帧同时改了方位与仰角（58.5° vs 17.4°）。我复算：17.4° 在 **δ=0** 下就判不过（形状 0.18、叠层糊化 1.04）⇒ C 帧的"恒定跨度"**主要是仰角病**，把它算作方位证据是**事实为真、因果错配**。
5. **反向证据（最要命的一条）**：当前代码 `startEntryFx → focusOnPlayerMainFleetForEntry → focusOnPlayerMainFleet → focusOnFleet` 把相机严格放到**我方主舰队正后方**（δ=0，仰角 58.5°），随后 v106 的增量跟随**保持相对视角**不变。⇒ 按代码推演，默认路径下**我方舰队是最不容易读不出的那一支**，被随便一个方位看着的才是帝国舰队。观察方向与预测方向相反。
6. **缺的三条证据（都可执行，缺一不可）**：
   - ① 用户复现路径下「冷启动 → 开战 → 8 秒不碰相机」的逐帧表：`camAzim / camEl / _camUserDragUntil / entryFxOff`，以及**每支舰队**（含帝国 ≥3 支）的 `formFacing` 与 δ；
   - ② 取景瞬间 vs 稳态的 `formFacing` 差 Δ（`placeUnitsAtFormationSlots` 会写 `formFacing`，而 `advanceFormationFacing` 随后可能限速转向 ⇒ **Δ ≠ 0 会让相机一次性错配并被增量跟随永久保持**，见 QA-2）；
   - ③ 同一场战斗里"用户说好的那一刻"与"用户说不好的那一刻"两张截图 + 两组数（这是唯一能证明"随方位变"的现场对照）。
7. **证伪条件（写死，便于下一轮直接判）**：若上面 ① 里我方 δ ≤ 20° 且 elev ∈ [50°,70°] 时**仍然**读不出 ⇒ **B 被证伪**，病因必须转 C（叠层）或 Q2（舰长/格距），与相机无关。
8. **另一条必须先排掉的坑**：`focusOnFleet` 在 `frontend/src` 内**没有 UI 调用点**（全库 `focusOnFleet` 只有定义 + `focusOnPlayerMainFleet` 包装 + 注释；UI 只调 `focusOnPoint`）。⇒ v103 的方位修复**只经入场聚焦生效**；一旦 `ENTRY_AUTO_FOCUS=false` 或 `entryFxOff`（设置项关闭入场动画），相机退回 `buildSpaceWorld` 的**固定机位（azim=0、仰角 35°）**，与任何 `formFacing` 无关 —— 该机位下我用 5 个 facing 全扫：**θ=0/45/90/135/180° 全部判不过**（绑定项分别是 排序0.45 / 箱宽 / 叠层0.51 / 箱宽 / 排序0.77）。这就是"有时中途自行变正常"的另一半解释。

> 一句话给主理人：**B 能把"为什么同一帧两支舰队读起来不一样"讲通，但不能把"为什么偏偏是同盟那一支"讲通。** 后者需要上面 ①②③，其中 ② 是一条独立的、可能更致命的代码路径（初值错配 + 增量跟随永久保持）。

## Q2 「异常时楔尖是小舰、大型舰打头就正确」能不能由 B 解释？

**判定：不能。且它指向的不是"阵位号与舰种排序耦合"，而是一条与相机无关的几何因子（并附带一个真正需要防的结构性风险）。**

1. **B 无法解释**：舰种换位不改变任何格位坐标。`placeUnitsAtFormationSlots` 只按 `u.formationSlot` 取 `offs[cellIdx]`，完全不看舰种（`BattleScene.ts:1977-1982`）⇒ 理论上屏幕点云应**逐点相同**，B 的任何说法都推不出"舰种会影响形状"。
2. **候选一（与相机无关的几何，能复现用户原话）**：排间屏幕间隙 = 26·sin(仰角)，而舰首沿纵深轴的投影 = 舰长·sin(仰角)。我按真实数值算：**大舰首投影恒为间隙的 98%**（58.5°/45°/35°/17.4° 四档都一样），**小舰 ≈ 40%**。
   ⇒ 大舰打头时楔尖与第 2 排**连成一片**，读作实心三角；小舰打头时楔尖是孤立点、身后空一格 —— 这正是用户原话「前面一艘 + 中间空隙 + 后面一堆」。
   ⇒ **这一条归位修不掉**（它与方位无关）。是否接受是设计取舍，不是"改完就好了"。
3. **候选二（结构性风险，须排除）**：`placeFlagshipAtRear`（`BattleScene.ts:3037-3049`）把旗舰（slot 0）与 `rearCommandSlot`（n=89 时为 slot 27）**对调** ⇒ 楔尖是"被换出来的那艘"，其舰种由建造顺序决定。这与"异常时楔尖是小舰"高度吻合，但**它是设计已记录的行为**，本身不是缺陷；真正的风险只在"换位/号段压缩后 n0 与 rankOf 是否仍自洽"（若自洽则无缺陷）。
4. **判别实验（一条命令即可定生死）**：同相机、同 n、同所有格位，**只替换 slot 0 上的舰种**（不动任何坐标）：
   - 屏幕点云逐点差 ≤ 1px ⇒ 候选一（感知/舰长），记「设计主张不同」，**不计缺陷**；
   - 差 > 1px ⇒ 候选二成立（舰种确实影响坐标）⇒ **阻断级**，退回 lead-programmer。
5. **不要用"用户换了大舰就好了"当证据**：换编成同时会改 `maxShipH` → 改 `layerGap` 的几何下限 → 改层数/厚度（`vLayout` 里三者互相耦合）。所以那句话里至少有 3 个变量同时在动，**必须做单变量对照**。

## Q4 误伤评估（逐条"会/不会 + 理由"；判"会"的已写进上述断言）

| # | 改动 | 会/不会引入新问题 | 理由与处置 |
|---|---|---|---|

## 6. 验收结论

**不达标（过程审核 · 阶段2 Demo 步骤）**

- **退回 team-lead（补证据）**：Q1 的 ①②③。在帝国侧样本为 0、坏角度系人工构造的情况下，"相机方位是同盟侧异常的病因"目前只是**相关**，不是**因果**。
- **退回 lead-programmer（实现须满足，否则不留）**：AC-W1/W2/W3 三条几何门禁 + AC-W4①~④ 四条负向断言。四条负向断言里，② ③ ④ 各自对应一条**已知会复发的事故**（阵位被相机污染 / 疯狂自转 / 急转后永久歪）。
- **可继续实施的部分**：取景归位（抬仰角到 [50,70] + 沿阵型轴）与过期注释订正 —— 这两项与"哪一侧"无关，我已独立复算其**必要性**成立（`OVERALL: PASS`）。
- **不得据此宣布"修好了"**：本项目历史事故（`tsc` 0 错 + 11 守卫全绿 + 24 项浏览器验收全过，用户仍报"操作不顺畅/炸弹不消失/在墙上跑"）。本轮只有自动化与离线复算，**没有一个人从冷启动路径上确认过"我看出来了"** ⇒ 结论必须带这一条保留。AC-W6 的真人路径与渲染帧是**交付必要条件**，不接受"断言全绿"代替。
