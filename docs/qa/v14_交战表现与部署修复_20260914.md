## 1. ① 尾焰"小圆点" → 朝后短喷流/锥

### 1.1 问题确认
1) 近景单舰特写对照：`before_flame_close.png` 清晰显示**舰尾一枚独立红色圆球**（静态球体 mesh）；`after_flame_close.png` / `after_flame_ship.png` 为**橙色喷流**、无圆球。
2) 构建代码核实：四条构建分支的 `glow`（舷侧）与 `flame`（主喷流）**全部**已由静态球改为 `ConeGeometry` 喷流锥。

### 1.2 实现（`buildEngineJet` / `buildGlowJet`，`Battle3DOverlay.ts:2762 / 2789`）
- 几何：`ConeGeometry(r, h, 6, 1, true)` → `rotateX(π/2)` → `translate(0, 0, h/2)`。
  - 轴 **+z 朝后**；**底在喷口 z=0、尖朝后 z=+h**；`h = L*lenK`、`r = L*rK`（按舰长 L 折算）。
- 材质：`MeshBasicMaterial { vertexColors:true, color:0xffffff, transparent, opacity:0.9, AdditiveBlending, depthWrite:false, side:DoubleSide }`。
- **颜色（金红系）**：主喷流顶点色沿长度由**底白黄 (1.00, 0.92, 0.72) → 尖深红 (0.72, 0.10, 0.03)**（与 WS15 粒子尾焰 hot/mid/cool 同色系常量，视觉连续）；舷侧小喷口锥恒金色 `0xffcc66`。
- **受创变红保留**：`flame.material.color.setHex(damaged ? 0xff5533 : 0xffffff)` 通道语义不变（白色=不改色相、红=受创）。

### 1.3 各分支参数（最终值）

| 分支 | glow（舷侧小锥） | flame（主喷流锥） |

| generic（`buildGenericShip`） | `buildGlowJet(L, W*0.11/L, 0.10)` ×2 舷 | `buildEngineJet(L, W*0.16/L, 0.16)` |

### 2.3 "我方 aux 只有 1 艘"的解释 + aux 状态机核对
- **折算层给出的是"每队"口径**（改前 9/队、改后 2/队），与本方舰队数无关；整场合计改前 `45+9=54`、改后 `10+2=12`。因此"只有 1 艘"**不可能**来自 `allocateUnitsPerType`（远多于 1）；也**不可能**来自 `collectAuxShips`（`SupplyChainSystem.ts:244` 无上限，逐补给实体各建 1 艘）。
- **落点只可能在下游"可见/激活"环节**：
  - 3D 覆盖层对 aux 仅在 `outbound` / `supplying` 状态画补给圈与链路（`Battle3DOverlay.ts:4122/4136/4139`）——起始全 `loading` ⇒ 圈/线不可见；
  - 2D aux sprite 在 `loading` 用 `alpha 0.35`（`BattleScene.ts:1175`）且**泊于母港 castlePos**，多艘重叠 ⇒ 视觉上≈1 艘。
- **台架限制（知识诚实）**：headless 3D-sim 台架里 Phaser `Clock` 计时器被**冻结**——所有 `activeEvs.elapsed` 恒定不变、自建计时器 `ownTicks=0`、6 个 `delayedCall(800)` 从不触发 ⇒ 1s `TimerEvent` 内的 `processSupplyAndCapture`（`collectAuxShips` 的**唯一调用点**）**从不自动执行**，`auxShips` 恒为空、自动状态机走不起来。仅"手动调用"能取到全集（`manualOk=true`、`manualAux` = 补给实体总数）。**故"我方 aux 只有 1 艘"在台架无法复现/证伪，需真机确认。**
- **状态机核对**（读码 `SupplyChainSystem.ts:145-205`，本次未改）：`loading`（泊港装货，`cargo < AUX_CAPACITY` 时留港）→ `outbound`（出航，朝 `targetFleet`）→ `supplying`（`d ≤ SUPPLY_AUX_RADIUS` 卸货，`cargo` 递减）→ `returning`（`cargo ≤ 0` 返航）→ `loading`。实测采集到的全部 aux 均处 `loading`（起始态），与"先满载再出航"的设计一致。

### 5.2 友军排斥 80px 评估（`BattleScene.ts:3917-3923`，本次**未改**）
- 现状：友军 `fDist < 80` 时 `force = (80 - fDist) * 0.02`；敌我 `fDist < 200` 时 `force = (200 - fDist) * 0.015`。

## 9. 勘误与修复（v14.1）

> 主理人核验发现 ③1 阵型 morph 存在**单位错误**。本节为勘误记录；**§3.1 正文按历史留痕保留不改**。

### 9.1 缺陷（已核到行，结论确凿）
`BattleScene.ts:4040`（v14 原版）：
```ts
(fleet as any)._formMorphT = Math.min(morphDurNow, morphTNow + dt);
```
此处 `dt` 是 `:3127 const dt = this.store.currentSpeedFactor`——**速度倍率**（默认 1.0，档位 [0.5,1,1.5,2,3]），**不是时间增量**。morph 每帧只推进 1.0（速度倍率 1 时）⇒ `FORMATION_MORPH_DUR = 3.5` 实际是 **3.5 帧**（60fps ≈ 58ms），不是 3.5 秒。
- 对照：3D 层是对的 —— `Battle3DOverlay.ts:5068 const dt = Math.min(this.clock.getDelta(), 0.05)` 是**真实秒**，故 ③2 转向限速 30°/s 正确。
- 全文件 `duration: xxx / dt` 约定佐证 `dt` 语义为速度倍率；`applyCommandEffects(delta)` 参数名佐证 `update(time, delta)` 的 `delta` 是**毫秒**。
- **原 §3.1 的 "过渡时长 3.5s" 不成立**：运行时样本（`morphT_first=3.5 / morphDur=3.5`）只证明计数器被夹紧到 3.5，**不能**证明墙钟时长。用户诉求是"变阵缓慢（秒级）"，按旧实现真机上仍会显得"突然变阵"。

### 9.2 修复（最小改动）
`BattleScene.ts:4046`（v14.1）：
```ts
(fleet as any)._formMorphT = Math.min(morphDurNow, morphTNow + (Math.min(delta, 100) / 1000) * dt);
```
语义：`delta`(ms) → 秒 ×`dt`(速度倍率) ⇒ **1x 全长 3.5 秒；3x ≈1.17 秒**；`delta` 夹 100ms 防单帧卡顿跳变。`FORMATION_MORPH_DUR = 3.5` 数值不动。
