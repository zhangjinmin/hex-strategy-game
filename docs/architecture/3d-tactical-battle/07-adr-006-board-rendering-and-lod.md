## 2. 棋盘渲染：**基板 + 顶盖 + 高格裙边** 三层结构

> **本节为终稿（R2）**，取代 R0/R1 两版。改动原因：R1 的"全裙边"方案（31,216 tris）在全局档下会顶到美术的 36,000 硬上限（见 §5.2）。R2 用"基板 + 裙边阈值"把棋盘降到 **10,206 tris（典型）/ 20,094（上限）**。

### 2.1 备选

| 方案 | 三角形 | draw call | 结论 |
|---|---|---|---|
| B1 全棱柱（`CylinderGeometry(…,6)` 带顶盖） | 1951 × 24 = **46,824** | 1 | ❌ 超硬上限 36,000 |
| B2 全棱柱去底盖 | 1951 × 18 = **35,118** | 1 | ❌ 逼近硬上限，且全局档下无剔除 ⇒ 必超 |
| **B5 基板 + 顶盖 + 高格裙边（选定）** | **10,206（典型）/ 20,094（上限）** | **18** | ✅ |
| B4 整块平面 + hex 网格纹理 | 2 | 1 | ❌ 无立体起伏，不满足"棱柱分层" |

### 2.2 决定：B5

```ts
// boardMesh.ts
// —— 层 0：基板（一整块平面，y = 0，覆盖整个棋盘 AABB）——
// 2 tris / 1 draw call。作用是"堵住所有低格下面的缝"，见下方"缝隙问题"
const baseMesh = new THREE.Mesh(new THREE.PlaneGeometry(bw, bh), baseMat);
baseMesh.rotation.x = -Math.PI / 2;

// —— 层 1：每个格子一个平顶六边形，位于 y = ELEVATION[type] ——
// 六边形拆成 2 个梯形 = 4 三角形
const topGeo = makeHexFanGeometry(4);                       // circumradius = 1/√3
// 按 16×16 格分块（见 §2.3）
topMesh: InstancedMesh[16];   // 每块容量 256，frustumCulled = true
// 每实例: position = (worldX, ELEVATION[type], worldZ), scale = (0.94, 1, 0.94)

// —— 层 2：只有"高格"画侧壁裙边（从 y=0 长到 y=ELEVATION）——
// 6 个四边形 = 12 三角形，无顶盖（顶盖由层 1 提供）、无底盖
const skirtGeo = makeHexSkirtGeometry();                    // 12 tris, origin 在底
const skirtMesh = new THREE.InstancedMesh(skirtGeo, skirtMat, 1024);  // 不细分块
// 每实例: position = (worldX, 0, worldZ), scale = (0.94, ELEVATION[type], 0.94)
```

**裙边阈值 `SKIRT_THRESHOLD = 0.25`（格）**：`ELEVATION ≥ 0.25` 的格子才画裙边。

| 有裙边（≥ 0.25） | 无裙边（< 0.25） |
|---|---|
| `pier` 0.26、`mine` 0.30、`gold_mine` 0.32、`barracks` 0.42、`castle` 0.52、`tower` 0.58、`planet` 0.70、`fortress` 0.85 | `sea` 0.10、`ruined` 0.14、`pending` 0.22 |

**"缝隙问题"为什么被基板解决了**（这是 R1 版我误判的地方）：

R1 版担心"低格不画裙边会露出侧面空洞"，于是退回"所有格子都画裙边"。正确解法是加基板：

- 相邻两格的高度差最多 `0.85 − 0.22 = 0.63 格`。高处那格**一定有裙边**（≥0.25），裙边从 `y=0` 长到 `y=ELEVATION`，是一堵完整的墙 ⇒ **高度差被高处那格的裙边遮住**，不需要低格也有裙边。
- 唯一例外是"低格 vs 同样低但略高的格"（如 `pending` 0.22 vs `ruined` 0.14），差 0.08 格。从 27° 仰角看投影 `0.08 / tan(27°) = 0.157 格`，在默认档（34 px/格）下是 **5.4 px**。这 5.4 px 的缝里露出的是**基板**（深色）而非背景 ⇒ 读作"阴影"，视觉上正确。
- 棋盘最外圈的侧面：由基板边缘提供（基板稍大于棋盘 AABB）。

**三角形核算**：

| 层 | 每实例 tris | 实例数（典型 / 上限） | 小计（典型 / 上限） | draw call |
|---|---|---|---|---|
| 基板 | 2 | 1 / 1 | **2 / 2** | 1 |
| 顶盖 | 4 | 1951 / 1951 | **7,804 / 7,804** | 16 |
| 裙边 | 12 | **~200 / 1024** | **2,400 / 12,288** | 1 |
| **合计** | | | **10,206 / 20,094** | **18** |

典型值 200 条裙边的依据：`random` 地图生成时只有 `pending/sea/ruined/planet` 四类，星球 15–24 个；开局每阵营 1 个 `castle`（≤8）；`tower/barracks/mine` 在对局中由玩家/AI 建造，实测规模取决于时长。取 200 为典型、1024 为池上限（超限则最老的实例被复用，表现为"最远的建筑失去裙边"）。

### 2.3 顶盖分块（chunk）：16 块

```
chunkId(q, r) = (floor(q / 16) + 64) * 128 + (floor(r / 16) + 64)
// random 地图 q, r ∈ [-25, 25] ⇒ floor(q/16) ∈ {-2,-1,0,1} ⇒ 4 × 4 = 16 块
```

| 项 | 不分块 | **分块（16 块）** |
|---|---|---|
| draw call（顶盖） | 1 | **16** |
| 提交三角形 @ D=13.3（L0，可见 19.6 格） | 7,804 | **~1,951**（25%） |
| 提交三角形 @ D=25.5（默认档，可见 37.5 格） | 7,804 | **~3,902**（50%） |
| 提交三角形 @ D=60（全局档，全盘可见） | 7,804 | **7,804**（无剔除） |

**取舍理由**：+15 draw call 换来全局档以外所有场景的 ~50% 顶盖剔除。美术的 draw call 预算是 **<180**（不是我最初假设的 120），+15 完全付得起；而三角形是最紧的资源。

**分块索引表在 `buildBoard()` 时构建一次**，地块归属/高度变化时按 `chunkId` 定位到对应 mesh 更新 —— 不需要重建。

**若实测 A6-2 显示棋盘成本 < 0.5 ms**，可回退到不分块（省 15 draw call）。记录为 A6-Q7。

### 2.4 顶面描边（不增加 draw call）

顶盖的六边形描边在 fragment shader 里画，用**实例 UV 到六边形边界的距离**：

```glsl
// 顶盖 shader 片元（示意）
// vHexUv: 顶点在单位六边形内的局部坐标（由 geometry 的 position.xz / circumradius 得到）
float d = hexEdgeDistance(vHexUv);          // 到最近边的距离，0 = 边，1 = 中心
float edge = 1.0 - smoothstep(0.0, 0.06, d);
vec3 col = mix(fillColor, strokeColor, edge);
```

- `topMat` 用 `onBeforeCompile` 注入，或直接用 `ShaderMaterial`。
- 归属色通过 `instanceColor` 传入（`InstancedMesh.setColorAt`）。
- 0 额外 draw call。

## 3. 舰船合批与 LOD

### 3.1 合批策略

| 对象 | 方案 | draw call |
|---|---|---|
| 常规舰（6 class × 2 faction） | `InstancedMesh` per `(faction, class)` × 3 材质层（实体/线框/发光） | **36** |
| 旗舰（≤ 8） | **独立 Mesh，不进 InstancedMesh**（art 规格 §6.5：需精确排序与独立材质）× 3 层 | **24** |
| 尾焰 | `InstancedMesh` per faction | 2 |
| 底盘光环（椭圆投影） | `InstancedMesh` per faction | 2 |
| 航母舰载机（≤ 384） | 单个 `InstancedMesh` | 1 |
| **小计** | | **65** |

- 旗舰不进 InstancedMesh 是 art 规格的明确要求（§6.5），接受 24 draw call。
- **LOD1 时关闭发光层** ⇒ 36 → 24，24 → 16，合计 **40**。
- **LOD2 时全部退化为 billboard**（1 个 `InstancedMesh`，单层）⇒ **1**。

### 3.2 LOD 触发：**统一用「舰船屏幕投影高度（px）」**（team-lead 对 C-7 的裁决）

> **本节为 R2 终稿，取代 R0/R1 的"按世界距离"方案。**
> **裁决（team-lead，C-7）**：两侧（美术的渲染 LOD / 设计的信息 LOD）的判据统一用**屏幕投影高度（px）**，不用世界距离。

**为什么这条裁决同时解决了我的单位制阻塞（R-16）**：
R-16 是"美术/UX 用 `1 unit ≈ 15 px`，工程用 `1 unit = 六边形间距`，差 3 倍"。**px 是唯一真相，不需要换算。** LOD 改成 px 判据后，美术、UX、工程三方写的是同一个数，**R-16 在 LOD 这个维度上被完全消解**（相机距离仍用"格"，见 ADR-002 §2.1.1 的"阈值用格、尺寸用像素"）。

**采纳设计侧重定标的四档**（`docs/design/3d-tactical-battle/` 信息 LOD 分级）：

| 档 | 屏幕投影高度 | 层策略 | 每舰 tris（名舰旗舰 / 战列） | draw call |
|---|---|---|---|---|
| **L0 全信息** | **≥ 48 px** | 实体 + 线框 + 发光 三层全开 | 1,100 / 410 | 65 |
| **L1** | **24 – 48 px** | 实体 + 线框（关发光） | 380 / 150 | 40 |
| **L2** | **12 – 24 px** | 实体 + 线框（关发光、降采样） | 380 / 150 | 40 |
| **L3 编队聚合** | **< 12 px** | 单层 billboard + ▲/◆ 编队标记 | ~2 | 1 |

**计算方式**（每帧、每舰队一次，不是每舰）：

```ts
// 舰队旗舰的世界包围盒高度（格）→ 屏幕像素
const pxPerHex = viewportH_px / (2 * camera.position.distanceTo(FLEET_ANCHOR) * Math.tan(fov / 2));
const screenPx = FLEET_SILHOUETTE_HEX * pxPerHex;   // FLEET_SILHOUETTE_HEX = 战列舰 0.733 格
```

- 判据用**舰队**而非单舰：同一支舰队的所有舰船共享一个 LOD 档（否则阵型里会出现"一半实体一半 billboard"的撕裂感）。
- **滞回**：档位边界 ±**4 px**（约 1/6 档宽）。以 24px 边界为例：从 L1 升到 L0 需 > 28px，从 L0 降到 L1 需 < 20px。
- **每帧重算**：`pxPerHex` 每帧只有 1 次除法，8 支舰队共 8 次乘法 ⇒ 可忽略。

**两档相机各落在哪一档**（720p / fov 45°，`random` 地图）：

| 相机档 | 距离 D | 可见格宽 | 战列舰投影 | **LOD 档** |
|---|---|---|---|---|
| **默认档**（主用） | **25.5 格** | 37.5 格 | **25 px** | **L1**（24–48）✅ 有体积、可读可点 |
| **全局档**（辅助，fit×1.15） | **60.1 格** | 88.5 格 | **10.6 px** | **L3**（<12）✅ 编队聚合标记接管识别 |
| **全局档**（对齐 2D zoom 0.2） | **96.5 格** | 142.1 格 | **6.6 px** | **L3** |
| 手动拉到最近（minDistance） | 4 格 | 5.9 格 | **159 px** | **L0** |

**⇒ 全局档下 L3 是主用档**（team-lead 的判断正确）。这正是 `ship-assets.md` §4.4 的 ▲/◆ 编队聚合标记存在的意义 —— **L3 下敌我识别完全由编队标记承担**（8 个 billboard，8 draw call，已计入预算）。

**四档阈值取值是否合理（工程侧复核）**：

| 检查 | 结果 |
|---|---|
| 48px 是否够看清？ | 战列舰 48px 长 × ~10px 宽，舰桥/舷台细节约 3–5px ⇒ **L0 的"全细节"在 48px 下仍有部分不可辨**。但 L0 只在 D < 13.3 格触发（比默认档近 2 倍），是"特写档"，够用。 |
| 12px 是否该切 billboard？ | 12px 时舰体轮廓约 4 个像素宽，线框层会产生严重摩尔纹 ⇒ **切 billboard 是对的**。 |
| 24px 边界是否落在默认档正中？ | 默认档 25px，距 24px 边界只有 1px ⇒ **有抖动风险**！滞回 ±4px 覆盖了它（降到 L2 需 <20px），但**建议把默认档设为 28–30px 以留出裕度** —— 即 D_default = 636.92/28 ≈ **22.7 格**。**需 UX 确认（A6-Q8）** |
| L1（24–48）与 L2（12–24）的层策略相同，有意义吗？ | L2 额外做"线框降采样"（art `ship-assets.md` §7）。若实测降采样收益不明显，**可合并 L1+L2 为一档**，简化实现。 |

### 3.3 半透明与 InstancedMesh 的排序问题

art 规格 §2.2 要求每层 `depthWrite: false`（避免半透明互相吞）。但 **`InstancedMesh` 内部不排序实例** ⇒ 大量半透明舰体重叠时会有绘制顺序错误。

**处置**：
- 实体层 `opacity = 0.22`，线框层 `opacity = 0.88`，两者都 `depthWrite: false` ⇒ 顺序错误表现为"某些舰的实体层盖住了另一艘的线框层"。
- 在暗背景 + 全息风格下，这种错误**观感上是可接受的**（反而像全息体积叠加），且 art 规格已接受"透明排序复杂度上升"这一代价。
- 若实测不可接受 ⇒ 退路：实体层改 `depthWrite: true` + `alphaTest` 风格的硬边（牺牲柔和度换正确遮挡）。记录为 A6-Q2。

## 4. 特效池（全部预分配 InstancedMesh）

| 特效 | 池容量 | geometry | 每实例 tris | 小计 tris | draw call |
|---|---|---|---|---|---|
| 主炮激光（细长 box，billboard） | 128 | Box(1, 0.02, 0.02) | 12 | 1,536 | 1 |
| 导弹/炮弹（小球 billboard quad） | 256 | 2-tri quad | 2 | 512 | 1 |
| 护盾涟漪（圆环） | 32 | Ring(32 seg) | 64 | 2,048 | 1 |
| 爆炸（低模球） | 24 | Icosahedron(detail 0) | 20 | 480 | 1 |
| 伤害数字（图集 quad） | 64 | 2-tri quad | 2 | 128 | 1 |
| 尾焰 | 128 | Cone(6 seg) | 12 | 1,536 | 2 |
| 底盘光环 | 128 | 椭圆 disc(12 seg) | 24 | 3,072 | 2 |
| 舰载机 | 384 | 2-tri quad | 2 | 768 | 1 |
| **小计** | | | | **10,080** | **10** |

**伤害数字为什么不用 `CSS2DRenderer`**：`CSS2DRenderer` 每个标签是一个 DOM 节点。密集齐射（6 发导弹 × 8 舰）会产生数十个 DOM 节点/秒，在 WebView2 里 DOM 操作比 GPU 实例慢一个数量级。改用**数字图集 + InstancedMesh**：预生成 `0-9` 与 `-` `!` 的 CanvasTexture 图集（1 张 256×32），每个数字实例通过 `instanceUvOffset` 属性选字。1 draw call。

**尾焰用 Cone 而非粒子系统**（[PLACEHOLDER] 已定案）：art 规格 §2.1 已选"程序化锥形"，工程侧确认。128 个 cone × 12 tris = 1,536 tris，2 draw call。

| 维度 | Cone（选定） | 粒子系统 |
|---|---|---|
| tris / draw call | 1,536 / 2 | 每舰 ~16 粒子 × 128 舰 = **2,048 实例**，2–4 draw call |
| CPU | 每帧写 128 个 `instanceMatrix` | 每帧模拟 2,048 个粒子的生命/位置/透明度 |
| 软渲染（R-15） | 填充率可控 | **overdraw 致命**（半透明粒子叠加） |
| 与 2D 现状 | 2D 用的是 `flame.png` 长条贴图（3:1），**本来就不是粒子** ⇒ 观感连续 | 会改变既有观感 |
| 闪烁/脉动 | 靠 shader uniform 里的双频正弦 | 靠逐粒子噪声 |

**观感等价性处理**：Cone 用 `MeshBasicMaterial` 会显得硬。改为 **Additive 混合 + 顶点色渐变**（根部亮、尾部 alpha→0），配合与 2D 完全相同的双频闪烁
`flicker = 0.75 + sin(phase*1.3)*0.20 + sin(phase*2.7)*0.08`（BattleScene.ts:2787 逐字搬）。
⇒ 与 2D 尾焰的差异仅为"贴图柔和边缘"vs"顶点渐变"，属可接受差异。

## 4.1 战术雷达技术选型：**2D Canvas 覆盖层**（[PLACEHOLDER] 已定案）

| 方案 | draw call | 与后处理的关系 | 软渲染（R-15） | 工时 |
|---|---|---|---|---|
| **A. 2D Canvas 覆盖层（选定）** | **0**（不进 WebGL） | 独立，不受 Bloom/CRT 影响 | ✅ 仍可用 | ~150 行 |
| B. DOM / CSS | 0 | 独立 | ✅ | ~250 行且每帧 DOM 写入，慢 |
| C. 正交相机第二遍渲染（scissor + viewport） | **+18~83**（棋盘+舰船简化重绘） | 需单独处理，否则被 CRT/Bloom 污染 | ❌ 渲染成本翻倍 | ~300 行 |

**选 A 的理由**：
1. **零 draw call**。本预算里 draw call 余量虽已宽裕（<180），但雷达是"常驻 UI"，不该占用战场渲染的预算。
2. **战略层已有可移植实现**：`ThreeStrategicMap.drawMinimap()`（`ThreeStrategicMap.ts:496`）。直接搬画法，风险低。
3. **不受后处理污染**：Bloom 会把雷达的亮像素糊开，CRT 扫描线会让它闪烁 —— 走 WebGL 就必须为它单独开一个不被后处理影响的通道（额外复杂度）。Canvas 天然独立。
4. **软渲染降级时仍可用**：R-15 的 `low` 档会关 Bloom 和大部分特效，但 Canvas 2D 是 CPU 绘制，不依赖 GPU ⇒ 雷达在最低画质下依然工作。
5. **雷达本来就该是 2D**：它是"战场态势缩略图"，2D 俯视是最合适的表达，正交相机的 3D 信息（高度）在缩略图尺度上完全不可辨。

**性能关键 —— 分层重绘**（否则 1951 格每帧画 2D canvas 会很慢）：

```ts
// 底层（地块归属）：只在 view.tiles.revision 变化时重绘到 offscreen canvas（≈1–10 Hz）
// 上层（舰队点）：每帧画，≤ 64 个 3px 圆点 + 阵营色
// 视口（相机可见范围框）：每帧画 1 个矩形
```
⇒ 每帧的 2D 绘制量 = ~65 个图元，可忽略。

**数据源**：`BattleView.fleets[].x/y`（逻辑平面）+ `BattleView.tiles.ownerId` + `onCameraInfo` 的可见范围。**不需要给规则层加任何新接口** ⇒ 不产生规则回归（V-P4-13）。

## 5. 性能预算表（R2 · 已与美术侧对账）

> 基准：1280×720 @ 60fps（16.67 ms/帧），中低端集显，Edge WebView2。
> **R2 变更**：① 采用美术侧预算（tris 峰值 30,000 / 硬上限 36,000 / draw call <180 / 粒子 ≤3,000）作为工程侧约束，取代 R1 自定的 60,000 / 120。② 棋盘改 B5 三层结构（§2.2）。③ LOD 改 px 判据（§3.2）。

### 5.1 与美术侧预算的对账

| 项 | 美术侧 | 工程侧 R2 推导 | 判定 |
|---|---|---|---|
| **三角形峰值** | ~30,000 | **~19,000**（默认档）/ **~13,800**（全局档） | ✅ 余量 37% |
| **三角形硬上限** | 36,000 | **~26,000**（最坏组合，见 §5.2） | ✅ 余量 28% |
| **draw call** | < 180 | **95**（默认档 L1）/ **120**（最近 L0）/ **49**（全局档 L3） | ✅ 余量 47% |
| **粒子 / 并发实例** | ≤ 3,000 | **~1,016**（池容量） | ✅ 余量 66% |
| **后处理** | 3 pass | RenderPass + Bloom(0.5×, 内部 ~10 sub-pass) + CRT = **2 个可见 pass** | ✅ |
| **同屏单位数** | — | ≤ 128（典型 48–64） | — |
| **棋盘格子数** | — | ≤ 2048（实测 1951） | — |

> **结论：工程侧全部落在美术预算内，且三角形/draw call 都有 >25% 余量。**
> R1 版之所以顶到上限，是因为用了"全裙边"棋盘（31,216 tris）且全局档无剔除。B5 结构（§2.2）解决了这一点。

| 项 | 工程侧预算（R2） | rationale |
|---|---|---|
| **逻辑 tick（`TacticalSim.tick`）** | **≤ 3.0 ms** (p95) | 现状实测 ~3.9 ms（§6.1 推导）；优化目标 1.5 ms |
| **渲染（`renderer.sync`）** | **≤ 8.0 ms** (p95) | 60fps 预算：逻辑 3 + 渲染 8 + Vue 1 + 合成 4 = 16，余 0.67 ms |
| **Vue 响应式** | **≤ 1.0 ms** (p95) | ADR-004 的 10Hz 拆分后目标 ≤ 0.3 ms |
| **显存** | **≤ 150 MB** | 1 个 WebGL context（后台 1280×720 RGBA ≈ 3.7MB + 深度 ≈ 1.8MB）+ 2 个半分辨率后处理 RT ≈ 1.8MB + 几何/纹理 ≈ 60MB |
| **帧率下限** | **≥ 30 fps** | 60fps 是目标，30fps 是红线；跌破按 §7 自动降级 |

### 5.2 三角形推导（按 LOD 档 / 相机档）

**棋盘列已计入 §2.3 的 16 块剔除 + §2.2 的裙边阈值（典型 200 条）**：

| 场景 | 距离 D | 可见格宽 | **棋盘（剔除后）** | 舰船 | 特效 | 星球 | 杂项 | **合计** |
|---|---|---|---|---|---|---|---|---|
| **L0 特写** | 13.3 格 | 19.6 | 1,951 + 2 + 720 = **2,673** | 16 艘 L0 = `2×1,100+14×410` = **7,940** | 10,080（满） | ~500 | 500 | **21,693** |
| **L1 默认档** | 25.5 格 | 37.5 | 3,902 + 2 + 1,440 = **5,344** | 22 艘 L1 = `3×380+19×150` = **3,990** | 5,040（50%） | 1,920 | 500 | **16,794** |
| **L1 默认档（满编）** | 25.5 格 | 37.5 | 5,344 | 40 艘 L1 = `5×380+35×150` = **7,150** | 5,040 | 1,920 | 500 | **19,954** |
| **L3 全局档** | 60.1 格 | 88.5 | 7,804 + 2 + 2,400 = **10,206** | 64 艘 L3 billboard = **128** | 1,008 | 1,920 | 500 | **13,762** |
| **L3 全局档（zoom 0.2）** | 96.5 格 | 142.1 | 10,206 | 128 | 1,008 | 1,920 | 500 | **13,762** |

**最坏组合**（L0 特写 + 裙边池打满 1024 + 特效池满 + 星球全可见）：
`2,673 + (12,288−2,400) + 7,940 + 10,080 + 1,920 + 500` = **~26,000** ⇒ 硬上限 36,000 余量 **28%** ✅

> **为什么"全局档"不是最坏场景**：全局档下所有舰船都是 L3 billboard（128 tris），棋盘虽然全部提交但只有 10,206 tris。**最坏场景永远是"最近 + 特效最密"**，而不是"最远"。这一点与直觉相反，是 R1 版算错的根源（R1 把"全盘可见"当成最坏）。

**剩余加压阀（若实测超标，按序启用）**：

| 阀 | 动作 | 省三角形 | 代价 |
|---|---|---|---|
| **V-2** | 特效池容量下调 40% | ~4,000 | 极限齐射时特效被丢弃 |
| **V-3** | L1 档也关闭实体层，只留线框 | ~3,000 | 体积感下降 |
| **V-4** | chunk 从 16 增到 32（更细剔除） | ~4,000 | +16 draw call（95 → 111，仍在 180 内）✅ 可用 |

### 5.3 draw call 推导

| 来源 | L0（特写） | L1（默认档） | L3（全局档） |
|---|---|---|---|
| 棋盘（基板 1 + 顶盖 16 + 裙边 1） | 18 | 18 | 18 |
| 舰船（12 组 `faction×class` ×3 层 + 8 旗舰 ×3 层） | 65 | 40 | 1 |
| 特效池 | 10 | 10 | 3 |
| **L3 编队聚合标记**（▲/◆，`depthTest:false` 不可合批） | 0 | 0 | **8** |
| 尾焰 / 光环 / 舰载机 | （计入特效池） | | |
| 星球 / 要塞 / 网格线 / 引导线 / 背景 | 7 | 7 | 7 |
| 后处理（RenderPass + Bloom~10 sub-pass + CRT） | 12 | 12 | 12 |
| **合计** | **120** | **95** | **49** |

- 三档全部 **< 180**（美术预算）✅，且 L1/L3 远低于我 R1 自定的 120。
- **R1 担心的"draw call 余量仅 2 个"（R-18）已被解除**：美术预算是 180 而非 120，且 L3 档只需 49 个。**R-18 从 A 级降为 C 级**（记录为已知约束，不再是风险）。

### 5.4 Wails / WebView2 的 WebGL 实际能力（**必须探测，不能假设**）

Wails v2 在 Windows 上用 **Microsoft Edge WebView2（Chromium）**。它**可能**回落到软件渲染：

| 场景 | 渲染器字符串 | 后果 |
|---|---|---|
| 正常（有 GPU 驱动） | `ANGLE (Intel, Intel(R) UHD Graphics ...)` / `NVIDIA ...` | 正常 |
| **无驱动 / VM / 远程桌面** | `SwiftShader` / `Google SwiftShader` / `llvmpipe` / `Microsoft Basic Render Driver` / `WARP` | UnrealBloomPass 在 1280×720 下可到 **100+ ms/帧** ⇒ 完全不可玩 |

**强制的启动探测**：

```ts
// postfx.ts —— 在 ThreeTacticalBattle 构造时执行一次
const gl = renderer.getContext();
const dbg = gl.getExtension('WEBGL_debug_renderer_info');
const rendererName: string = dbg
  ? String(gl.getParameter(dbg.UNMASKED_RENDERER_WEBGL))
  : 'unknown';
export const isSoftwareGL = /swiftshader|llvmpipe|basic render|warp|software/i.test(rendererName);

// 探测结果驱动的初始档位
const quality: 'high' | 'medium' | 'low' = isSoftwareGL ? 'low'
  : (gl.getParameter(gl.MAX_TEXTURE_SIZE) < 4096 ? 'medium' : 'high');
```

| 档位 | `pixelRatio` 上限 | Bloom | 后处理 | 默认 LOD 偏移 | 特效池 |
|---|---|---|---|---|---|
| `high` | `min(dpr, 1.5)` | 开（0.5× 分辨率） | Bloom + CRT | 0 | 100% |
| `medium` | `min(dpr, 1.25)` | 开（0.35× 分辨率） | Bloom + CRT | +1 档（更快进 LOD2） | 60% |
| `low`（软渲染） | **1.0** | **关** | **仅 CRT**（单 pass） | **强制 LOD2** | 30% |

`pixelRatio` 上限为什么是 **1.5** 而不是战略层的 `2`：战略层只有 59 个节点、几何简单；战术层有 31k 三角形的棋盘 + 128 舰 + 特效池。**在 DPR=2 的 4K 屏上，pixelRatio 2 意味着 2560×1440 的渲染目标 = 3.7M 像素**，集显填充率扛不住。1.5 → 2.1M 像素。

## 6. 逻辑层（规则域）的性能：不能只优化渲染

### 6.1 现状复杂度推导（实测行号）

`update()` 每帧对 `tilesList`（1951）的完整遍历：

| 行 | 位置 | 每次成本 | 每帧次数（8 舰队） |
|---|---|---|---|
| 2003 | 全局（塔射击） | `tilesList.forEach` | 1,951 |
| 2233 | **每舰队内**（最近敌方价值地块） | `tilesList.forEach` | 8 × 1,951 = 15,608 |
| 2247 | **每舰队内**（最近敌方塔） | `tilesList.forEach` | 8 × 1,951 = 15,608 |
| 2401/2408 | **每舰队内**（撤退补给点，仅 retreating） | `tilesList.forEach` ×2 | ≤ 8 × 1,951 × 2 = 31,216 |
| 2545 | **每舰队内**（探索打分，含 6 邻居内层循环） | `tilesList.forEach` × 6 | ≤ 8 × 1,951 × 6 = **93,648** |
| 3216 | 全局（迷雾，内层循环 ~30 视界源） | `tilesList.forEach` × 38 | **74,138** |
| 3280 | 全局（接壤高亮，6 邻居） | `tilesList.forEach` × 6 | 11,706 |
| **合计** | | | **≈ 243,875 次距离计算/帧** |

按 `Phaser.Math.Distance.Between`（`Math.sqrt(dx²+dy²)` + 属性访问）约 **15 ns/次** 估 ⇒ **≈ 3.7 ms/帧**。

⇒ **现状的逻辑层在最大地图上已经吃掉 22% 的帧预算。** 3D 化后的渲染（8ms）+ 逻辑（3.7ms）+ Vue（1ms）+ 合成（4ms）= **16.7 ms —— 正好卡在 60fps 红线上，零余量。**

### 6.2 优化方案：**结果逐位相同**（不改变任何行为）

| # | 优化 | 影响行 | 预估节省 | 为什么结果不变 |
|---|---|---|---|---|
| **O1** | **平方距离**：`Distance.Between(a,b) < R` → `dx²+dy² < R²` | 全部 36 处 | ~30% | `sqrt` 单调，`x < R ⟺ x² < R²`（两边非负） |
| **O2** | **视界源缓存**：3216 的内层 `allyVisionNodes` / `allyFleets` 位置每帧算一次，不在 tile 循环内重复读 `sprite.x/y` | 3216 | ~40% of 该项 | 纯缓存，无语义变化 |
| **O3** | **价值地块索引**：维护 `team → valuableTiles[]`（`castle/planet/barracks/gold_mine/tower/pier`），在**归属权变化时**增量更新，替代 2233 的全表扫描 | 2233 | 15,608 → ~200 | 扫描的是同一个集合，只是不做全表过滤 |
| **O4** | **塔索引**：同上，维护 `team → towers[]` | 2247 | 15,608 → ~50 | 同上 |
| **O5** | **探索打分的空间剪枝**：只对"距舰队 ≤ 探索半径"的格子打分。用 `tilesDict` 做环形展开（从舰队所在格向外扩 ring），而非全表 | 2545 | 93,648 → ~10,000 | **需谨慎**：若"探索半径"小于地图，会漏掉远处的 `-3000` 未探索加分 ⇒ **必须**在剪枝后仍保留"全局最低分"的兜底扫描。见下 |

**O5 的正确性问题（重要）**：当前探索打分是全表取 `minScore`。若按距离剪枝，`score -= 3000`（未探索奖励）可能只在远处成立 ⇒ 剪枝会改变选择。
- **安全做法**：先用环形展开（半径 = 当前 `minScore` 对应的距离上界）扫描近处；若近处已找到 `score < -3000 + 2500`（即已确定优于任何可能的远处未探索格），则提前退出；否则回退到全表扫描。
- 这是一个**保守剪枝**：数学上保证与全表结果一致。若实现复杂，直接跳过 O5（接受 93,648 次的成本）。

**目标**：`3.7 ms → 1.5 ms`（O1 + O2 + O3 + O4 已足够；O5 可选）。

**验证**：golden replay —— 优化前后的事件序列与结果必须**逐项相等**。

### 6.3 **不许做**的"优化"

| 做法 | 为什么禁止 |
|---|---|
| 把迷雾计算从 60Hz 降到 10Hz | 改变行为（敌方舰队可见时机延后最多 100ms）⇒ 违反"规则零改动"。**除非用户明确批准** |
| 把探索打分降到 2Hz | 同上 |
| 合并 `tilesList` 与 `tilesDict` | 不必要，两者用途不同 |
| 用 `Math.hypot` 替代手写 `sqrt(dx*dx+dy*dy)` | `Math.hypot` 在 V8 上**更慢**（要做溢出保护）⇒ 用 `Math.sqrt(dx*dx+dy*dy)` |

## 7. 自动降级阶梯（跌破 30fps 时）

| 级 | 触发 | 动作 |
|---|---|---|
| L-1 | 连续 30 帧 fps < 45 | 关闭 Bloom |
| L-2 | 连续 30 帧 fps < 38 | 常规舰强制 LOD2（billboard），仅旗舰保留 LOD1 |
| L-3 | 连续 30 帧 fps < 32 | `pixelRatio` 降到 1.0；关闭护盾涟漪与伤害数字 |
| L-4 | 连续 60 帧 fps < 26 | 全部 LOD2 + 关闭 CRT 后处理（只剩 RenderPass）+ `store.triggerToast('已切换到低画质模式')` |

**恢复**：连续 120 帧 fps > 55 时逐级回退（带 10 秒冷却，防止在阈值附近反复横跳）。

## 8. 后果

### 正面

1. **棋盘从 46.8k 降到 10.2k（典型）/ 20.1k（上限）** —— 靠「基板 + 裙边阈值 0.25 + 顶盖 16 块剔除」三招，相对 B1 削减 **78%**。这是工程侧能落在美术 36,000 硬上限内的决定性因素（R1 的"全裙边"31.2k 做不到）。
2. LOD 与降级阶梯让最坏机型仍可玩（30fps 红线）。
3. 逻辑层优化有明确的目标值（3.7 → 1.5 ms）与**自动验证手段**（golden replay）。
4. **R-18（draw call 余量仅 2 个）已解除**：美术预算是 <180 而非我 R1 自定的 120，且 L3 全局档只需 49 个。
5. **R-16（单位制冲突）在 LOD 维度上已消解**：LOD 改用 px 判据后，art / UX / 工程三方写的是同一个数，不需要换算。

### 负面 / 代价

1. **默认档 25px 距 L1 下界 24px 只有 1px**（滞回 ±4px 已覆盖，但裕度不足）⇒ 建议默认档改 **28px**（D=22.7 格）。见 A6-Q8。
2. **半透明 InstancedMesh 无法逐实例排序** ⇒ 会有叠加顺序错误。已接受（art 侧亦接受）。
3. **`InstancedMesh` 的 `computeBoundingSphere()` 需要每帧调用**（舰船移动）⇒ 见 ADR-003 §2.4 的降级预案。
4. **棋盘"基板"是一个隐含假设**：它假设所有低格（<0.25）下方的缝都由基板遮住。若将来新增 `ELEVATION` 在 0.25–0.30 之间的地块类型，需要重新检查缝的可视性。
5. **性能预算中的多数数值是推导值而非实测值**。所有 `[PLACEHOLDER]` 必须在 Phase 3 结束前用 §9 的验证命令实测并回填。

## 9. 验证方式

| 编号 | 验证 | 命令 / 判据 |
|---|---|---|
| **A6-1** | 三角形 / draw call 实测 | dev 构建下读 `renderer.info.render.{triangles, calls}`，在**三档各采样一次**。判据：**triangles ≤ 30,000（峰值）/ 36,000（硬上限）且 calls ≤ 180**。三档预期：L0 特写 120 / L1 默认 95 / L3 全局 49 |
| **A6-8** | **两档切换后预算不退化** | 连续切换 20 次（默认↔全局），每次稳定后读 `renderer.info.render.triangles`。**判据：20 次读数全部 ≤ 30,000，且 L3 档 ≤ 15,000**（证明全局档没有"棋盘全提交 + 舰船全 LOD0"的组合） |
| **A6-9** | **LOD 档位边界无抖动** | 缓慢推拉相机穿过 48 / 24 / 12 px 三个边界各 5 次，记录 LOD 档位切换次数。**判据：每个边界来回 5 次，切换次数 = 5（不是 10+）**，证明 ±4px 滞回生效 |
| **A6-2** | 棋盘渲染成本 | 单独关闭其他层，只渲染棋盘，测 `renderer.info.render.triangles` 与帧时间，判据 **≤ 0.5 ms**；且在 L3 全局档下棋盘三角形 ≤ **11,000** |
| **A6-3** | 帧时间分解 | 在 `TacticalHost.#frame()` 中插桩三段（sim / renderer / vue），外部用 Chrome Performance 交叉验证。判据：**sim p95 ≤ 3.0 ms，renderer p95 ≤ 8.0 ms** |
| **A6-4** | 特效池峰值 | 构造"8 舰队全员齐射 + 6 连导弹 + 要塞开火"，读 `renderer.info.render.calls`，判据 **≤ 120** |
| **A6-5** | WebGL 能力探测 | 在 3 台机器上分别运行并打印 `UNMASKED_RENDERER_WEBGL`：①独显台式机 ②集显笔记本 ③无 GPU 驱动的 VM。记录三台分别落到哪个档位 |
| **A6-6** | 逻辑优化不改变结果 | golden replay：优化前 vs 优化后，事件序列与终局**逐项相等**（见 `08-roadmap` §Phase2-C） |
| **A6-7** | 降级阶梯 | 人为把 `pixelRatio` 设为 4 制造卡顿，确认阶梯按 L-1 → L-4 依次触发且 toast 出现；恢复正常后能在 2 分钟内逐级回退 |
