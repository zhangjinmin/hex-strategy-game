## ① 架构现状速览

```
App.vue (is3dBattle = mapStyle === '3d')
   ├─ Phaser.Game ── BattleScene (4139 行)  ← 唯一逻辑真源，持续 update()
   │                    └─ 画布被 body.battle3d-mode { visibility: hidden } 隐藏（App.vue:584）
   └─ Battle3DOverlay (1431 行)  ← 每帧从 BattleScene 公开字段同步，独立 rAF + 独立 WebGL context
        渲染管线：主场景 → 离屏 MSAA RT(samples:4) → CRT 全屏合成 → 默认帧缓冲
        App.vue:318/337 驱动 window.resize；App.vue:249 有 8s 未就绪降级
```

**3D 层职责边界**：纯渲染，零逻辑。占领/补给/AI/CP 全在 BattleScene，overlay 只 `drainFx3d()` 消费事件。这个切分是对的。

**三个结构性事实（决定后面所有结论）**：

1. **两个独立 WebGL context** —— Phaser 一个，overlay 一个。overlay 每次进出战斗重建一个。
2. **overlay 通过 `any` 读 BattleScene 私有字段**（`factionMap`、`handleTileClick` 都是 private）—— 零编译期保护。
3. **CPU 大头不在 3D 层**。overlay 每帧约 5.4k 次迭代，Phaser `update()` 侧约 53.9k 次 —— **3D 层只占 1/10**（详见 §③ 对照表）。先优化 3D 层是搞错重点。

### 2.3 累积泄漏路径（重复进出 3D 战斗）

触发场景：切 `mapStyle` ↔ 3d（App.vue:258 watch）、战斗结束返回菜单、8s 降级销毁（App.vue:249）、`tryCreate3dOverlay` 重试前先 destroy（App.vue:236）。

| 项 | 每次泄漏 | 类型 | 撞墙条件 |
|---|---|---|---|
| **WebGL context** | **1 个** | **硬上限** | **约 16 次进出即失败** |
| hexInst instance buffer | 235 KB | 显存 | 16 次 ≈ 3.8 MB |
| boatInst instance buffer | 3.6 KB | 显存 | 可忽略 |
| starTex | 4 KB | 显存 | 可忽略 |
| flame 等 JS 侧 buffer | 32 KB | JS 堆 | GC 可回收 |

> **结论：显存量级（≈248 KB/次）不致命；致命的是 WebGL context（1 个/次，约 16 次撞墙）。**
> **排期建议：L1 一行代码、零风险、必须最先做。** 与用户已报的"第二局黑屏"症状吻合 —— 当前归因于 2D 隐藏时序（App.vue:194 注释），但 context 耗尽是并存的可能根因，值得在修完时序后复测"连续进出 16 次"。

**注**：战略层范本 `ThreeStrategicMap.destroy()`（`:2124-2130`）**比战术层更差** —— 它连 `scene.traverse` 都没有，所有 geometry/material 全不释放。之所以没暴露，是因为战略层进出频率远低于战斗层。**这不是范本，是同源债务。**

**GC 压力**：约 **1,000 个临时对象/帧（≈960 字符串 + 1 Set + 2 Color）= 60,000/秒**。V8 新生代能扛，但属完全可消除的浪费。

**本可脏标记驱动却做成每帧全量重算的三处**：
1. `:843` 线框 color buffer —— 只有 ownerId 变化时才需要重传，却无条件全量上传 **891 KB/帧**。
2. `:985-987` 舰船受创色 —— 每帧无条件 `setHex`，应先比后写。
3. `:992` 死亡检测 —— 应改为由 `drainFx3d` 的 destroy 事件驱动，而非每帧全表扫描。

**特效路径无池化（战斗高烈度时的真实热点）**：
- `spawnLaser` `:1137` —— **每次激光 new CylinderGeometry + new MeshBasicMaterial**，每次一个 GPU buffer 创建+销毁循环。
- `spawnHit` `:1189` —— **每次命中 `createElement('canvas')` + `createRadialGradient` + new CanvasTexture**。颜色只有几个阵营色，**完全可缓存**（现有代码每命中一次上传一张 32×32 纹理）。

**`heightAtPx` 复杂度：O(9) 固定**（3×3 邻域），**不是线性全表扫描** —— 算法选型正确。真正的开销是模板字符串 key，不是查找次数。改用数值 key（`q*10000+r`）或 Int32Array 网格可消除 96% 的字符串分配。

- **地图半径 32（格）** → 六边形地图格数 = 3×32²+3×32+1 = **3,169 格**（验算：3×1024+96+1=3169 ✓）
- **`hexRadius` 26/32/38/44/50（像素）** → `BattleScene.ts:1311-1315` 按总舰数动态取值，**当作世界单位用**（`:637`）
- **两者数值同为 32 纯属巧合，无任何关联。**

### 4.8 CRT 离屏 RT 显存与带宽（`:340-341`，samples:4）

| MSAA resolve（读 4× + 写 1×） | 166 MB |
| Pass2 读 tDiffuse（每像素 3 次采样，cache 友好按 1× 计）+ 写默认帧缓冲 8.3 MB | 41.5 MB |

### 4.9 far 修正的影响（质检 D 系列要求评估）

**关键发现：far 的问题不是"太远"，而是"太近"。方向与直觉相反。**

> **修订记录（2026-09-02，quality-lead 复核后更正）**
> 初稿用**径向距离**度量，口径错误。WebGL 的远裁剪面是**垂直于视轴的平面**，裁剪判定用**视空间深度** `dot(P−cam, forward)`，不是到相机的直线距离。本节数字已按视空间深度重算，初稿高估 10~13%。
> 同时 `span` 已从"推算"升级为"源码坐实"（见 §4.0）。**方向性结论不变，量级下修。**

**深度公式推导**：相机偏移 `(0, d·sin0.96, d·cos0.96)`（`:659`），forward = `(0, −sin0.96, −cos0.96)`。

```
depth = d − py·sin(0.96) − Δz·cos(0.96)
```

**forward 的 x 分量为 0 → 视深与 X 偏移完全无关。** 这是初稿算错的根本原因。

| hexR | span | dist | 初稿（径向，错） | **视空间深度（正确）** | vs far=4000 |
|---|---|---|---|---|---|
| ~~26~~ | ~~2,882~~ | ~~3,314~~ | ~~4,401~~ | ~~4,030~~ | **该档实战不可达，剔除** |
| 32 | 3,547 | 4,079 | 5,416 | **4,960** | ❌ 超出 24% |
| 38 | 4,212 | 4,844 | 6,432 | **5,890** | ❌ 超出 47% |

**hexR=26 档实战不可达**：`:1311` 要求 `totalShips ≤ 4`，但 `:1307` 的 `enemyCount × 6`（`activeFactionCount` 默认 2 → 12 艘起）使该条件恒假。**实战最小档是 hexR=32。** 剔除这一档后结论更干净：**四档全部确定超出，无一例外。**

拉满 `maxDistance` 时：hexR=32 → 7,408；hexR=50 → **11,575**。→ **far 必须每帧随缩放更新，只在 `buildTerrain` 里设一次不够。**

#### ⚠️ 补充：建议公式的余量是 12%，不是 1.7×

quality-lead 建议 `far = camD + mapSpan × 0.5`，称有 ≥1.7× 理论余量。该余量是按**初始朝向**推的（polar 固定 0.96、深度由 Z 半展驱动）。但 **OrbitControls 的 azimuth 无限制**（`:380-389` 未设 `min/maxAzimuthAngle`，可 360° 旋转），**polar 可拉到 `maxPolarAngle = 0.35π`（63°，`:386`）**：

| 因子 | 初始朝向 | **最坏朝向** |
|---|---|---|
| 驱动深度的水平半展 | Zhalf = 48·hexR = **0.433·span** | 转到 X 轴 → Xhalf = 55.43·hexR = **0.5·span** |
| sin(polar) | sin(0.96) = **0.5735** | sin(0.35π) = **0.891** |
| **深度外延** | **0.248·span** | **0.4455·span** |

→ `far = camD + 0.5·span` 对**地形**仍有 **12.2%** 余量（0.5 / 0.4455），**公式可用**；但声称的 1.7× 实际是 **1.12×** —— 是薄余量，不是厚余量。

**代码库自身的 bug 史独立佐证"最坏朝向"才是生效口径**：`:1340` 注释记载旧版 `fog.near = camD + 0.32×span` "吞掉外圈约 36% 地块"。若地形深度外延只有 0.248·span（初始朝向），则 0.32·span 已在地形之外，**不该有任何地块被雾吃到**。该 bug 只有在外延 > 0.32·span 时才可能发生 —— 与最坏朝向的 0.4455·span 吻合（(0.4455−0.32)/0.4455 ≈ 28%，量级一致）。

#### 星空：A-1 修好后仍会被雾吃掉，且建议公式覆盖不到

- 星点 `r = 2500 + random × 1500` → **最大 4,000**（`:552`）；`frustumCulled = false`（`:577`）**只跳过 CPU 剔除，GPU 远裁剪照常生效**
- 按视空间深度：hexR=50 初始视角星点深度 = `6374 + 0.5735·r` = **7,808 ~ 8,668** > far 4,000 → 全部被裁。**quality-lead 的 A-1 归因成立**（其 8,874~10,374 用了径向，数值偏高但结论同向，不影响判定）
- `PointsMaterial`（`:573-576`）**未设 `fog: false`** → 即使 far 覆盖，也会被 `:1343` 的 `fog.near = camD + span×1.05`（hexR=50 ≈ 12,194）吞成雾色 `0x040810` → **仍然看不见**
- **且 `far = camD + 0.5·span` 覆盖不到星空**：hexR=50 拉满需 `camD + 0.891×4000` ≈ **13,762**，公式给 12,969 → **差 793**

> **结论：A-1（星空消失）与 D-9 必须一起修，且 far 要按星空半径定尺寸，不是按地图跨度。**

#### 建议公式（修订版）

```ts
const camD   = this.camera.position.distanceTo(this.controls.target);
const sinMax = Math.sin(this.controls.maxPolarAngle);   // 0.891，勿硬编码
const reach  = Math.max(this.mapSpan * 0.5, STAR_R);    // 地形 X 半展 vs 星空半径 4000
this.camera.far  = camD + reach * sinMax * 1.15;        // +15% 余量
this.camera.near = Math.max(1, this.hexR * 0.2);        // 5.2 ~ 10
this.camera.updateProjectionMatrix();                    // 必须
```

- **放置位置**：`:1341-1345` 的雾块 —— 每帧跑，且 `camD` 已在 `:1342` 算好，**只需把它提出 `if` 块**。放这里白送"自动跟随缩放"，不用额外监听 controls 的 `change` 事件
- **验算**（hexR=50 拉满，camD = 10,198）：`far = 10198 + 4000 × 0.891 × 1.15` = **14,297**；地形需 12,667（余量 **12.9%**）、星空需 13,762（余量 **3.9%**）
- **深度精度**：near = 10 / far = 14,297 → **1,430 : 1**，24-bit depth 无 z-fighting 风险。`minDistance = hexR×3 = 150 ≫ near = 10`，不会误裁近处几何体
- **若不打算救星空**：可退化为 `reach = mapSpan × 0.5`（省掉 STAR_R 项，far 降到 ≈13,080），但必须同步处理 `fog`，否则星空恒不可见，A-1 会换个形态复现

> **§4.8 的 RT 显存/带宽与 far 无关** —— 收窄或放大 far 都不改变任何 §4.8 数字。

### 5.2 双引擎隐式契约的脆弱点

overlay 以 `any` 读取的 BattleScene 字段：`tilesList`、`globalFleets`、`hexRadius`、`factionMap`（**private**）、`handleTileClick`（**private**）。TS strict 下这是**刻意的 any 逃逸**，`vue-tsc` 不会报错 —— **因为全是 any，类型检查完全失效**。

| # | 脆弱点 | 故障模式 |
|---|---|---|
| C1 | **字段重命名零防护** | `tilesList` 改名 → `bs.tilesList \|\| []` 静默为空 → `buildTerrain` 永不执行 → `hexInst` 永远 null → `onReady` 永不触发 → **8 秒后 App.vue 降级销毁（`:249-254`）**。表现为"3D 模式莫名回退 2D"，**静默失败，不崩溃，难定位** |
| C2 | **时序依赖** | `buildTerrain` 在 `tick()` 轮询 `tilesList.length > 0`（`:1312-1320`）。若第二局 BattleScene 重建时 tilesList 短暂非空但内容未就绪 → **建出错误地形且永不重建**（`hexInst` 一旦非空就不再检查） |
| C3 | **undefined 传播** | `:933` `u.sprite.x`。`if (!u.sprite \|\| u.hp <= 0) return`（`:912`）只挡了 sprite 为 null，**挡不住 sprite 已被 `destroy()` 但引用还在**（`BattleScene:216` `u.sprite.destroy()` 在 update 内）。destroy 后坐标变 undefined/0 → `heightAtPx` 返回兜底 0 → NaN 传播 → 舰船消失或飞到原点 |
| C4 | **污染 BattleScene 对象** | `:914` 给 Phaser sprite 打私有属性 `_b3dKey`（值为 `Math.random().toString(36)`）。逻辑层的对象被渲染层打标，职责越界；且随机 key 无碰撞保证（概率极低但非零） |
| C5 | **双份状态无校验** | overlay 维护 `ships` Map 镜像，BattleScene 维护 `globalFleets`。两者无一致性校验，漂移时静默 |

## ⑥ D-1：`scene.sys.setVisible(false)` 方案技术判断

### 6.1 事实核验（已查 `node_modules/phaser` 实际源码，非推测）

| 文件:行 | 代码 | 含义 |
|---|---|---|
| `src/scene/Systems.js:683-695` | `setVisible: function (value) { this.settings.visible = value; return this; }` | 文档注释原文：**"An invisible Scene will not render, but will still process updates."** |
| `src/scene/SceneManager.js:593-601` | `if (sys.settings.visible && sys.settings.status >= LOADING && < SLEEPING) { sys.render(renderer); }` | **render 门控在 `settings.visible`** |
| `src/scene/SceneManager.js:update` | `if (sys.settings.status > START && <= RUNNING) { sys.step(time, delta); }` | **update 门控只看 `status`，不看 `visible`** |
| `src/scene/Systems.js:step` | `events.emit(PRE_UPDATE) → UPDATE → this.sceneUpdate.call(scene,...) → POST_UPDATE` | `sceneUpdate` = `scene.update(time, delta)` |

> **判定：方案 D-1 正确。** `setVisible(false)` 精确命中"停渲染、保逻辑"的语义，是 Phaser 官方支持路径，不是 hack。

**对比当前方案**：`App.vue:584` 的 CSS `visibility: hidden` 只影响浏览器合成，**Phaser 的 WebGL 渲染管线完整执行**（display list 遍历 + 全部 draw call 提交到 GPU，只是最终 canvas 不参与合成）。质检报告 D-1 的描述准确。

### 6.2 风险评估

| 风险 | 说明 | 缓解 |
|---|---|---|
| **R1 `update()` 内的渲染副作用不会停** | `renderIntentLines()`（`BattleScene:2213`）**在 update 内调用**，不在 render 内。`intentLines.clear()` **每帧无条件执行**；仅当 `commandBridge.visible` 为真时才重建线条 | setVisible 覆盖不到。需单独加 `if (!this.sys.settings.visible) return;`（但它已在 `clear()` 之后，需调整顺序） |
| **R2 失去 2D 兜底** | setVisible(false) 后若 3D overlay 运行时崩溃，用户看到**全黑**而非 2D。当前 App.vue 的 8s 降级只覆盖"创建阶段未就绪"，**不覆盖运行时崩溃** | overlay 内 tick 包 try/catch，捕获即 `onError` → App.vue 回调 `setVisible(true)` 回滚 2D。保留 CSS 隐藏作为第二道保险 |
| **R3 收益被高估** | setVisible 只省下 **Phaser 的 display list 遍历 + WebGL batch 提交**（GPU 侧空转）。**CPU 大头（§3.2 的 53.9k 次/帧 AI 全表扫描）在 update 里，setVisible 完全救不了** | 见 §6.4 |
| R4 场景切换 / 输入 | `setVisible(false)` 不影响输入事件与 scene 状态机，无副作用 | — |

### 6.3 替代方案对比

| 方案 | 收益 | 风险 / 代价 | 判定 |
|---|---|---|---|
| **A. `scene.sys.setVisible(false)`** | 一步停掉整个 display list 遍历 + WebGL batch；逻辑 update 完整保留（**已源码验证**） | R1（update 内副作用不停）、R2（无 2D 兜底） | **✅ 采纳** |
| B. `scene.sys.pause()` | 彻底停 | **❌ 不可行** —— pause 停 update，逻辑引擎死掉 | 否决 |
| C. monkey-patch `game.render` / `renderer.pause()` | 绕开 Game 主循环 | Phaser 4 的 `Game.step` 内部直接调 `sceneManager.render`，无公开 hook；patch 内部方法脆弱且升级即断 | **否决** |
| D. 保持 CSS 隐藏 + 把 update 里每帧全量 tilesList 遍历改为降频/空间网格 | **治本**，直接砍掉 53.9k 次/帧 | 改动涉及 AI 逻辑，有回归风险；**1~2 人日 + 完整回归** | **✅ 应做，但独立排期** |
| **E. A + D 组合** | 收益叠加：GPU 侧空转立刻停，CPU 侧 AI 扫描根治 | A（0.5 人日）+ D（1~2 人日） | **✅ 推荐路线** |
| F. A + `update()` 内按 `settings.visible` 跳过视觉副作用 | 覆盖 R1，收益最大 | 需改 BattleScene 一处，风险低 | **✅ 随 A 一起做** |

### 6.4 技术判断（给主程的排期结论）

> **`setVisible(false)` 方案正确、低风险、值得做，但它不是"战术界面卡"的主因。**
>
> **量化对比**：
> - setVisible 省下的是 Phaser **渲染侧**开销（3169 格 display list 遍历 + 全量 draw call 提交 + 特效 Graphics 对象）
> - 但 **update 侧 53.9k 次/帧的 AI 全表扫描仍在跑**（`BattleScene:2495`、`2509`），这部分是 3D overlay 每帧开销的 **10 倍**
>
> **推荐顺序**（按性价比）：
> 1. **L1 `forceContextLoss()`** —— 1 行，零风险，解决"反复进出黑屏"的硬上限（§2.1）
> 2. **A（`setVisible(false)`）+ F（update 内跳过视觉副作用）+ R2 兜底** —— **0.5 人日**，立竿见影停掉 GPU 空转
> 3. **契约测试 C + NaN 兜底 E（§5.3）** —— **0.1 人日**，把静默失败变成显式报错
> 4. **线框 `needsUpdate` 脏标记 + `heightAtPx` 数值 key** —— **0.5 人日**，砍掉 53.5 MB/s 带宽 + 57k 字符串/秒
> 5. **D（`update()` AI 目标搜索降频 + 空间网格）** —— **1~2 人日 + 回归**，这才是帧率主因
> 6. **舰船几何体缓存 / InstancedMesh 批处理** —— **1~2 人日**，draw call 960 → ~20，消除开局卡顿
> 7. **CRT RT 分辨率上限 + 按 dpr 降 samples** —— **0.5 人日**，防 4K@dpr2 的 1.33 GB OOM
