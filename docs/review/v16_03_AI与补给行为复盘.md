## 1. TL;DR

1. **"占领完原地不动 + 敌军路过不动"** = **断粮撤退 → 就地驻留重组（`fleet._regrouping`）** 与 **信标残留（`fleet.targetFlare`）** 两个分支的组合。占领完成后代码本身是正确的（`BattleScene.ts:1450-1451` 写 `state='exploring'/stance='search'`），但**占领动作几乎必然把舰队带到远离基地处 → 补给快速见底 → 下一秒被强制 `retreating`**；撤退/重组分支把目标设成"当前位置"（`:3822-3823`/`:3834-3835`）并**强制关闭开火判定**（`:3851` 的 `!_regrouping`）⇒ 表现为「站桩 + 不还手」。驻留结束条件是 `supply>80`（`:3824`），断粮舰从 ~10 补到 80 需 ~14 秒逻辑 Tick，观感即"发呆"。
2. **"直线飞行、路过敌人不管"** = **信标态（`flaring`）优先级高于一切联战判定**。`BattleScene.ts:3647-3648`：只要 `fleet.targetFlare` 存在且非手动撤退，`state` 被**无条件**写成 `'flaring'`（在接敌评估 `:3649` 之前），而 `flaring` 分支（`:3746-3767`）**不设 `isEngaging`** ⇒ 不移动偏航、不开火。**且它会盖掉"断粮自动撤退"**（`isManualRetreat` 只看 `stance==='fallback'`，`:3634`；断粮撤退只改 `state` 不改 `stance`，`:3636`）——即"带信标的断粮舰会无视撤退令，直直飞向信标并不还手"。
3. **"补给往返怪象"**（本报告置信度最高）= **运输舰的目标释放阈值 70 与舰队撤退退出阈值 80 存在 10 点死区，且运输舰"卸完即返航"**。数值探针复现（§3）：断粮舰撤退途中被运输舰追上 → 停船被补到 **~70–78** → 运输舰**立刻放弃该目标返航** → 舰队补给重新跌破 70 并**继续直线飞回基地**，直到**飞进自己的补给源圈（420）靠源圈 +5 才越过 80 线退出撤退**。运输舰"白来一趟"，与用户描述逐字吻合。**运输舰无法单独把舰队从撤退里拉出来**，只会在 70 附近产生锯齿。
4. **两个"承诺了但没生效"的字段（dead field）**：`fleet._userStanceLockUntil`（`BattleScene.ts:2800` 写入，注释称"12s 用户姿态锁"，**全 src 零读取**）与 `fleet._escortPlayer`（`:587/:589` 写入，**零读取**）。前者意味着"点姿态→下一秒被 AI/断粮逻辑改写"的防护**从未存在**。
5. **设计意图 vs 实际**：`docs/design/战术层深度复盘与章程_20260905.md §4.1` 明写补给源优先级是「**运输舰 > 星球中继 > 基地（就近取）**」，但**舰队撤退的目标从不包含运输舰**——撤退目标只在"最近补给源 / 原地"之间选（`:3820/:3830/:3848`）。这是**实现与已拍板设计不一致**，不是设计取舍。

## 2. 现象 → 证据 → 根因（逐条）

### 现象 A —— 「占领完补给基地后就原地不动，敌军路过也不动」

#### A.0 占领完成时到底写了什么（先排除误解）

| 事实 | 行号 | 说明 |
|---|---|---|
| 占领进度推进 | `BattleScene.ts:1433-1434` | `capTarget.captureProgress += (isInfiltration?100:20)`，由 **1s 逻辑 Tick** 驱动（`:638` 调 `processSupplyAndCapture`，Tick 源 `:478-479` `delay:1000, loop:true`）⇒ 普通占领 = 100/20 = **5 秒** |
| 占领完成结算 | `BattleScene.ts:1440-1462` | `ownerId=fac.id`、`captureProgress=0`、邻近格转 `pending`；**`:1450-1451` 正确写 `fl.state='exploring'; fl.stance='search';`** |
| 退回到"非己方 planet/relay"时清零 | `BattleScene.ts:1463-1464` | 清的是 **`currentTile`（旗舰所在格）** 的进度，**不是 `capTarget`** |
| 占领完成**没有**清信标 | 全 src `targetFlare` 赋值点仅 `:971`(初始化)/`:1545`(投放)/`:2781`(中继送达)/`:3763`(清除) | `:1440-1462` 未清 `targetFlare` ⇒ **若这次占领是"信标驱动"的，信标仍在**（见 A.2） |

**结论**：占领完成后状态机**没有**被写成 `defend` 或"驻留"，`state='exploring'` 是**行为正确**的。所以"原地不动"**不是**占领代码直接造成的——它在占领完成的**下一段**。

#### A.1 根因 A-1（主因）：断粮 → 撤退 → 就地驻留重组（`_regrouping`），且驻留期禁止反击

占领基地意味着舰队深入（离己方补给源远）。舰队的补给消耗为**每 Tick 判一次**：

| 逻辑 | 行号 |
|---|---|
| 源圈内（`chainInfo.inSupply`）→ `+5/tick` | `BattleScene.ts:1330-1333` |
| 源圈外 → `-2/tick`（普通难度；AI 按难度 1/2/4） | `BattleScene.ts:1336-1341` |
| 断粮三段式：`supply<30` → 士气 `-1.5/tick`；`supply<=0 && morale<=0` → `hp -= maxHp*0.02` | `BattleScene.ts:1345-1353` |
| **撤退进入：`supply < 30`** | `BattleScene.ts:3635-3636` |
| **撤退退出：`supply > 80`** | `BattleScene.ts:3637`（早退）与 `:3824`（驻留分支） |

进入 `retreating` 后，每帧执行撤退分支（`:3768-3849`）：

```
3818  const ci4 = this.supplyInfo.get(fleet);       // 上一 Tick 的补给结果
3819  const supplyChainLive = !!(ci4 && ci4.inSupply);   // 源圈内 或 运输舰正在补给
3820  if (command && supplyChainLive && supply < 90) {
3822     fleet._regrouping = true;
3823     fleetTargetX = fleet.x; fleetTargetY = fleet.y;   // ← 目标=当前位置（停船）
3824     const regroupDone = currentSupply > 80;
3825     if (regroupDone) { fleet._regrouping=false; fleet.state='exploring'; fleet.stance='search'; }
3829  }
3830  else if (nearestSupply && !supplyChainLive) { 目标=最近补给源; 到 60 内 → _regrouping, 停船 }
3847  else { 目标 = myFac.castlePos; }               // 兜底回司令部
3851  isEngaging = !!(closestEnemyFleet && minFleetDist < 250 && !fleet._regrouping);
```

**三个叠加效果**：

1. **停船**：`_regrouping` 时目标 = 自身坐标（`:3823`/`:3835`），`distToTarget<5` → 不动（`:4128`）；`distBase` 完全停滞。→ "原地不动"。
2. **不还手**：`:3851` 的 `!fleet._regrouping` **显式关闭** `isEngaging`，而开火门是 `:4310 if (isEngaging && ...)`。敌方舰队路过即便进入 250px 也不开火。→ "敌军路过也不动（更不打）"。
3. **发呆期长**：退出条件是 `supply>80`。断粮舰在源圈内只有 `+5/tick`，从 ~10 补到 80 需 **(80-10)/5 ≈ 14 Tick ≈ 14 秒**（若无运输舰叠加）。这 14 秒内动不了、打不了。

**这是"占领完发呆"最贴合的整链**：把舰队派去/深入占领补给基地 → 补给见底 → 强制撤退 → 在刚占领的基地（现在是我的补给源，进圈了 → `supplyChainLive=true`）内**驻留 10~14 秒**重组，期间无视一切。

> 佐证：`docs/design/战术层深度复盘与章程_20260905.md §4.1` 的断粮三段式与"到达补给点后等待恢复"本就是**设计要求**（`BattleScene.ts:3770` 注释"到达补给点后等待恢复"）。所以"驻留"**是设计**，但 **①驻留期完全禁止反击、②退出阈值 80 导致过久** 是**缺陷**。

#### A.2 根因 A-2（次因）：信标残留 → `flaring` 态原地等待

若占领是玩家用**信标**驱动的（`deployFlare` 写 `nearest.targetFlare`，`:1545-1546`）：舰队 `flaring` → 飞到信标 → 距离 <40 时按信标格判定（`:3746-3767`）：

```
3754  const isUncapturedPlanet = 该格是 planet/relay 且 ownerId !== 我的 factionId;
3755  const isEnemyTile = 该格 ownerId != 0 && != 我 && 敌队;
3759  if (isEnemyTile) { fleetTargetX = fleet.x; fleetTargetY = fleet.y; }   // ← 停在信标格"等占领"
3762  else if (!isUncapturedPlanet) { targetFlare = null; state = 'exploring'; } // ← 只有这一条会清信标
```

占领在 `processSupplyAndCapture`（`:1391-1462`）里完成，但**占领完成不清信标**。于是：

- 占领完成后，信标格 `ownerId` 已变我 → 下一帧 `flaring` 分支走 `:3762` 清信标 → 正常回 `exploring`。**这条路能自愈**。
- 但若**信标格不是被占领的那一格**（玩家点在星球**旁边**，`capR = hexRadius*2` 覆盖到星球，占领成功；但信标格是普通格）⇒ `:3762` 的 `!isUncapturedPlanet` 也会成立 → 清信标 → 也自愈。
- **真正卡住的情况**：舰队因友军排斥/风阻漂移出 40px、或信标格解析为**相邻的敌方格**（`isEnemyTile=true`）→ 舰队持续"停住等一个够不到的占领"，信标永不清除。这条**依赖地图细节**，属**观察项**（见 §5）。

#### A.3 根因 A-3（制度性）：`_regrouping` 残留

`fleet._regrouping` 只在 `:3826` / `:3842`（撤退分支内部）被复位。若舰队从 `:3637`（早退通道，`supply>80`）离开撤退，**`_regrouping` 不会被清**，残留为 `true`。一旦该舰队**下次**再进入撤退，`:3851` 会因残留的 `!fleet._regrouping===false` 而**永久关闭** `isEngaging` ⇒ 再也不会拖刀还击。属**状态泄漏 bug**。

### 现象 B —— 「发出去的舰队直线飞行，路过敌人也不管」

#### B.1 根因（唯一）：`flaring` 优先级高于联战，且不设开火

```
3634  const isManualRetreat = fleet.stance === 'fallback';
3635  if (state!=='retreating' && (isManualRetreat || supply<30)) state='retreating';
3637  else if (state==='retreating' && !isManualRetreat && supply>80) state='exploring';

3647  if (fleet.targetFlare && !isManualRetreat) fleet.state = 'flaring';   // ← 无条件覆盖
3649  else if (fleet.state !== 'retreating') { ... 接敌评估(closestEnemyFleet/engageDist=900/1000) ... }

3746  if (fleet.state === 'flaring' && fleet.targetFlare) {
3747     fleetTargetX = fleet.targetFlare.x; fleetTargetY = fleet.targetFlare.y;   // ← 直线奔向信标
3759     ... isEnemyTile → 停 ...
3762     else if (!isUncapturedPlanet) { 清信标; state='exploring'; }
     }
```

- `isEngaging` 全文件仅两处**置真**：`:3851`（撤退拖刀）、`:3853`（engaging 分支）；`:3612` 为每帧初始 `false`。其余（`:4070`/`:4075`/`:4130`/`:4144`/`:4254`/`:4310`）均是**读取点**。**`flaring` 分支一个合并机会都没有** ⇒ 开火门 `:4310 if (isEngaging && ...)` 恒假 ⇒ **信标态舰队全程不开火**。→ "路过敌人不管"。
- 且 `:3647` 在 `:3635` 之后、`:3649` 之前 ⇒ **信标会覆盖断粮自动撤退**：`isManualRetreat` 只认 `stance==='fallback'`（`:3634`），而断粮撤退（`:3636`）只写 `state` 不写 `stance` ⇒ 断粮舰带信标时，`:3635` 先置 `retreating`，`:3647` 立刻改回 `flaring` ⇒ **无视撤退、继续奔向信标且不还手**。

#### B.2 设计意图判定

- `docs/design/3d-tactical-battle/15-battle-tactics-review.md:73`（V3）把信标定义为「**转进点**」；`09-dual-zoom-modes.md:102` 把信标列为"保留的大尺度指令"。**没有任何设计文档规定"执行信标期间是否应接战"**。
- 因此「路过敌人不管」是**机制未定义（design gap）**，**不是**被文档背书的意图。它**与本项目"舰队自主接战"的总体模型相冲突**——信标事实等价于一纸"停火令 + 强制航向"，玩家观感是"AI 坏了"。
- 对照 `v16_02` 的接口口径（`:1545-1546` 只写 `targetFlare`+`stance='search'`，不写 `state`）：**信标命令本就依赖主循环 `:3647` 才能转 `flaring`**，所以"信标抑制接战"是主循环的锅，不是命令通道的锅。

### 现象 C —— 「飞出去→补给不够→飞回来→碰到补给船补了→还是要直线飞回去」

#### C.0 补给链参数与调用节奏（全部实读）

| 常量/逻辑 | 值 | 出处 |
|---|---|---|
| `SUPPLY_SOURCE_RADIUS` | 420 | `SupplyChainSystem.ts:22` |
| `SUPPLY_RELAY_RADIUS` | 500 | `:26` |
| `SUPPLY_AUX_RADIUS`（运输舰覆盖） | 260 | `:28` |
| `AUX_RESUPPLY_RADIUS`（回港装货） | 300 | `:30` |
| `AUX_CAPACITY` | 100 | `:34` |
| `AUX_LOAD_RATE` | **10/tick ⇒ 新舰装满需 10 秒** | `:36` |
| `AUX_SUPPLY_RATE` | 8/tick | `:40` |
| `AUX_SPEED` | **1.4 px/帧** | `:44` |
| 运输舰目标筛选 | 同阵营 + 源圈外 + **`supply < 70`** | `:159-166`（`:163`） |
| 运输舰卸货 | `+8` 给半径内同阵营舰队；`cargo<=0 → returning` | `:184-197` |
| 运输舰新舰 | `cargo=0, state='loading'`，泊母港 | `:262-268` |
| 舰队 `inSupply`（源圈或运输舰）→ `+5/tick` | — | `BattleScene.ts:1330-1333` |
| 撤销退出阈值 | **`supply > 80`** | `BattleScene.ts:3637` / `:3824` |
| 调用节奏 | `processSupplyAndCapture` 每 **1s**；`moveAuxShips` **每帧** | `BattleScene.ts:638`（`time.addEvent delay:1000` `:479`）· `:4631` |

> **关键量**：当运输舰在 260 内且 `cargo>0`，舰队同 Tick 同时吃到 **运输舰 +8** 与 **`inSupply` +5** = **+13/tick**；运输舰一舱 100 = 约 **12.5 Tick** 的补给量。

#### C.1 根因 C-1（核心）：**阈值死区 70 ↔ 80**

- 运输舰**释放**目标的条件是 `supply >= 70`（`SupplyChainSystem.ts:163`）。
- 舰队**退出**撤退的条件是 `supply > 80`（`BattleScene.ts:3637/3824`）。
- ⇒ 运输舰把舰队补到 **70 ~ 78** 就会**放弃该目标**（下一 Tick 目标筛选跳过它 → 无目标 → `aux.state='returning'`，`:180`）。舰队此时**仍 <80**、**仍在撤退**，且因目标已被放弃 → `supplyInfo.inSupply=false` → `supplyChainLive=false` ⇒ **恢复直线飞回基地**，同时补给**重新按 -2/tick 流失**。

#### C.2 根因 C-2：运输舰"卸完即返航"，不驻留护航

`SupplyChainSystem.ts:180`（`!target → returning`）与 `:197`（`cargo<=0 → returning`）：运输舰一旦失去目标或空了货就**头也不回地回母港**，不会"陪同目标直到其脱离断粮"。

#### C.3 根因 C-3：首航 10 秒装货延迟

新运输舰 `cargo=0, state='loading'`（`:262-268`），装货 `10/tick`（`:36`）⇒ **断粮发生后的头 10 秒，运输舰零出勤**。此时断粮舰已在全速撤退。

#### C.4 根因 C-4：撤退目标**从不包含运输舰**（设计不一致）

撤退分支目标只在「原地 / 最近补给源 / 司令部」之间选（`:3820/:3830/:3848`），**没有"迎向正在赶来的运输舰"这一支**。⇒ 舰队与运输舰是**两套独立寻路**，唯一的协同是"运输舰钻进 260 后，舰队下一 Tick 才因 `inSupply` 停船"（`:3820`）。这**违反** `章程_20260905 §4.1`「补给源优先级：运输舰 > 星球中继 > 基地（就近取）」。

#### C.5 辅助缺陷

| 缺陷 | 行号 | 影响 |
|---|---|---|
| `collectAuxShips` 每 Tick 用 `castlePos` **覆写** `aux.homeX/homeY` | `SupplyChainSystem.ts:258-259`（`homeOf` = `castlePos`，`BattleScene.ts:1260`） | `resolveAuxHome` 的换港滞后（`:104-106` 的 120px 迟滞）失去"上一次母港"参照 ⇒ **"就近装中继"的防抖保护实际失效** |
| 运输舰只看 `units[0].supply` 判"是否需要" | `SupplyChainSystem.ts:163` + `BattleScene.ts:3631` | 多舰编队只要旗舰满就不触发，其余建制舰被饿 |
| `moveAuxShips` 只在 `dist>=4` 移动，速度 1.4/帧 | `SupplyChainSystem.ts:216-233` | 舰队 `supply∈(30,80]` 时撤退速可达 **~0.9 px/帧**（`fleetSupplyFactor=1.0`，`:4104`），mobility 高时可到 **~1.8** > 1.4 ⇒ **运输舰追不上** |

#### C.6 撤退目标切换的"另一只脚"：退出后回城堡

即使舰队靠运输舰**越过了 80**、退出 `retreating` → `exploring`，`exploring` 分支的兜底是 `:4045-4047` **回司令部 `castlePos`**（无敌人 / 无 `exploreTarget` 时）。再加上 `:4001-4011` 的 `needsTethering`（`supply<75` 时对"远离己方连通网"的格 `+5000` 分）把 `exploreTarget` 拉回己方一侧 ⇒ **补给一恢复，"回家"仍是最短路径**。→ 用户看到的"补了还是要直线飞回去"。

## 3. 时序推演：一次"补给往返"全过程（带秒数）

> 复现脚本 `_v16r3_supply_sim.mjs`（输出 `_v16r3_supply_sim.out.txt`），逐条复刻 `SupplyChainSystem.ts:145-233` 与 `BattleScene.ts:1306-1355 / 3635-3637 / 3820-3848 / 4104-4119`。
> 场景 A：舰队在 1200px 外断粮（`supply=29`），撤退回基地；运输舰为**新建舰**（`loading, cargo=0`，即真实战斗常见态）；`mobility=50`。

| t(s) | 距基地 | supply | 运输舰态(cargo) | 舰队 state | 现场 |
|---|---|---|---|---|---|
| 0 | 1200 | 27 | loading(10) | retreating | 断粮，撤退开始；运输舰**还在装货** |
| 3 | 1087 | 21 | loading(40) | retreating | 直线撤退，补给只掉不涨 |
| 6 | 975 | 15 | loading(70) | retreating | 已掉过 30 线，士气同步下滑 |
| 9 | 866 | **9** | outbound(100) | retreating | **运输舰终于出航**（首航延迟 9~10s 用完） |
| 12 | 757 | 3 | outbound(100) | retreating | 舰队已飞掉 ~440px |
| 15 | 651 | 13 | supplying(92) | retreating | **相遇**：进入 260 半径，舰队**停船**（`:3820`），吃 +13/tick |
| 18 | **651** | 52 | supplying(68) | retreating | 停船不动（`distBase` 停滞=用户看到的"补上了"） |
| 21 | 651→ | **76** | returning(52) | retreating | **`supply≥70` → 运输舰放弃目标返航**（`:163`/`:180`） |
| 24 | 434 | 70 | returning/loading | retreating | 失去补给覆盖 ⇒ **恢复直线飞回**，-2/tick 流失 |
| 27 | 362 | **85** | loading | **exploring** | **飞进自己的源圈（420）**，靠 +5/tick 才越过 80 |

**读数**：
- 全程 `supply` **一直在 70 附近锯齿**（首次被补给后最低回落到 **13**，`out.txt` 记录），**从未在源圈外（>420px）越到 80** ⇒ **运输舰没能把舰队从撤退里拉出来**，舰队最终**靠飞回基地脱困**。
- 这正是用户原话「**中途碰到补给船有了补给，经常性的还是要直线飞回去**」。
- 对照组 D（运输舰**已满载在途**）：`supply` 在 `t=12` 冲到 **78** 仍不足以越 80，同样被放生，`t=23` 在源圈内（381px）才退出。
- 对照组 C（`mobility=100`）：因断粮舰速度慢（`fleetSupplyFactor=0.5`，`:4104`）运输舰及时咬住，**唯一一例在源圈外（562px）被救回**（`t=18`）。⇒ **结果对"运输舰是否及时/是否还剩货"极度敏感** ⇒ 用户感受到的是「**经常性**还要飞回去」，而非"永远"。

## 4. 修复方案选项

> 明确区分【BUG 修复】（当前行为与设计/字段承诺矛盾，应修）与【设计调参】（数值手感），以及【设计决策】（需用户拍板）。

### 4.1 BUG 修复（建议优先）

| # | 问题 | 落点 | 建议 |
|---|---|---|---|
| **B1** | 撤退目标从不包含运输舰 → 与 `章程 §4.1`「运输舰优先」不一致 | `BattleScene.ts:3818-3848` | 新增分支：**若存在"被指派给本舰队、正在赶来/覆盖"的运输舰 → 停船迎候（或向运输舰靠拢）**，而不是飞向远基地。可复用 `this.supplyInfo` 的 `via==='aux'` 与运输舰 `targetFleet` 反查 |
| **B2** | 阈值死区 70↔80 | `SupplyChainSystem.ts:163` ↔ `BattleScene.ts:3637/3824` | **对齐两阈值**，或引入迟滞（如释放阈值 ≥ 撤退退出阈值 + 迟滞带宽）。这是"补了又走"的**直接根因** |
| **B3** | 运输舰卸完/失目标即返航，不驻留 | `SupplyChainSystem.ts:180 / 197` | 目标仍缺补给时应**保持 supplying/跟随**，直到目标脱离或本舱耗尽 |
| **B4** | 占领完成不清信标 | `BattleScene.ts:1440-1462` | 补 `fl.targetFlare = null`（并在有 `playerFlare` 时销毁视觉），杜绝 A.2 的卡死 |
| **B5** | `_regrouping` 可从 `:3637` 早退通道泄漏 | `BattleScene.ts:3637` | 早退时一并 `fleet._regrouping=false` |
| **B6** | `collectAuxShips` 每 Tick 覆写母港，破坏换港滞后 | `SupplyChainSystem.ts:258-259` | 只在"新建/母港为 null"时写 `homeX/homeY`，保留 `resolveAuxHome` 的迟滞语义 |
| **B7** | `_userStanceLockUntil`（`:2800`）与 `_escortPlayer`（`:587/:589`）**写入但零读取** | `BattleScene.ts:2800 / 587 / 589` | 二者承诺的语义（12s 姿态锁 / 玩家护航）**从未生效**。要么接入状态机读取，要么删除字段与注释，避免"承诺≠实现" |

## 5. 不确定项 / 待核

1. **用户真机走的是哪条链**未确定：若是**军议 `mission capture_planet`**（`BattleScene.ts:1969-1987`，每帧 `_missionDest` 牵引），则"占领完不动"更可能是**任务完成后回退到常轨**（`:490`）+ 断粮撤退；若是**信标**，则叠加 A.2 的信标残留。两条归因不同，需真机日志确认真实 `fleet.state/stance/mission/targetFlare/_regrouping`。
2. **`mobility`/统帅实际值未知** ⇒ §3 的速度-追及结论在场景 A 与 C 之间（用户"经常性"正落在此敏感区间）。未拿到真机参战时不敢给单一结论。
3. **A.2 的信标残留是否真会卡死**依赖地图细节（信标格是否为相邻敌方格 / 舰队是否漂出 40px）。本报告为**代码推演**，需真机复现确认。
4. **`currentSpeedFactor` 表示不一致**：`gameStore.ts:2268` 定义为 `ref<number>(1.0)`；`BattleScene.ts:3296` 直接取用（当 number），`BattleScene.ts:4982` 却按 `?.value ?? raw` 兼容对象。若某些运行路径下取到的是 `{value}`，则 `dt` 参与运算会异常。**本轮未在真机验证 dt 的实际类型**，仅登记为风险。
5. **指挥制 `tilesList` 内容未逐项验证**：`exploring` 的 `exploreTarget` 打分（`:3968-4016`）与 `needsTethering`（`:4001-4011`）依赖地块；指挥制下地块经济"形同虚设"（`15-battle-tactics-review.md` V7）。这会影响"退出撤退后到底去哪"，需确认地图生成。
6. **本报告为只读推演 + 数值探针**，**未跑 dev server、未做真机截图**。所有"用户看到"的表述均为**机制推演**，建议由 QA 按 §3 场景复现取证据。
