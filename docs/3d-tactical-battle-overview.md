## 5. 关键技术结论

### 5.1 性能瓶颈是 draw call，不是三角形

| 项 | 美术预算 | 工程实测 | 余量 |
|---|---|---|---|
| tris 峰值 / 硬上限 | 30,000 / 36,000 | 美术自认峰值"几乎不可达" | 充裕 |
| draw call | <180 | 最近档 **120** / 默认档 **95** / 全局档 **49** | **47%** |
| 粒子 | ≤3,000 | ~1,016（池容量） | 66% |

**冲突已解决**：工程 R1 阶段自定保守预算 120（当时算出余量仅 2 个，标为 A 级高风险），R2 修订后**采纳美术口径 180**，余量 47%。

**代价说明**：舰船占 65 个 draw call（12 个 faction×class × 3 材质层 + 8 旗舰 × 3 层）——这是"半透明实体 + 线框"三层材质的**直接成本**，是您为体积感支付的价格。tris 从 50k 降到 36k，靠的是"禁止仰视 → 底面免建模"省下 5,333（投向旗舰 4,020 / 特效 800 / 舰船数 513）。

### 5.2 拾取：平面反解被否决，改用 InstancedMesh raycast

在已拍板的 27° 仰角下，传统"射线打 `y=0` 平面再反解格子"的视差误差达 **1.67 格**（`d = h / tan θ`，要塞高 0.85 单位），点击会判给相邻格。**改用 P2 InstancedMesh raycast 打实际几何体**——精确、自动处理高度与遮挡。

**关键澄清**：`pendingCallback` 签名是 `(targetFleetId: number | null)`，目标选择选的是**舰队不是棋盘位置** ⇒ 打舰船实例，精确无误差。**遗留风险**：将来若加"指定位置"类命令（AOE 选点），视差问题会重现。

### 5.3 LOD 判据统一为屏幕投影像素

美术 R0 用**世界距离**（20 单位切 billboard）是错的——20 单位处战列舰投影 135px，而全图档才 27px，**拉远恰恰是全屏最清晰时，却退化成 billboard**。根因是"把相机距离当成可读性的代理量，两者不成正比"。

已统一为：**LOD0 >48 / LOD1 24–48 / LOD2 12–24 / LOD3 <12 px**，滞回 ±15%，与设计侧信息 LOD 四档 1:1 对齐。

**推论**：战列舰与旗舰在可达距离内**永不退化**（全图档仍有 27–34px）；**舰载机才是拾取困难主体**（4.6px），不是"远处舰船"。

### 5.4 其他已定

- **尾焰选 Cone**：128 cone × 12 tris / **2 draw call**，理由是粒子系统在 WebView2 软渲染下会成为瓶颈（标 `[PLACEHOLDER · 验证 A6-4]`）
- **雷达走 2D Canvas**：复用战略层 `ThreeStrategicMap.drawMinimap`，数据直接取 `BattleView`，**不给规则层加任何新接口**，**0 draw call** 且不受 Bloom/CRT 污染。选型对比中"正交相机第二遍渲染"方案因 +18~83 draw call 被否决
- **Phaser 依赖不能移除**：地图编辑器 `EditorScene` 仍在用
- **选择性 Bloom**：余量从 2 恢复到 47% 后重新有了可能性，但**仍建议不上**，等实测再定

## 6. 重大发现：CP 命令「已配置、未实现」

这是本次评审最有价值的副产品。11 个命令中 **9 个从未生效**（不是配置错误，是实现层空白）：

| 符号 | 位置 | 现状 |
|---|---|---|
| `getDamageMultiplier` | CP:117 | 唯一调用点 `BattleScene:2845` 传 `isDefending=false` ⇒ **CP:126 的 shield 分支永不可达** |
| `getSpeedMultiplier` | CP:138 | **零调用**（只有 import） |
| `getMoraleModifier` | CP:153 | **零调用** |
| `getActiveEffects` | CP:110 | **零调用、零 import**（完全死代码） |
| `reflect` | CP:134 | **只有注释无实现**，配置在 `commandAbilities.ts:107` |
| `teleport` | 配置 `commandAbilities.ts:152` | **无 handler**，且 `durationMs: 0` 入库即过期 |
| `heal` | `commandAbilities.ts:11` 类型已声明 | **无 handler** |

**过渡期状态分布（层 1 完成后）**：

| 状态 | 数量 | 命令 |
|---|---|---|
| 正常可用 | 2 | `focus_fire`、`ecm_jam`（层 1 补完即生效） |
| 部分生效 | 1 | `reinhard_roar`（伤害+50% 真生效；**移速+30% 在配置里根本没有**，描述有一半是假的） |
| 完全无效（置灰） | **8** | 其余 |

**置灰态设计要点**：用 `filter: grayscale(1)` 而非 opacity（极暗底下 opacity 会让文字不可读，而恰恰需要玩家读懂为什么不能用）；角标用 `⚠` 不用 `⊘`（⊘ 是"你不能做"责任在玩家，⚠ 是"这里有问题"责任在游戏）；**点击反馈分通道**——临时不可用（CP 不足/冷却）保留红色抖动+拒绝音，未实现态**不抖动不播拒绝音**只出提示条（未实现是游戏没做完，给玩家"你按错了"的红色抖动会让他们误以为是自己的操作失误）。

**层 2 还卡着三个全局性前置问题**（不解决则单个命令修了也白修）：
1. `durationMs: 0` 语义与实现**正好相反**（注释写"0=瞬时"，实现是"入库即过期"）
2. `Math.max(0.1, mult)` 下限 ⇒ `evasive_maneuver` 的「2 秒无敌帧」**实际是 90% 减伤**，与"闪避所有攻击"不符
3. **士气系统完全不存在**（`morale_rally` 不是接个函数，是要新建整套机制）
